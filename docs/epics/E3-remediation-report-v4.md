## Root Cause Analysis

Three of the four Highs/Mediums this pass fixes (F-1, F-2, F-3) share one root cause, worth stating plainly rather than treating as three unrelated bugs: **every "complete file list" or "complete grid" claim in this document's history has been produced by enumerating the cases the author was actively thinking about, not by a procedure guaranteed to enumerate every case.** F-1 happened because a pointer was written when content existed on the other end, and the pointer was never re-checked after that content was deleted. F-2 happened because the alias fix was reasoned from "what resolves `packages/ui`'s source" (tsc, Next's bundler, Storybook's Vite) without separately reasoning from "what resolves it in each consuming app's own test run" — a fourth axis that only becomes visible if you ask "for every tool that touches this source, does it have its own independent configuration" rather than "have I covered the tools I already listed." F-3 happened because the token-by-token contrast recomputation in Pass #3 iterated the _newly added or corrected_ tokens exhaustively (border, focus-ring, the eight hue-based semantic tokens) but never separately asked "which tokens exist in the shipped `tokens.css` that this grid has never once mentioned" — `--color-text` had been in the shipped file since E1 and was never wrong, which is likely exactly why it was never flagged: nothing about it looked like a problem, so it was never independently checked against the "does every semantic token have a grid row" question. F-4 and F-5 share a related but distinct root cause: both are cases where a _true statement about the rule's text_ ("the rule text is correct," "these values are within DESIGN_SYSTEM.md's range") was written in a way that implied a _false statement about the rule's or value's live status_ ("already enforced," using invented values instead of the already-correct shipped ones). This pass's fix for all five is procedural, not just corrective: §6b's file list is now organized by resolver class with an explicit "checked and found not needed" sub-list (so the next pass has the negative space recorded, not just the positive list); §12.1's grid is now cross-checked against `tokens.css`'s actual token inventory rather than against the set of tokens this document itself has previously discussed.

### F-1 (HIGH) — "ADR-024 points to design-doc §23. That content no longer exists. This recreates the exact documentation-loss problem that earlier reviews rejected."

**Resolution: Closed. Option B chosen (spec moved entirely into the ADR).** `DECISIONS.md`'s ADR-024 now contains, in full: a token-category mapping table (color/radius/shadow/spacing/typography/breakpoints/motion, each with its `tokens.css` source, generated-artifact shape, and Flutter-side consumption target); an explicit naming convention (kebab-to-camelCase, grouped by category); a schema-versioning scheme (a plain incrementing integer, bump conditions stated); consumer compatibility rules and schema-evolution rules (non-breaking vs. breaking changes defined, with the loud-failure requirement stated); failure behavior (three named failure conditions, no fallback); an explicit "unsupported token categories" statement (z-index, with the reasoning — Flutter has no CSS-style z-index concept); and a worked JSON example. The design document's §23 ADR-024 bullet now states plainly that the full specification lives only in DECISIONS.md and explains, for the historical record, how the two-way pointer defect happened (one revision pointed at §23, a later revision deleted §23's content without updating the pointer). §20's T18 row now names ADR-024 by name as the deliverable's specification source, replacing the previous vague "schema" reference. RISK_REGISTER.md's R-55 already said "ADR-024 specifies the full token-category mapping ... in advance" without naming a location — this was not technically broken, but is now unambiguous, since ADR-024's content genuinely matches the claim.

**Verification performed:** grepped the finished ADR-024 text for each of the eight required elements the user's brief named (token categories, Flutter mapping, naming convention, schema versioning, consumer compatibility rules, schema evolution, failure behavior, unsupported token categories, examples) — all nine (the brief lists eight plus "examples" as a ninth) are present as their own labeled subsection or table.
