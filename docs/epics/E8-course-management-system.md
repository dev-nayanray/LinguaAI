## 0. Why this document exists now, and what it is not

E7 (Personalized Learning Engine) is implementation-complete (T1–T5, 2026-08-08) — confirmed at T6's own would-be start that §9 defines no further task, by explicit user direction to move on. Per ROADMAP.md, E8 is the next epic whose dependency (E4 — Database Schema & Core Data Layer, `content.prisma`) is already satisfied. This is the **first, single-pass design** for the Course Management System (PRD.md module 5) — following the same process E4–E7 each went through (CLAUDE.md's own workflow rule: "Architecture and planning precede feature development... do not scaffold or implement application features until the corresponding module has an approved design"). This document does not write any application code; it designs the module, surfaces real gaps found while doing so (§3), and proposes the ADR implementation will need (§7). Once a direction accepts this document (explicitly, or by the same "proceed by direct instruction" pattern E4–E7's own status lines record), implementation follows IMPLEMENTATION_GUIDE.md's 20-phase lifecycle per task, exactly as E4–E7 did.

## 1. Epic Definition

`content.prisma`'s full `Language → Course → Level → Unit → Lesson → Activity → Exercise/Quiz` hierarchy plus `ContentVersion` has existed, fully designed, since E4 T2 — but has **zero application logic anywhere**, confirmed by direct inspection (no `apps/api` module queries any of these models; `packages/database/scripts/seed.ts`'s own `seedSampleCourse()` comment states plainly this seeds "a representative course chain proving the full content hierarchy seeds correctly — not a real content catalog (E8)"). This epic is what makes that schema real: an admin-facing authoring/publish API, a learner-facing catalog-read + exercise-attempt API, the platform's first real emission of two domain events `EVENT_ARCHITECTURE.md` already catalogs but has never had a producer for, and an AI-assisted first-draft content-generation capability (RISK_REGISTER R-03's own named mitigation).

**In scope:**

- Admin-facing CRUD + publish/versioning workflow for the full content hierarchy, `ADMIN`-role-gated (§6.1).
- Learner-facing read API (published course catalog, a lesson's servable content) and exercise-attempt submission with real, deterministic scoring for the hierarchy's objective `ExerciseType`s (§6.2).
- First real emission of `learning.lesson.completed` / `learning.exercise.answered` — both already named in `EVENT_ARCHITECTURE.md`'s catalog (Producer: "`apps/api` (Course module)"), neither ever produced by any real code (§3.2, §6.3).
- AI-assisted content drafting — a new, narrow `services/ai-engine` capability that proposes a first-draft `Lesson`/`Activity`/`Exercise` for admin review, never auto-published (§6.4, RISK_REGISTER R-03's own stated mitigation: "AI-assisted content authoring, Epic E8").
- `apps/api`'s first real Prisma access against `content.prisma`'s models.

**Explicitly out of scope** (cited against ROADMAP.md/PRD.md's own classification, not silently absorbed):

- **The real admin authoring UI (`apps/admin` pixels)** — matching E4–E7's own precedent (backend/engine epics, not UI epics), this epic designs the data model operations and API contract a future UI consumes, not the actual screens. PRD.md module 5's "content authorable by non-engineers via admin" acceptance bar is only _fully_ met once that later, UI-focused epic ships (§3.6) — this epic is its necessary, load-bearing precondition, not the whole bar.
- **Authoring a real, launch-quality 10-language A1–B2 catalog** — RISK_REGISTER R-03 names this epic's own AI-assisted authoring tool as a mitigation for that risk, not a claim that this epic _produces_ the catalog. R-03 stays open after this epic ships (§3.7); a phased content-authoring effort using the tool this epic builds is separate, ongoing operational work.
- **`recommendation-engine`'s own consumption of `learning.lesson.completed`/`learning.exercise.answered`** — a real, found gap: E7's own design doc named these as in-scope events to consume, but only ever built consumption of `assessment.attempt.completed` (§3.3). This epic is the events' _producer_; fixing the still-missing _consumer_ side is `recommendation-engine`'s own domain, flagged here, not silently absorbed.
- **Gamification's own consumption of `learning.lesson.completed`/`learning.exercise.answered`** (XP awarding, streak updates) — Gamification Engine's own scope (module 15, E14 per ROADMAP.md), not yet built; this epic emits the event for real, E14 is who reacts to it.
- **`ExerciseType.SPEAKING_PROMPT` scoring** — needs real speech/AI scoring infrastructure (`services/speech-service`, not yet built until E10), the same class of boundary call E6 already made excluding `SPEAKING` from assessment scope entirely (§3.2 of that epic's own design doc). A `SPEAKING_PROMPT` `Exercise` can be authored and served by this epic; submitting an attempt against one is explicitly out of scope until E10 exists (§6.2).
- **Vocabulary/SRS extraction from lesson content** — Vocabulary Intelligence's own scope (module 6, E9 per ROADMAP.md, depends on E8 — a future epic building on top of this one, not reopened here).
- **`TEACHER` self-serve course authoring** — PRD.md §5.1 states plainly the `TEACHER` role has "no monetization or self-serve course publishing until Teacher Marketplace" (module 18, Growth phase). Every authoring/publish endpoint this epic builds is `ADMIN`-only (§3.5); not extended to `TEACHER` here.
- **Certificate issuance** — `Certificate` (module 21) already exists as schema (`exams.prisma`, E4-scoped) with real relations into `Course`/`Level`; issuing one is a separate, later epic's own scope, not reopened here.

**Depends on:** E4 (Database Schema & Core Data Layer — the full `content.prisma` hierarchy already exists, real schema, zero drift found during this document's own research).

## 2. Business Objective

PRD.md module 5's acceptance bar: _"Content authorable by non-engineers via admin."_ This epic makes that literally true at the API level for the first time — a future admin-UI epic supplies the "non-engineers" half (a real screen, not a Postman collection); this epic supplies the "authorable" half for real, including the AI-assisted first-draft capability RISK_REGISTER R-03 already names as this platform's own chosen strategy for producing 10-language A1–B2 content at viable cost. It is also the direct, load-bearing prerequisite for PRD.md's own Journey A step 4 ("Day 1 lesson plan already generated") and Journey B's "recommended activities" to ever mean anything beyond the one seeded Spanish chain — `recommendation-engine`'s entire E7 build (`LearningPlan`/`DailyGoal` generation, weakness-detection's `ActivityType → Skill` mapping) already assumes a real, growing content catalog exists to recommend from; today it has almost nothing to recommend.

**Success looks like:**

- An `ADMIN` can author a full `Course → Level → Unit → Lesson → Activity → Exercise` chain, publish it, and a learner can browse and complete it — end to end, against real Postgres, not a mocked substitute (§6.1, §6.2).
- Editing a _published_ `Lesson`/`Activity`/`Exercise`/`Quiz` never retroactively changes what an already-recorded `ExerciseAttempt` was scored against (`ContentVersion`'s own stated purpose, DATABASE.md §2.3) — verified by a real test proving a post-edit re-read of a historical attempt still reflects the version it was actually attempted against (§6.1).
- `learning.lesson.completed`/`learning.exercise.answered` are real, cataloged, and firing — closing `EVENT_ARCHITECTURE.md`'s own long-standing gap (§3.2) — even though no real consumer exists yet for either (the same "build it real, flag the not-yet-wired consumer" precedent E7 T2/T4 already established for `recommendation.daily_goal.ready`).
- AI-assisted drafting produces a real, schema-valid `Lesson`/`Activity`/`Exercise` draft an `ADMIN` can review and edit before it ever becomes visible to a learner — never auto-published, the same "never model-generated content feeding back... uncurated" discipline `AI_SYSTEM.md` §3 already states for the RAG knowledge base, applied here to authored curriculum instead (§6.4).

## 3. Scoping boundary and conflicts found

### 3.1 `content.prisma` is already fully designed (E4 T2) — zero schema drift found

The full hierarchy (`Language`, `Course`, `Level`, `Unit`, `Lesson`, `Activity`, `Quiz`, `Exercise`, `ExerciseAttempt`, `ContentVersion`) exists exactly as DATABASE.md §2.3 describes, confirmed by direct inspection of `packages/database/schema/content.prisma` during this document's own research — not assumed from the doc's own summary alone. No schema change is anticipated by this design; if implementation surfaces a real need for one, it goes through DATABASE_CHANGE_TEMPLATE.md the same as any other epic, not silently bundled in here.

### 3.2 Two already-cataloged events with no real producer yet — this epic is the first

`EVENT_ARCHITECTURE.md` §3 already lists `learning.lesson.completed` (Producer: `apps/api` (Course module); consumers: Gamification, `recommendation-engine`, `analytics-service`) and `learning.exercise.answered` (Producer: `apps/api`; consumers: `recommendation-engine`, `analytics-service`) — both real catalog rows with a real payload summary, neither ever actually published by any code in this repository, confirmed by a full-file search for both type strings outside the catalog itself. This epic is the "Course module" the catalog already names; §6.3 is the first real implementation of either.

### 3.3 A real, found cross-epic gap: E7 named itself a consumer of these same two events but never built it (new RISK_REGISTER R-92)

E7's own design doc (`docs/epics/E7-personalized-learning-engine.md`) §1 "In scope" states: _"Real consumption of three events that already name `recommendation-engine` as a consumer in `EVENT_ARCHITECTURE.md`'s catalog: `assessment.attempt.completed`, `learning.lesson.completed`, `learning.exercise.answered`."_ E7 T2 built real consumption of `assessment.attempt.completed` only — `DomainEventDispatcher.dispatch()` (`services/recommendation-engine/src/domain-events/`) early-returns as a no-op on every other event type today, confirmed by direct inspection of its own source and its own doc comment ("every event type this consumer doesn't yet care about... is a real no-op, not a missing case"). E7 is now marked implementation-complete (T1–T5) with no task having ever closed this. **Found and flagged here (RISK_REGISTER R-92), not silently fixed by this epic**: this epic is the two events' producer, not their consumer — building `recommendation-engine`'s own missing consumption logic is that service's own domain (E7's, or whichever future task next touches `DomainEventDispatcher`), out of E8's scope even though E8 is what finally makes the gap observable in production for the first time.

### 3.4 `AiRequestClass` has no slot for content generation

`services/ai-engine`'s own `RouterService.AiRequestClass` (`services/ai-engine/src/gateway/router.service.ts`) is a closed union today: `'teacher' | 'assessment'`, confirmed by direct inspection. AI-assisted content drafting (§6.4) is neither a conversational persona turn (`'teacher'`) nor an assessment-scoring call (`'assessment'`) — the same class of "doesn't fit a closed union built for something else" gap ADR-039 already found and solved when `AssessmentScoringService.scoreWritingResponse()` needed a slot `PromptManagerService`'s own `AgentPersona`-keyed template store had none for. Resolved here (§6.4, §7) the same way: a third request class is added, not forced into an ill-fitting existing one.

### 3.5 Authorization: `ADMIN`-only at MVP, not `TEACHER`

PRD.md §5.1 states plainly: the `TEACHER` role "exists at MVP with a scoped capability set... but no monetization or self-serve course publishing until Teacher Marketplace (module 18, Growth/Enterprise phase) ships with its content-governance workflow." Every authoring/publish endpoint this epic builds is therefore `@Roles('ADMIN')`-gated (`RolesGuard`, matching `AuditController`'s own established precedent for platform-wide `ADMIN`-only routes) — not extended to `TEACHER` here, a deliberate scope boundary, not an oversight.

### 3.6 This epic is backend/engine only, not the actual admin authoring UI

Matching E4–E7's own precedent (backend/engine epics, not UI epics — see each of those epics' own §3.6/§3 equivalent), this epic designs the data-model operations and API contract, not `apps/admin`'s real content-authoring screens (11 files today, a login/dashboard shell only, confirmed by direct inspection — no content-management UI of any kind exists). PRD.md's "authorable by non-engineers via admin" acceptance bar is only fully satisfied once that later, UI-focused epic ships; this epic is the necessary, load-bearing precondition for it, not a claim of having met it.

### 3.7 Real content authoring at scale remains RISK_REGISTER R-03's own tracked, separate risk

This epic builds the authoring tool, including AI-assisted drafting (§6.4) — it does not itself produce a complete 10-language A1–B2 catalog. R-03 ("Content pipeline can't produce 10-language A1–B2 content at launch quality/cost") stays **open** after this epic ships, flagged explicitly here rather than silently treated as "solved" by the tool's own existence — the same honesty class E6's own `AssessmentItem` seed content ("~1 item per skill per A1/B1/C1 band, 13 items total... real, tracked future content-authoring work") already modeled.

### 3.8 `ExerciseType` and `AssessmentItemType`/`Skill` are independently-defined, non-overlapping enums — a real scoring-logic boundary, not a reuse opportunity

`content.prisma`'s `ExerciseType` (`MULTIPLE_CHOICE`, `FILL_BLANK`, `MATCHING`, `TRANSLATION`, `LISTENING_COMPREHENSION`, `SPEAKING_PROMPT`) and `assessment.prisma`'s `AssessmentItemType` (`MULTIPLE_CHOICE`, `FILL_IN_BLANK`, `OPEN_RESPONSE`) are separately-defined enums with only a loose naming resemblance, not a real 1:1 correspondence — `MATCHING`/`TRANSLATION`/`LISTENING_COMPREHENSION`/`SPEAKING_PROMPT` have no assessment-module equivalent at all. The same "two independently-defined enums, don't force a shared mapping" discipline E7 T3's own `ActivityType → Skill` table already established applies here: `apps/api/src/modules/assessment/objective-scoring.util.ts` is **not** reused for `Exercise` scoring — a new, `Exercise`-shape-specific scorer is built fresh in this epic (§6.2), scoped to the objective types only (`SPEAKING_PROMPT` excluded per §1's own scoping call).

## 4. Bounded context & ownership

A new `apps/api/src/modules/course/` (`CourseModule`) — per **ADR-001** ("Core domain (identity, courses, progress, gamification, subscriptions) lives in one NestJS API; only `ai-engine`/`speech-service`/`recommendation-engine`/`notification-service`/`analytics-service` are separate, justified by independent scaling, runtime isolation, or blast-radius isolation"), content CRUD has none of those three properties, so it belongs in `apps/api`, not a new microservice — the same call `AssessmentModule`/`RecommendationsModule` already made for their own domains. AI-assisted drafting is a new, narrow `services/ai-engine` capability `CourseModule` calls over the existing internal HTTP contract (`AiEngineClientService`, matching `AssessmentService.scoreWritingItem()`'s own already-established precedent for calling into `ai-engine` from `apps/api`).

## 6. Cross-cutting mechanics

### 6.1 Admin CRUD + publish/versioning workflow

`ADMIN`-only routes (`RolesGuard`, matching `AuditController`'s own precedent) for creating/updating every node in the hierarchy. Two real, already-existing schema constraints this design works _with_, not against, confirmed by direct inspection of `content.prisma` rather than assumed:

- **Publish state is a `Course`-level toggle only** — `Level`/`Unit`/`Lesson`/`Activity`/`Quiz`/`Exercise` have no `publishedAt` of their own, only `deletedAt` (soft-delete). Once a `Course.publishedAt` is set, everything under it is live by construction; an `ADMIN` can still soft-delete an individual node (e.g. pull one `Lesson` from active use) without touching the whole course's own publish state.
- **`ContentVersion` is scoped to leaf entities only** — its `ContentEntityType` union is `LESSON | ACTIVITY | EXERCISE | QUIZ`, deliberately excluding `Course`/`Level`/`Unit`. This matches `ExerciseAttempt.contentVersionId`'s own stated purpose (pinning what a learner's attempt was actually scored against) — a learner attempts an `Exercise`, never a `Course` or `Level` directly, so only the entities a learner can actually be scored against need a pinnable version history.

**Versioning trigger, a real design decision made here, not left silently ambiguous:** a new `ContentVersion` snapshot is created for a `Lesson`/`Activity`/`Exercise`/`Quiz` (a) the moment its owning `Course` is first published (version 1 for every leaf entity under it), and (b) on every subsequent edit to that entity while its course remains published. `ExerciseAttempt.contentVersionId` always records the highest `versionNumber` `ContentVersion` for that `Exercise` at attempt time (`null` only for the edge case of an attempt against an exercise whose course was never actually published through this mechanism — should not occur for any content this epic itself creates, since publish is what creates version 1). **Left as a genuinely provisional, implementation-time decision, flagged rather than silently invented:** exactly which field edits on a live entity are "content-affecting" enough to warrant a new version versus purely cosmetic/reordering changes that shouldn't churn version history — the same class of provisional-parameter honesty E6's CEFR-banding thresholds and E7's weakness-detection thresholds already carry.

### 6.2 Learner-facing read API + exercise-attempt submission

Published-only reads: an offset-paginated course catalog listing (`API_GUIDELINES.md` §4's own named example — "bounded, rarely-changing admin list, e.g. the `Language` catalog" — applies equally to a `Course` listing), and per-lesson lazy-loaded content (a lesson's `Activity`/`Exercise` tree, fetched on entering that lesson, not eagerly nested into the course listing itself — avoiding an unbounded response size as real content volume grows, PERFORMANCE.md §3's Standard CRUD budget, p95 < 300ms). `POST .../exercises/:id/attempts` scores against `Exercise.correctAnswer` via a new, `Exercise`-shape-specific scorer (§3.8) for `MULTIPLE_CHOICE`/`FILL_BLANK`/`MATCHING`/`TRANSLATION`/`LISTENING_COMPREHENSION` — deterministic, structured-answer matching, the same "never trust a client-supplied correctness claim" scoring-integrity discipline `AssessmentService`'s own objective scorer already established. `SPEAKING_PROMPT` attempts are rejected (422) at this epic's own scope boundary (§1) — a real, named future dependency on `services/speech-service` (E10), not silently accepted and left unscored.

### 6.3 Domain events: `learning.lesson.completed` / `learning.exercise.answered`

`learning.exercise.answered` publishes on every scored `ExerciseAttempt` (payload: `userId`, `exerciseId`, `correct` — matching the catalog's own already-stated summary). `learning.lesson.completed` publishes when every `Exercise` in a `Lesson`'s own `Activity`/`Quiz` set has at least one attempt on record for that user (payload: `userId`, `lessonId`, `score` — an aggregate across the lesson's own attempts, this task's own concrete formula to define at implementation time, the same "provisional, not silently invented" honesty as §6.1's versioning-trigger decision). Both use the existing `DomainEventPublisher`/`createDomainEventsQueue` (`packages/events`) `apps/api`'s own `EventsModule` already wires up — no new transport, matching every other `apps/api`-origin event's own precedent. Neither event has a real, wired-up consumer as of this epic (§3.3) — built real and cataloged-correct regardless, the same "build it real, flag the not-yet-wired consumer" precedent E7 T2/T4 already established for `assessment.attempt.completed`'s own second consumer and `recommendation.daily_goal.ready`.

### 6.4 AI-assisted content drafting

A new, narrow `services/ai-engine/src/content-authoring/` capability (`ContentDraftingService.draftLesson()`), composing the same already-built E5 mechanisms `AssessmentScoringService` already established the pattern for: `RouterService.generate()` (§3.4's new `'content'` request class, not forced into `'teacher'`/`'assessment'`), `SafetyLayerService.sanitizeOutput()` on the returned draft (the same output-sanitization discipline every model-generated text this platform ever renders already carries, `AI_GOVERNANCE.md` §7), and a new, versioned prompt template (matching `AssessmentScoringService`'s own "standalone template, not forced into `PromptManagerService`'s persona-keyed store" precedent, ADR-039). The model's JSON response is validated against a new Zod schema (`@linguaai/validation`, this epic's own first real content in a `course`/`content-authoring` bounded context) before ever being returned — a malformed response is a thrown error, never a silently-accepted guess, matching every other AI-output-consuming service in this platform. **The draft is never auto-published**: `POST /v1/admin/courses/.../ai-draft` returns a proposed `Lesson`/`Activity`/`Exercise` shape an `ADMIN` must explicitly review, edit as needed, and submit through the same real create/update endpoints §6.1 already defines — no separate "AI-authored" bypass path exists. This directly extends `AI_SYSTEM.md` §3's own stated principle for the RAG knowledge base ("licensed/sourced content, never model-generated content feeding back into the knowledge base uncurated") to authored curriculum content, a genuinely new application of an already-established governance principle, not a new one invented for this epic alone.

## 8. Alternatives considered

- **A separate `content-service` microservice** — rejected per ADR-001's own already-settled reasoning: content CRUD needs no independent scaling, no runtime isolation, no blast-radius isolation from the rest of `apps/api`'s core domain; a new service here would be unwarranted infrastructure, not a justified boundary.
- **Reusing `AssessmentModule`'s objective-scoring util for `Exercise` attempts** — rejected (§3.8): `ExerciseType` and `AssessmentItemType` are independently-defined enums with only superficial naming overlap; forcing a shared scorer would either silently drop `MATCHING`/`TRANSLATION`/`LISTENING_COMPREHENSION` support or corrupt `AssessmentModule`'s own type with cases that don't belong to it.
- **Forcing AI-assisted drafting into the existing `'assessment'` `AiRequestClass`** — rejected (§3.4): a content-drafting call has a materially different cost/latency/safety profile than an assessment-scoring call (drafting a full lesson is not a bounded, single-essay critique), and conflating the two would make per-request-class cost monitoring (ADR-012's own circuit breaker) misleading.
- **Auto-publishing AI-generated drafts directly** — rejected (§6.4): directly contradicts `AI_SYSTEM.md` §3's own already-stated "never model-generated content feeding back... uncurated" principle; a launch-quality curriculum claim requires a human editorial gate, the same reasoning RISK_REGISTER R-03 itself already implies by naming this a "content pipeline" quality risk, not just a volume one.
