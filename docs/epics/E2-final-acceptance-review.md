## 2. Identity security

**Verified sound.** Argon2id via `@node-rs/argon2` with a `verifyPassword` that is never bypassed; `passwordHash` never returned by `toPublicUser` and never logged (there is an explicit e2e test scanning captured log output). Login is enumeration-resistant (`validateCredentials` returns `null` identically for no-such-account and wrong-password). Refresh rotation is a genuine atomic conditional claim (`updateMany({ where: { revokedAt: null } })`), with reuse → full-session revocation, proven by a real concurrent race test. `tokensValidAfter` staleness is checked on **every** authenticated request in `JwtStrategy.validate()` before any claim is trusted. The `jti` denylist is real, wired, and its e2e test re-uses the revoked token. MFA is TOTP with an encrypted-at-rest secret (`encryptField`, verified by a test that decrypts a genuinely stored value), a working 5-in-10-minutes lockout, and a real login step-up path (`MFA_REQUIRED` → `MfaChallengeToken` → session). OAuth matches **only** on `(provider, providerAccountId)` and refuses email-based auto-linking with a distinct `link_required` outcome. Bootstrap/emergency recovery is gated by an infra-tier secret compared with `timingSafeEqual`, connects as `app_service_role`, creates `mfaEnrolled: false`, and correctly distinguishes recovery from first bootstrap by live admin count, emitting a distinct max-severity event.

### F1 — HIGH: org-member removal does not invalidate the removed member's live access token

`OrganizationsService.removeMember` (`apps/api/src/modules/organizations/organizations.service.ts:220–277`) deletes the `OrganizationMembership` row and sets `User.organizationId = null`, but **never bumps `User.tokensValidAfter` and never revokes the target's sessions.**

I confirmed by exhaustive grep that `tokensValidAfter` is written in exactly three places in the whole codebase: `auth.service.ts:522` (password reset), `users.service.ts:175` (GDPR erasure), and inside the `SECURITY DEFINER` functions. Membership _removal_ is not one of them.

This contradicts the approved design directly. Part 5: "`tokensValidAfter` … **Bumped on every role/org-membership change**." Part 9A: "On any successful role/org-role change, the target's `User.tokensValidAfter` is bumped … the change takes effect on the target's very next request."

**Consequence, traced through the actual code.** The access token's `organizationId`/`orgRole` claims are minted at issue time (`signAccessToken`). `TenantContextInterceptor` (`database/tenant-context.interceptor.ts:56–61`) derives the RLS session context — including `app.current_org_id` and `app.caller_org_role` — from those claims. With `tokensValidAfter` unchanged, `isTokenStale` returns `false`, so for up to the full 15-minute access-token lifetime after removal:

- RLS still admits the removed user to the org (`org_read`, `membership_read`, and `user_read`'s `"organizationId" = current_org_id` branch).
- `assertCallerManagesOrg` — which reads `caller.organizationId`/`caller.orgRole` from the claim, by design (`organizations.service.ts:287–293`, `audit.service.ts`, `role-lifecycle.service.ts:183–189`) — still returns true for a removed `ENTERPRISE_ADMIN`.
- A removed `ENTERPRISE_ADMIN` can therefore still call `GET /v1/organizations/:id`, `POST /v1/organizations/:id/members`, `DELETE /v1/organizations/:id/members/:userId`, and `GET /v1/organizations/:id/audit-log`.

**The inconsistency is the proof this is an oversight, not a decision.** The _demotion_ path (`set_org_role()`) does bump `tokensValidAfter` for the target, and `PATCH .../members/:userId/role` is additionally protected because the function re-derives actor authorization inside the database — precisely the remediation-pass-#4 hardening. The _removal_ path received neither treatment. GDPR erasure, which also ends membership, does bump it. Member removal is the single path that does not.

No test covers it: `organizations.e2e-spec.ts:325` ("removes a non-last member, clearing their `User.organizationId`") asserts the membership and column, never the token.

**Not a Critical** because the window is bounded at 15 minutes, requires the removed user to already hold a live token, and the highest-consequence operation (`orgRole` change) is independently blocked in-database. **High** because it is a live authorization bypass against an explicit, written design guarantee, in the epic whose entire purpose is that guarantee.

### F2 — see §8. The suite that would catch a regression here does not run in CI.

### Lower-severity identity observations

- **No progressive backoff.** SECURITY.md §2 requires "rate limiting **+ progressive backoff** on auth endpoints." `RateLimiter` is a fixed-window `INCR`/`PEXPIRE` counter; nothing escalates. Reasonable for MVP, but it is a written requirement with no implementation and no tracked deferral.
- **Registration → `ACTIVE`.** `PENDING_VERIFICATION` is unreachable; no email-verification flow exists. Honestly flagged in code, untracked in docs.
- **`logout` is cookie-only.** Correctly and prominently flagged in-code as a known gap for the future Flutter client (E21). Acceptable; should be a tracked risk before E21 starts.

## 3. Multi-tenancy

**Independently verified.** `pg_class` confirms `User`, `Organization`, `OrganizationMembership` all have `relrowsecurity = t` **and** `relforcerowsecurity = t`; `AuditLog` has `relrowsecurity = t`. The runtime application connects as `app_role` (`createAppPrismaClient`, driven by `APP_DATABASE_URL`), **not** the migration superuser — the follow-up the T4 migration comment flagged as unresolved is genuinely closed, and `pg_roles` confirms `app_role` is `NOSUPERUSER NOBYPASSRLS`.

**Negative-test evidence is real, not policy-existence theatre.** `apps/api/test/tenant-rls.e2e-spec.ts` mounts a throwaway `test-only/rls-probe` controller (in `apps/api/test/`, **not** in `src/` — I checked; no test-only route ships in the application) that issues raw `appPrisma` calls with the application-layer filter absent _by construction_, then asserts RLS alone denies. It covers all three tables across **all four** policy directions (read/insert/update/delete) — 26 tests, materially broader than the read-only negative examples the design's prose spelled out. `user_insert`/`user_delete` `WITH CHECK (false)` are proven to hold even for a platform admin.

**Tenant context establishment.** `tenant.middleware.ts` does not exist; the mechanism is `TenantContextInterceptor` (AsyncLocalStorage bridge, runs after guards) + `tenantRlsExtension` (Prisma client extension batching `set_config` with each operation in one transaction). This is a _better_ implementation than the design named — it correctly solves the pooled-connection problem that a per-request `SET LOCAL` cannot — and the reasoning is documented in-code at length. All four session variables are set on every call, always explicitly, with non-matchable sentinels for nulls rather than relying on cross-request reversion. `isPlatformAdmin` is derived from the verified JWT `role`, never client-supplied.

**`app_service_role` (BYPASSRLS).** `pg_roles` confirms it is the only non-superuser role with `rolbypassrls`. **However, its scope has grown well beyond ADR-022's own enumeration** — see §11, R-36.

**Background jobs.** GDPR erasure (`UsersService.requestDeletion`) runs through `app_service_role` inside one transaction and is _self_-scoped (`where: { id: userId }` throughout) — it cannot wander across tenants. It is currently synchronous, not a BullMQ job; honestly flagged in-code. No BullMQ consumer exists anywhere yet, so there is no background job that could accidentally bypass isolation. Correct today; the "each such job implements and tests its own scoping" discipline (Part 9) has no enforcement mechanism for when one is added.

**One residual, and it is real** — see §11, R-45: I demonstrated that `app_role` can set `app.is_platform_admin` itself and read all 115 `User` rows. RLS defends against a _missing application filter_ (its stated primary purpose in MULTITENANCY.md §2, which it genuinely does) but not against raw SQL execution as `app_role`.

## 4. Privileged operations — the database _is_ the final boundary

**I verified this myself rather than trusting the test suite.** Connecting directly as `app_role` (password from the T4 migration) and issuing raw SQL:

| Attempted statement (as `app_role`)                                    | Postgres response                                           |
| ---------------------------------------------------------------------- | ----------------------------------------------------------- |
| `UPDATE "User" SET role='ADMIN';`                                      | `ERROR: permission denied for table User`                   |
| `UPDATE "User" SET "organizationId"=NULL;`                             | `ERROR: permission denied for table User`                   |
| `UPDATE "User" SET "passwordHash"='x';`                                | `ERROR: permission denied for table User`                   |
| `UPDATE "User" SET "tokensValidAfter"='2000-01-01';`                   | `ERROR: permission denied for table User`                   |
| `UPDATE "User" SET "mfaEnrolled"=true;`                                | `ERROR: permission denied for table User`                   |
| `UPDATE "User" SET status='ACTIVE';`                                   | `ERROR: permission denied for table User`                   |
| `UPDATE "OrganizationMembership" SET "orgRole"='ENTERPRISE_ADMIN';`    | `ERROR: permission denied for table OrganizationMembership` |
| `UPDATE "AuditLog" SET action='tampered';` / `DELETE FROM "AuditLog";` | `ERROR: permission denied for table AuditLog` (both)        |

`information_schema.column_privileges` confirms `app_role`'s `UPDATE` on `User` is exactly `{displayName, avatarUrl, locale, timezone, updatedAt}` — the four Part 9C columns plus the `updatedAt` bookkeeping column Prisma's `@updatedAt` forces into every generated `UPDATE` (a legitimate implementation fix, not a widening of the privileged set). **These are privilege-level rejections, not application-level ones.** ADR-023's central claim holds.

**Function ownership and authorization.** `pg_proc` × `pg_roles` confirms `approve_role_change`, `set_org_role`, `complete_mfa_enrollment`, and `enforce_last_enterprise_admin` are all owned by `governance_role`. `governance_role` holds only `SELECT` on three tables, column-scoped `UPDATE` on exactly the governed columns, and `INSERT` on `AuditLog` — narrower than a superuser, and deliberately `NOBYPASSRLS` so the functions' own internal reads remain RLS-scoped.

**Caller identity, ADMIN authorization, last-admin protection, concurrency.** All present in the deployed function bodies (`20260730115047` is the live version) exactly as the fourth targeted review approved: `current_setting('app.current_user_id')` cross-check → `caller_identity_mismatch`; fresh in-function approver lookup for existence/`ACTIVE`/`ADMIN` → `approver_not_authorized`; atomic `WHERE status='PENDING' AND requestedBy <> approver` claim; `pg_advisory_xact_lock(43,0)` for the platform-admin floor and `pg_advisory_xact_lock(44, hashtext(org))` for the per-org floor, both acquired _before_ the reads their decisions depend on. `role-lifecycle.e2e-spec.ts` proves each of these under genuine concurrency, plus the different-orgs control case.

**Audit logging is atomic with the state change** — the `AuditLog` INSERT is inside the same function body/transaction. **Token invalidation is inside the functions too** — both `approve_role_change` and `set_org_role` bump `tokensValidAfter`. (The gap is only on the _removal_ path, which is not a function — F1.)

**Two low-severity asymmetries in the lockdown:**

- `app_role` retains table-level `DELETE` on `"User"` (neutralized only by `user_delete USING (false)` — i.e. by RLS, not by privilege) and on `"RoleChangeRequest"` (not neutralized by anything: `RoleChangeRequest` has no RLS at all). A pending two-person approval request can therefore be _deleted_ by `app_role` even though it cannot be _updated_. No endpoint does this and it destroys rather than escalates, but it is an inconsistency with Part 9C's stated model that resolution fields "are the approval gate."
- `AuditLog` has `ENABLE` but not `FORCE ROW LEVEL SECURITY`, unlike the other three RLS tables. No practical consequence (neither `app_role` nor `governance_role` owns it), but the inconsistency is undocumented.

- **Schema ↔ migration consistency:** verified. `pnpm typecheck` passes against a generated client; the live database matches (the e2e suite runs against it). All UUID columns are `@db.Uuid`, which the RLS `::uuid` casts require.

## 6. API

Every endpoint in Part 6's table is implemented and reachable. Error contracts conform to API_GUIDELINES.md §3: `VALIDATION_ERROR` 400 via `ZodValidationPipe`, `AUTH_REQUIRED` 401, `FORBIDDEN` 403 from `RolesGuard`/`MfaGuard`, `CONFLICT` 409 on duplicate email and on governance conflicts, and — importantly — **tenant-scoped 404 rather than 403** applied consistently in `OrganizationsService`, `AuditService`, `RoleLifecycleService`, and `UsersService.revokeSession` (including for a malformed UUID, so a parse error can't leak a different shape). **API_GUIDELINES.md §12 is new, and I verified every claim in it against the code — all five bullets are accurate**, including the deliberate fail-open behaviour of the `jti` denylist and its stated contrast with §7's fail-closed limiter.

**Findings:**

- **F4 — MEDIUM: `Idempotency-Key` on `POST /v1/auth/register` was never implemented.** Part 6 makes this an explicit, reasoned extension of §6 ("registration wasn't named in API_GUIDELINES.md's own examples … so this design explicitly extends that list rather than leaving registration idempotency undefined"). There is no `Idempotency-Key` handling anywhere in `apps/api`, no key store, no replay path. It is not mentioned in §12, not deferred in the epic docs, and not in RISK_REGISTER.md. A duplicate retry on a flaky connection returns a spurious `CONFLICT` — the precise outcome the design says this exists to prevent.
- **F12 — LOW: three undocumented route-shape deviations.** `POST /v1/users/me/oauth-accounts` → `GET /v1/users/me/oauth-accounts/link/{google,apple}`; `GET /v1/auth/oauth/:provider(/callback)` → static per-provider routes, with Apple's callback correctly a `POST` (Apple uses `form_post`); "Also accepts CSV bulk import" → JSON array only. Every one of these is a _defensible_ engineering call and each is explained in a code comment — but Part 6's table is the API spec, and no doc records that the shipped surface differs from it.
- **F10 — LOW: `MFA_CHALLENGE_RATE_LIMIT`'s by-identifier rule is dead configuration.** It keys on the raw `challengeToken` with `max: 10`, but a challenge token is single-use and is _consumed before_ the TOTP code is checked (`auth.service.ts:340–351`), so the counter can never legitimately reach 2 for a given key. The real defense is the `userId`-keyed DB lockout in `MfaService`, which is correctly shared with `/mfa/verify`. Harmless, but it reads as protection that isn't doing anything.

## 9. Performance

I read `docs/epics/E2-T27-performance-report.md` and diffed it against the raw artifact `tests/load/results/2026-07-31T18-41-26-541Z.json`. **Every figure matches exactly** (register p50 156.69/p95 383.07/p99 388.77; login p50 172.88/p95 221.54/p99 277.09; orgDetailRead p95 2.37ms; membershipListRead p95 2.44ms; verdicts FAIL/FAIL/PASS/PASS). The report does not round in its own favour and does not hide the FAILs.

**Does the documented exception hold up, and does it compromise security?** I checked rather than accepting it.

- **The reasoning is sound, and the report deserves credit for not stopping where it could have.** It would have been easy to write "Argon2id is slow by design, exception granted." Instead it traced the cost to source (`packages/utils/src/password/hash-password.ts` passes only `{ algorithm: 2 }`, so `@node-rs/argon2`'s defaults apply: `memoryCost=4096`, `timeCost=3`, `parallelism=1`) and then said the genuinely uncomfortable thing: **the parameters were never chosen by anyone**, and 4 MiB is _below_ OWASP's current 19 MiB minimum. That is the opposite of a rationalization — it is an admission that the latency being excused is not even buying full memory-hardness.
- **The exception does not compromise security.** It relaxes a _latency budget_, not a hash parameter. The report explicitly refuses to weaken the hash, and explicitly declines to _strengthen_ it unilaterally on the grounds that it is a security-architecture decision needing its own ADR. Both halves of that are correct discipline.
- **But the open item is load-bearing and must not drift.** R-42 leaves the platform running below OWASP's memory-cost minimum indefinitely. That is a real (if modest) security posture gap, not merely a performance footnote — and raising `memoryCost` to 19456 will _change_ the measured latencies, which means the just-granted PERFORMANCE.md §3 exception is provisional on a decision nobody has made. **REQUIRES ACTION.**
- **RLS overhead is genuinely measured, not assumed** — 1,000 users across 50 orgs, p95 2.4ms against a 50ms budget (~20× margin). This properly discharges implementation-plan §15's second requirement.
- **Honest limitations, correctly stated:** dev-mode server on a shared machine, concurrency 20 as an admittedly synthetic figure, and no basis yet for §6's "3× observed peak" target. A staging re-run before launch is correctly named as still required.

**Not measured anywhere** (no budget was defined for them, so this is an observation, not a failure): MFA verification, OAuth callback round-trip, token refresh, and the `SECURITY DEFINER` governance-function calls under advisory-lock contention — the last being the one path with a known, accepted global serialization point (R-41).

### Decision

## CONDITIONAL ACCEPTANCE

**Reasoning.** This is strong work and I want to be precise about why it is not a clean acceptance, because the instinct to round it up would be understandable. The things that are hardest to get right here _are_ right: I connected to Postgres as `app_role` and could not write a single privileged column; function ownership is a narrowly-scoped `governance_role`, closing an item that had been carried, unresolved, since the third targeted review; audit immutability holds against `app_service_role` as well as `app_role`; the concurrency proofs are real concurrency against real Postgres, including a control case for the _absence_ of over-serialization; and the revocation test re-uses the actual revoked token rather than smiling at a 204. The T27 performance report and the T28 security review are both models of engineering honesty — each went looking for the uncomfortable answer and reported it, and T28's self-found P1 was genuinely closed with a genuinely adversarial test. Every remediation migration explains a real bug found empirically. That is not a codebase that was talked into looking finished.

But three things block a clean ACCEPT.

First, **F1 is a live authorization gap, not a theoretical one.** Removing a member from an organization does not invalidate their existing token's org claims, so a removed `ENTERPRISE_ADMIN` retains org read access _and_ member-management authority for up to fifteen minutes. The design says `tokensValidAfter` is bumped on "every role/org-membership change"; the demotion path does it, GDPR erasure does it, removal does not. That the adjacent paths get it right is what makes this an oversight rather than a trade-off — and no test covers it.

Second, **F2 means E2's security guarantees are unprotected against regression.** Every mandatory security test class this epic built — the cross-tenant RLS negatives that are the sole evidence for closing R-06, the governance concurrency and authorization proofs, audit immutability, the privileged-column privilege checks — runs only when a human types the command. The approved implementation plan said in terms that CI would be "the actual proof, not a manual check." It is currently a manual check, on a repository whose `ci.yml` has no database service at all. A suite this good deserves to be load-bearing, and right now it isn't.

Third, **no gate for E2 has been signed by anyone.** The epic document still declares itself in design phase; its gate log is eleven unstarted rows; the Architecture Gate checklist says "reviewed by someone other than the author — not yet done"; and E2-security-review.md declines to self-certify, correctly. ROADMAP.md and CHANGELOG.md meanwhile declare the epic complete. This review is one independent input, not a substitute for those sign-offs — and an epic whose entire process discipline has been _no self-certification, four times over_ cannot close on an unsigned log.

None of this is REJECTION territory. There is no unmitigated Critical, no broken tenant boundary, no fabricated verification — and notably, I could not find a single instance of a prior document claiming something was closed that turned out not to be. Where prior reviews said an item was open, it was genuinely open; where they said closed, I verified closed. That consistency is worth as much as any individual control.
