## 5. What T26 actually found (new this session)

T26's own acceptance criterion — "a request to `apps/api`'s `/health` produces a structured log line and a visible trace in local Jaeger" — was failing. Two real, previously-undiscovered bugs were found and fixed while trying to verify it:

1. **`turbo.json` had no `concurrency` setting.** With 14 persistent (`dev`-mode) tasks across the workspace and Turborepo's default concurrency of 10, `pnpm dev` refused to start at all (`Invalid task configuration`). Fixed by adding `"concurrency": "20"`.
2. **No `.env` loading mechanism existed anywhere in the monorepo.** `dotenv` was not installed; every app/service's `dev` script (`nest start --watch` ×6, `next dev` ×2) ran with zero mechanism to load the root `.env` file into `process.env`. `OTEL_EXPORTER_OTLP_ENDPOINT` (and every other `.env`-defined variable) was always `undefined` at runtime for locally-run processes, so `initObservability`'s own documented graceful-fallback correctly produced zero span processors — spans were created and immediately discarded. This is why `/health` worked, structured logs worked, but nothing ever reached Jaeger. **Fixed** by adding `dotenv-cli` and changing the root `dev` script to `dotenv -e .env -- turbo run dev`, covering all 8 apps/services in one change.

An earlier hypothesis from before this session's context reset — that `packages/observability/src/init.ts` misused the OpenTelemetry SDK's `NodeTracerProvider` constructor (passing an allegedly-invalid `spanProcessors` option) — was **re-checked and found incorrect**: `spanProcessors` is confirmed a real, valid `TracerConfig` property (`@opentelemetry/sdk-trace-base@1.30.1`'s own `types.d.ts`). No code in `init.ts` needed to change; the bug was entirely in env-loading, one layer up.

After both fixes: `apps/api` boots, `/health` returns 200, and `"api"` appears as a real service in Jaeger with a real span (confirmed via direct query against `http://localhost:16686/api/services` and `/api/traces?service=api`). `packages/observability`'s own test suite (31 tests) still passes at 100% coverage, confirming the package's code itself was never the problem.

**Files changed this session:** `turbo.json` (concurrency), `package.json` root (`dotenv-cli` dependency + `dev` script), `README.md` (corrected setup guide — status line, full service/port list, dotenv/port-conflict/Docker-Desktop-timing notes).
