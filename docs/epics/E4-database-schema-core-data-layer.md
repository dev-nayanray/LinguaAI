## 1. Epic Definition

**What this Epic is:** the Prisma schema, migrations, Row-Level Security policies, indexing, partitioning, and vector-search setup for every core data-layer domain the platform's feature epics (E5–E9, E14–E19) will build application logic against, that is not already built. It delivers `packages/database`'s schema for the Learning, AI Coaching, Commerce, and Community bounded contexts (ARCHITECTURE.md §2.1) — the tables themselves, not the services/endpoints that read and write them.

**In scope** (DATABASE.md §2.2–§2.10, net of what's already built — see §3.1):

- Assessment & learning plan (§2.2): `AssessmentAttempt`, `AssessmentResponse`, `ProficiencyLevel`, `ProficiencyLevelHistory`, `LearningPlan`, `DailyGoal`.
- Content & curriculum (§2.3): `Language`, `Course`, `Level`, `Unit`, `Lesson`, `Activity`, `Exercise`, `Quiz`, `ExerciseAttempt`, `ContentVersion`.
- Vocabulary intelligence (§2.4): `VocabularyItem`, `UserVocabulary`, `PersonalDictionary`.
- AI teacher & conversation (§2.5): `AIAgentSession`, `AIMessage`, `AIMemoryEntry`, `KnowledgeBaseEntry`, `PronunciationScore`, `FluencyScore`.
- Gamification (§2.6): `UserXP`, `Streak`, `Badge`, `UserBadge`, `Mission`, `UserMission`, `League`/`Cohort`, `LeaderboardEntry`.
- Community (§2.7): `Friendship`, `Group`, `GroupMembership`, `Challenge`, `Discussion`, `Post`, `Comment`, `ContentReport`, `ModerationAction`.
- Exams & certification (§2.8): `ExamProgram`, `MockTestAttempt`, `Certificate`.
- Subscriptions & billing (§2.9, net of `EntitlementChangeLog` — see §3.1): `Plan`, `Subscription`, `Invoice`, `Entitlement`. `Coupon`/`Discount` deliberately excluded — see §10, resolved item 3.
- Analytics & platform (§2.10, net of `AuditLog` — see §3.1): `LearningEvent`, `AIUsageLog`, `NotificationLog`, `NotificationPreference`.
- The cross-cutting mechanics every domain above needs: Prisma schema-composition strategy, RLS-migration pattern reuse, pgvector field/index mechanics, time-based partition automation, field-level encryption for `AIMessage.content`, seed-data strategy, and CI wiring for schema/migration validation.

**Explicitly out of scope:**

- Identity & access (DATABASE.md §2.1) — **already implemented by E2** (docs/epics/E2-identity-access-platform.md, ADR-018–023). Confirmed against the live schema (`packages/database/schema.prisma`): `User`, `OAuthAccount`, `UserProfile`, `Organization`, `OrganizationMembership`, `Session`, `RefreshToken`, `ConsentRecord`, `DeviceToken`, `PasswordResetToken`, `OAuthState`, `MfaVerificationAttempt`, `MfaChallengeToken`, `RoleChangeRequest`, `AuditLog`, `EntitlementChangeLog` all exist today. This epic does not redo that work — see §3.1.
- `TeacherProfile`, `TeacherPayout`, `ApiKey` (DATABASE.md §2.11) — explicitly reserved for Growth/Enterprise/Future phase epics per ROADMAP.md's own classification (module 18, module 27); adding them now would be scope creep this document's own instructions forbid.
- Any application-layer service, controller, or business logic that reads/writes these tables — that is each consuming feature epic's own scope (E5–E9, E14–E19), built after this epic's schema exists.
- Sharding, read-replica routing, enforced data residency — explicitly deferred in DATABASE.md §11, unchanged here.

**Depends on:** E1 (per ROADMAP.md). E2 is not a formal ROADMAP.md dependency of E4, but is a _load-bearing precedent_ this design reuses directly (§3.1, §6.2) — flagged here since ROADMAP.md's dependency column doesn't capture it.

## 2. Business Objective

**Which PRD.md goal does this serve?** Every MVP persona journey PRD.md §4 describes — assessment-driven placement, AI tutoring, structured curriculum progress, gamified motivation, vocabulary retention (SRS), and subscription monetization — requires a durable data model before any of it can be built. This epic has no user-facing feature of its own; its business objective is entirely enabling: it is the hard dependency named by 11 of the remaining 19 unbuilt MVP epics (ROADMAP.md's dependency column: E5, E6, E7, E8, E9, E14, E15, E16, E17, E18, E22).

**Success looks like:**

- Every table DATABASE.md §2.2–§2.10 names (net of §3.1's already-built set) exists in `packages/database/schema.prisma` with a corresponding migration.
- Every tenant-scoped table (per §3.3's resolved list) ships its RLS policy in the same migration, reusing E2's `app_role`/`app_service_role` pattern — no new table is added without this, per MULTITENANCY.md §6 and DATABASE_CHANGE_TEMPLATE.md §3.
- `AIMessage`, `LearningEvent`, and `AIUsageLog` are range-partitioned by month from their first migration, not retrofitted later.
- `AIMessage.content` is field-level encrypted from its first migration, not added as a follow-up hardening pass.
- Every feature epic that depends on E4 (E5–E9, E14–E19) can begin its own Technical Design phase (IMPLEMENTATION_GUIDE.md phase 6) against a real, migrated schema instead of a paper one.

## 3. Scoping boundary and conflicts found

Per this task's own instruction: conflicts are documented here, not silently resolved.

### 3.1 Overlap between DATABASE.md's domain sections and E2's already-built schema

DATABASE.md lists `AuditLog` in both §2.1 (Identity & access) and §2.10 (Analytics & platform), and `EntitlementChangeLog` in both §2.1 and §2.9 (Subscriptions & billing) — in each case with near-identical descriptions. Read against the live schema, both tables already exist, built by E2. This is not a documentation error to correct silently: DATABASE.md's structure suggests these two tables are intentionally _cross-referenced_ from the domain sections that consume them, not duplicated new work — but DATABASE.md's own text does not say so explicitly, and a reader who only opens §2.9/§2.10 (as this epic's own scope definition initially did, until checked against the live schema) would plan to rebuild both. **Resolved (§10, item 5):** DATABASE.md's §2.9/§2.10 rows for these two tables are edited, in the same PR as this document, to say "see §2.1, already implemented" rather than repeating the description.

### 3.2 `verify-boundary-lint`-equivalent RLS lint script ownership is ambiguous

MULTITENANCY.md §6 states the CI check rejecting a tenant-scoped table with no RLS policy is "enforced via a schema-lint script introduced in Epic E1/E22." Checked against the repo: no such script exists (`scripts/` contains no schema/RLS lint; `packages/database` has no lint step beyond generic `eslint`). E1 is marked implementation-complete (ROADMAP.md) and evidently did not build it; E22 (Security Hardening & Compliance Gate) has not started. **This is a real gap, not a naming ambiguity**: this epic is about to add roughly 54 new tables with no mechanical CI enforcement of the "RLS policy ships in the same migration" rule MULTITENANCY.md §6 requires — only code-review discipline. **Resolved (§10, item 1):** E4 builds the script itself, in T11 (§9), rather than waiting for E22.

### 3.3 Which of E4's new tables are actually tenant-scoped?

MULTITENANCY.md §1 defines tenant-scoped data as "org-owned data — members, assignments, reports, seats." Read literally against DATABASE.md §2.2–§2.10's entity list, **none of the ~54 tables this epic adds are organization-owned** in that sense — they are all user-owned (a `Course` enrollment, an `AssessmentAttempt`, a `Subscription`) or globally shared reference data (`Language`, `Course` content itself, `VocabularyItem`, `ExamProgram`, `Badge`/`Mission` catalogs). An `ENTERPRISE_ADMIN`'s need to see aggregate reports across their org's members (MULTITENANCY.md §1's "reports") is a **query pattern** — `SELECT ... FROM AssessmentAttempt JOIN User ON ... WHERE User.organizationId = X` — not evidence that `AssessmentAttempt` itself needs an `organizationId` column and its own RLS policy. Giving every user-owned table its own redundant `organizationId` column purely so it can carry an RLS policy would duplicate `User.organizationId`, create a drift surface (a user's org membership changing without a matching update cascading to every historical row), and contradicts DATABASE.md §6's own soft-delete/retention table, which already treats `LearningEvent`-class rows as identity-independent, anonymizable-in-place records rather than tenant-owned ones.

**Conclusion this document adopts, stated explicitly rather than left implicit:** none of E4's new tables get their own `organizationId` column or RLS policy. Tenant isolation for this epic's data is achieved by mediation through `User`/`OrganizationMembership` (already RLS-protected by E2) in any org-scoped reporting query a later epic (most likely E18 Admin Platform) builds — that later epic's own Database Gate is where an org-scoped _read path_ (a reporting view or query, not a new column) gets designed and reviewed. This conclusion satisfies DATABASE_CHANGE_TEMPLATE.md §3's "is this table tenant-scoped?" question with a documented "No" for every table in §5 below, rather than leaving it unanswered per table. **Confirmed (§10, item 4)** — this document's own judgment call, put to and confirmed by direct decision rather than left as a standing assumption.

## 4. Bounded context & ownership

Per TECHNICAL_DESIGN_TEMPLATE.md §2: this epic's _deliverable_ (schema + migrations in `packages/database`) is a single shared package, per ARCHITECTURE.md §5's own description of `packages/database` as "single source of schema truth." But the _domains_ it schemas for span four of ARCHITECTURE.md §2.1's six bounded contexts — Learning (assessment, curriculum, vocabulary, gamification), AI Coaching (AI teacher/conversation), Commerce (subscriptions/billing), and Community. This is not a boundary violation: ARCHITECTURE.md §2.1's bounded-context rule ("a NestJS module inside `apps/api` may only depend on another module through its exported service") governs _application-code_ ownership, not schema authorship — Prisma's single generated client is explicitly shared infrastructure (ARCHITECTURE.md §5), and no bounded context "owns" `packages/database` any more than one owns TypeScript itself. Each consuming feature epic (E5–E9, E14–E19) still owns its own bounded context's _application logic_ against these tables; this epic only owns getting the tables into existence, correctly, once.

## 6. Cross-cutting mechanics

### 6.1 Soft-delete / retention classification mechanism

No new mechanism — DATABASE.md §6/§7 already specifies the three-category model (soft delete / hard-delete-anonymize / append-only-anonymized-in-place) and the retention matrix. §5 above classifies every domain against it; no domain in this epic's scope needs a fourth category.

### 6.2 RLS-in-Prisma-migrations — reused, not re-decided

E2 already established and shipped a working pattern (`packages/database/migrations/20260730111235_add_identity_rls_policies/migration.sql` and siblings): a raw-SQL migration authored alongside the Prisma-generated one, a non-superuser `app_role` (`NOSUPERUSER NOBYPASSRLS`) as the real per-request runtime role with session GUCs (`app.current_org_id`, `app.current_user_id`, `app.caller_org_role`, `app.is_platform_admin`) set by Prisma middleware, `ENABLE ROW LEVEL SECURITY` + `FORCE ROW LEVEL SECURITY`, and per-operation (`FOR INSERT`/`UPDATE`/`DELETE`) policies, plus a separate `app_service_role` (`BYPASSRLS`) for the narrow set of legitimately cross-tenant operations (ADR-022). Per §3.3's conclusion, **no table in this epic's scope needs its own RLS policy** — this section is included to state explicitly that the pattern exists, is proven, and would be reused unchanged if the Architecture Gate reviewer overturns §3.3 for any specific table, rather than requiring this document (or a future one) to re-derive it.

### 6.3 pgvector fields and HNSW indexing — new mechanics, existing extension

The `vector` extension is already installed (`packages/database/migrations/20260730105822_record_vector_extension`, via docker-compose's Postgres init script, predating any Prisma migration) — reused unchanged. What's genuinely new for this epic: `AIMemoryEntry.embedding` and `KnowledgeBaseEntry.embedding` are the **first actual vector-typed columns**. Prisma's schema language has no native vector type; the established pattern (documented in Prisma's own docs, not invented here) is `Unsupported("vector(N)")` in `schema.prisma` plus a raw-SQL migration statement for the column and its HNSW index (`CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)`), mirroring the same "Prisma schema + companion raw-SQL migration" shape §6.2's RLS policies already use — not a new authoring pattern, an application of the existing one to a new statement type. Embedding dimensionality (`N`) is fixed per DATABASE.md §4's own `embeddingModelVersion`-pinning rule; this document does not choose a specific embedding model or dimension — that is AI_SYSTEM.md/AI_GOVERNANCE.md's decision, consumed here as a parameter, not decided here.

### 6.4 Field-level encryption for `AIMessage.content` — new decision, ADR-029 proposed

DATABASE.md §5/§8 requires field-level encryption on `AIMessage.content`, keyed via KMS envelope encryption, but does not specify the mechanism — Prisma has no native field-encryption feature. §7 below proposes ADR-029: encrypt/decrypt in an explicit Prisma Client Extension in `packages/database`'s own generated-client wrapper (not scattered per-call-site in `ai-engine`), so every consumer gets transparent encryption without each having to remember to call it. See ADR-029 for the full alternatives analysis.

### 6.5 Time-based partition automation — new decision, ADR-028 proposed

DATABASE.md §5/§9 specifies `AIMessage`, `LearningEvent`, and `AIUsageLog` are "range-partitioned by month from the start," but not how new monthly partitions get created before the current one fills, or by what mechanism. §7 below proposes ADR-028. Decided once, applied to all three tables — the second and third are reuses of the first table's mechanism, not independent decisions.

### 6.6 Prisma schema file composition — new decision, ADR-027 proposed

`schema.prisma` is currently one file (~470 lines, ~26 models, all from E2). This epic adds roughly 55 more models across 9 domains. DATABASE.md §2's own header ("Each maps to one or more Prisma schema files composed into the shared `packages/database` schema") already signals multi-file intent, but the current repo state is single-file, and no decision has been made about _how_ multi-file composition would actually work with this repo's Prisma version. §7 proposes ADR-027.

## 8. Alternatives considered

Summarized here; full analysis lives in each ADR (§7/DECISIONS.md) per TECHNICAL_DESIGN_TEMPLATE.md §7's requirement.

| Decision | Alternative                                                                                                                              | Why rejected                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ADR-027  | Continue single `schema.prisma`                                                                                                          | Would reach an estimated 3,000+ line single file across ~80 models total; no functional blocker, but a real, avoidable code-review/navigation cost this epic is the last natural point to avoid paying                                                                                                                                                                                                                                                                                                                                         |
| ADR-027  | Split into multiple independent Prisma _projects_ (separate clients per domain)                                                          | Rejected outright — contradicts ARCHITECTURE.md §5's "one schema, one migration history, one generated client" and would reintroduce cross-service schema drift risk ADR-005/MULTITENANCY.md exists to prevent                                                                                                                                                                                                                                                                                                                                 |
| ADR-028  | Hand-rolled BullMQ job creating next month's partition on a cron schedule                                                                | Rejected as the primary mechanism — a missed/failed job run silently drops writes for the next month with no natural detection point until they fail; `pg_partman`'s own maintenance function is a purpose-built, widely-used solution to exactly this problem, still triggered by BullMQ (scheduled `pg_partman.run_maintenance()` call) rather than removing scheduling entirely                                                                                                                                                             |
| ADR-028  | Native Postgres declarative partitioning with manually pre-created partitions covering the next 24 months upfront                        | Rejected — defers the problem rather than solving it (partitions still run out eventually) and pre-creates 24 empty partitions per table for no benefit over automated creation                                                                                                                                                                                                                                                                                                                                                                |
| ADR-029  | Encrypt at the `ai-engine` application-service layer (explicit encrypt-before-write/decrypt-after-read calls, no Prisma-level mechanism) | Rejected as the sole mechanism — correct once, but every future consumer (a support tool, an admin export, a future analytics job) must remember to call it too; a Prisma Client Extension makes the encryption structural to the table's access path, not a discipline every caller must re-derive                                                                                                                                                                                                                                            |
| ADR-029  | Postgres `pgcrypto` column-level encryption (`pgp_sym_encrypt`/`pgp_sym_decrypt` in SQL)                                                 | Rejected — ties the encryption key to a value the database itself must have to query, undermining KMS envelope encryption's actual security property (the database should not be able to decrypt its own encrypted columns without an external KMS call); also makes `content` unreadable to any raw-SQL admin tooling without replicating the app's decrypt call, which DATABASE.md §5's own "admin/support tooling accesses a redacted view by default" requirement already assumes happens at the application layer, not the database layer |

## 10. Open questions — resolved

These five were genuinely unresolved when this document was first drafted. Each is now resolved **by direct product/engineering-lead decision (2026-08-07)** — a real decision, recorded honestly as exactly that, not as an independent Architecture Gate review's sign-off. This is the same distinction ADR-025 already draws in this repo (T4's icon-library choice: "Accepted — by explicit user direction... not... an Architecture Gate sign-off"). The Architecture/Security/Database Gates in §12 remain unchecked; resolving an open question is not the same as passing a gate, and this document does not conflate the two.

1. **RLS-lint script ownership (§3.2) — resolved: E4 builds it.** T11 (§9) now includes the interim RLS-policy-lint script as a firm deliverable of this epic, not a proposal contingent on E22's timeline. It closes the enforcement gap before any of this epic's ~54 new tables merge, rather than leaving them under code-review-only enforcement.
2. **`Certificate` verification token generation scheme (§5) — resolved: random opaque token, database lookup.** Not a signed JWT. Chosen specifically for trivial revocation (delete/rotate the row, no denylist infrastructure needed) over the JWT alternative's stateless-verification benefit, since a certificate-verification endpoint's query volume does not need to avoid a database round-trip the way a high-QPS auth check does. Token entropy, rate-limiting the verification endpoint against enumeration, and the exact lookup-table shape remain real Security Gate work at T8's implementation time — this resolves the _scheme_, not the full security design.
3. **`Coupon`/`Discount` schema-reservation scope (§1, §5, §9 T9) — resolved: wait for a real feature spec.** E4 does **not** reserve `Coupon`/`Discount` placeholder tables. Removed from T9's scope and from §1's in-scope list — a genuinely unshaped reservation was judged more likely to lock in a wrong shape than to save a later migration. DATABASE.md §2.9's own reservation intent stands (a future promotions epic still revisits it when a real feature spec exists) — that document's entry for it is updated with a one-line "not built by E4" status note, in the same PR, so a reader isn't left assuming this epic already reserved it.
4. **§3.3's "no table is tenant-scoped" conclusion — confirmed.** Every table in §5 keeps its "No" tenant-scoped classification. §6.2's RLS-pattern-reuse section stands as written (documenting the pattern exists and would be reused if a future table needs it, without any table in _this_ epic's scope actually needing it).
5. **DATABASE.md §2.9/§2.10's duplicate `AuditLog`/`EntitlementChangeLog` listings (§3.1) — resolved: fixed.** DATABASE.md itself is corrected in the same PR as this document's update (see that document's own §2.9/§2.10) — no longer restated as a "recommendation for the Architecture Gate reviewer," since it has already been applied.
