## Executive Summary

The sixth review found the design document "materially stronger than a five-NO-GO history suggests," independently re-executing and confirming both of its hardest technical claims (the boundary-lint diagnosis and the entire WCAG contrast grid) without a single discrepancy, and confirmed all ten of the fifth review's findings genuinely closed. It nonetheless found one new High finding and several smaller ones the first five reviews never examined — not recurrences of prior defects, but a fresh layer of scrutiny finding what the earlier five passes' own attention was elsewhere for.

**The High finding, P6-1, is a genuine architecture gap, not a documentation-completeness gap like the last three reviews' High findings.** The Tier-2 typography token layer (`--type-*`) had a name and a mapping table but no CSS form that could actually exist: Tailwind v4 has no theme namespace that lets one custom property carry a font size, a line height, a weight, and a family together, and ADR-024's Flutter generator required exactly those four values from a source that provided none of them. This pass fixes it by applying the identical, already-proven mechanism this document uses for motion (`@utility` blocks composing several declarations under one class name) to typography — a design choice that required no new architectural pattern, only the consistent application of one already in the document.

The three Medium findings and six Low findings are addressed individually below. Two of them (M-1, M-2) add real component-level content (a full AI-component contract and four composite-widget accessibility contracts) rather than correcting existing text — the design document continues to grow in genuine substance with each pass, not merely have its own claims walked back.

## Root Cause Analysis

P6-1's root cause is different in kind from the completeness-reconciliation failures of passes #4 and #5: this was not a missing row in an otherwise-sound mechanism, it was a mechanism that never existed for one of the four token categories BR-4 names. The document had already solved the identical problem once, for motion — Tailwind v4 lacking a `--duration-*` theme namespace, solved by `@utility duration-*` blocks — and simply never applied that same reasoning one section later to typography, where the identical namespace gap exists (`--type-*`/`--font-size-*` is equally absent from Tailwind v4's theme namespace). The fix is not a new pattern; it is the existing pattern, applied where it was always needed. This pass's specific check going forward: whenever this document declares a token "Tier 2, mapped onto Tier 1," verify a real CSS construct exists that can hold the mapping, not only a table describing an intended one.

M-1 and M-2's root cause is the same completeness gap the fourth, fifth, and now sixth reviews have each found in a different layer: a component or a primitive can be _named_ in an early section (§6c, §12.2) without a later section (§12.4) ever being checked against that naming. This pass does not introduce a new procedure to prevent this the way pass #5 did for tokens (a test assertion) — a "does every named primitive have a §12.4 contract" check is not something a Vitest test can enforce the way a token-completeness check can, since primitives are prose, not parseable CSS — but it does close every specific instance the sixth review found, and names the same class of gap explicitly enough (in M-1's and M-2's own resolution text below) that a future reviewer auditing this same axis knows exactly what to check.

## Finding-by-Finding Resolution

### P6-1 (HIGH) — Typography token layer had no implementable representation

**Resolution.** §12.1a is rewritten. Tier 1 gains explicit line-height primitives (`--text-<size>-leading`, parallel to the existing size primitives) rather than leaving line-height as a value that exists only inside a markdown table cell. Tier 2 becomes a set of `@utility type-<name>` blocks — the exact multi-declaration Tailwind v4 construct already proven and shipped for `--duration-*` — each composing four real Tier-1/primitive custom properties (`font-size`, `line-height`, `font-weight`, `font-family`) under one applied class name. Letter-spacing is addressed explicitly (omitted from every current block, stated as a deliberate choice with a stated extension point, not silently absent). The `display-lg`/`display-xl` tokens are corrected to reference `--font-display` (they previously, silently, would have inherited `--font-sans` by omission — a defect this rewrite closes as a side effect of giving them a real declaration to specify).

`DECISIONS.md`'s ADR-024 gains: a corrected typography mapping-table row describing the `@utility` source construct instead of an unimplementable single-property one; an explicit typography schema-validation rule (all four sub-fields required, generator names the specific token and specific missing field on failure); and the Failure-behavior paragraph extended to reference it. §17's Token-palette regression row gains a typography-completeness assertion (parses every `@utility type-<name>` block, fails if any of the four declarations is missing or its `var()` reference unresolvable) — mirroring ADR-024's own rule so the gap is caught at T1 time, not only T18's.

**A second, related honesty correction made in the same edit:** the sixth review separately observed (non-blocking, but directly adjacent to this section) that §17's existing color-token completeness assertion overclaimed being "achievable by construction" — it cannot mechanically read §12.1's markdown tables, only a test-internal fixture array. The row is corrected to state exactly what the assertion can and cannot do (`tokens.css` ⊆ test-fixture, with the fixture's sync-with-§12.1 responsibility stated as a maintained-by-hand requirement, not a mechanically-guaranteed one), and the previously-unstated interaction with the disabled-token exemption is now an explicit exclusion list rather than a contradiction between two document sections.

T1's deliverable list is corrected to name the full `@utility type-*` block set as its literal typography deliverable, not a summary of intent.

**Status: Closed**, pending the seventh review's own independent verification (in particular, re-executing the claim that `@utility` blocks with multiple declarations are valid, parseable Tailwind v4 CSS — this pass reasoned through Tailwind v4's documented `@utility` capability and the document's own pre-existing, unchallenged `--duration-*` precedent, but did not independently re-verify the CSS parses against the installed Tailwind version, since doing so would require running a build, out of this pass's documentation-only scope).

### M-1 (MEDIUM) — Missing "thinking" vs "typing" AI component contract

**Resolution.** A full §12.4 contract added: purpose (distinguishing "reasoning before any output" from "actively streaming," a distinction the streaming-renderer contract alone does not cover), visual difference (a non-spinner pulse/shimmer, deliberately not implying determinate progress), a `phase` prop, `aria-live="polite"` behavior with a single one-time announcement (not per-pulse, to avoid screen-reader spam), reduced-motion handling (matching §12.1's stated degrade-to-static principle), loading-state behavior (the `thinking` phase is itself the loading state, CLS-dimensioned per §15), testing requirements (unit + interaction), and an explicit ADR-006/§13 presentational-only compliance statement (no network access, no inference about _why_ the AI is thinking, consistent with every other component in the category).

**Status: Closed.**

### M-2 (MEDIUM) — Composite Radix widget accessibility gaps

**Resolution.** Full accessibility contracts added for DropdownMenu, Popover, Tabs, and Tooltip — keyboard interaction, focus management, ARIA pattern, screen-reader expectations, and testing approach for each. Tabs, per the brief's own instruction, receives the most detail: the roving-tabindex mechanism §12.5 already names as a blind spot is specified explicitly (which tab is in the natural Tab order, arrow-key vs. Tab-key semantics, "manual activation" chosen over "automatic activation" and the reason given), and Tabs is added to the mandatory manual-screen-reader-verification list — the list's own stated inclusion criterion ("the highest-risk combination of custom ARIA, live-region timing, or focus management") applies to it, and the review named this gap directly. The list grows from seven to eight; every prose reference to the count (§5, §6c, §12.4, §12.5, §17, §21) and RISK_REGISTER.md's R-54 are updated to match, continuing the same reconciliation discipline pass #5 established for the six→seven correction.

**Status: Closed.**

### M-3 (MEDIUM) — Secondary token collision with AI-purple

**Resolution.** `--color-secondary-text`/`--color-secondary-solid` are renamed to `--color-ai-text`/`--color-ai-solid`, matching the canonical `--color-ai` anchor name and removing the collision with the shipped `secondary` Button variant. A new "Brand tokens vs. Action tokens" explanatory section separates two categories this document previously conflated: brand tokens (meaning-bearing, usable only for what they signal — AI-purple, danger, warning, success, info, accent) versus action tokens (a button's emphasis role — primary, secondary, ghost, destructive — independent of any specific brand color, since DESIGN_SYSTEM.md never assigns a brand color to "secondary" or "ghost" as a concept). Button's `secondary` and `ghost` variants are defined using tokens that already exist and are already validated in this grid (`--color-surface-muted`/`--color-border`/`--color-text`) — no new hex value was invented; the fix was recognizing these variants never needed a new color, only to stop being pointed, by name collision, at an unrelated brand color. `destructive` is confirmed to already correctly use `--color-danger-solid`.

**Status: Closed.**

### M-4 (MEDIUM) — Palette lint gate/control scope mismatch

**Resolution.** §14's palette-restriction control row and §21's Frontend quality-gate row both now explicitly separate CURRENT STATE (no `packages/ui`-scoped rule exists in `eslint.config.js` today; `packages/ui/src/components/button.tsx` ships today with several raw-palette violations, named specifically) from POST-IMPLEMENTATION STATE (T2's corrected deliverable: the rule extended to cover `packages/ui` alongside `apps/web`/`apps/admin`, running as part of `pnpm lint`, failing the build on a match outside the documented escape hatch) — with T1 named as the task that actually removes `button.tsx`'s current violations (via the Brand-vs-Action re-theme from M-3), since the lint rule alone only prevents regression, it does not retroactively fix an existing file.

**Status: Closed.**
