## 1. Epic Definition

`vocabulary.prisma`'s `VocabularyItem` / `UserVocabulary` / `PersonalDictionary` models have existed, fully designed, since E4 T4 — but have **zero application logic anywhere**, confirmed by direct inspection (no `apps/api` module, controller, or service references any of the three; no `vocabulary` subpath exists yet in `packages/types`/`packages/validation`). This epic is what makes that schema real: a curated vocabulary catalog with `ADMIN`-authoring, a per-user personal dictionary that ingests saved terms from any source, and a real SM-2-derivative spaced-repetition scheduler that is the epic's own named PRD acceptance bar.

**In scope:**

- Curated `VocabularyItem` catalog: `ADMIN`-only authoring (create/update/soft-delete) plus an authenticated, published-catalog-style read API (§6.1).
- Personal dictionary: save/list/remove a term from any `VocabularySource` (reading, camera translation, conversation, manual entry), independent of whether a matching catalog `VocabularyItem` exists (§6.2).
- SRS review engine: add a `VocabularyItem` to a learner's own spaced-repetition deck, a due-cards query, and a review-submission endpoint implementing a real, documented, testable SM-2-derivative scheduling algorithm — the PRD's own literal acceptance criterion for this module (§6.3, ADR-042).
- AI-assisted vocabulary-item drafting (translations + example sentences) — a narrow extension of E8 T4's own `ContentDraftingService`/`'content'` `AiRequestClass`, admin-review-gated, never auto-published, continuing RISK_REGISTER R-03's own named content-authoring-at-scale mitigation strategy from lesson content to vocabulary content (§6.4).
- `apps/api`'s first real Prisma access against `vocabulary.prisma`'s models.

**Explicitly out of scope** (cited against ROADMAP.md/PRD.md/ARCHITECTURE_REVIEW.md's own classification, not silently absorbed):

- **The real flashcard/dictionary UI (`apps/web`/`apps/mobile` pixels)** — matching E4–E8's own precedent (backend/engine epics, not UI epics), this epic designs the data-model operations and API contract a future UI consumes, not the actual screens (§3.5).
- **Lesson-content vocabulary extraction** — E8's own design doc (§1, "Explicitly out of scope") already named this as this epic's future scope; found here to still have no real design of its own. `content.prisma`'s `Activity.content` (a `VOCABULARY_DRILL`-typed activity) carries no FK to `VocabularyItem` at the schema level (confirmed by direct inspection, §3.2) — automatically surfacing a lesson's own vocabulary into a learner's SRS deck is a real, separately-scoped future capability, not built here.
- **Camera-translation / conversation-transcript ingestion pipelines themselves** — `VocabularySource.CAMERA_TRANSLATION`/`CONVERSATION` are enum values `PersonalDictionary.source` already supports (E4 T4), but the actual camera-translation capability (module 13, Growth-phase per ROADMAP.md) and the Orchestrator's own extraction-into-`PersonalDictionary` wiring (module 4/`ai-engine`) do not exist yet and are not built here. This epic builds the save/list/remove API any such producer would call; it does not build the producers themselves (§3.3).
- **Gamification's own reaction to a completed review** (XP awarding, streak credit) — Gamification Engine's own scope (module 15, E14 per ROADMAP.md, not yet built); no event is invented here for a consumer that doesn't exist and that no document names (§3.4).
- **`recommendation-engine`'s own consumption of SRS state** for weakness-detection or `DailyGoal` generation — a real, named architectural tension this document resolves for the synchronous review-submission path (§3.1, ADR-042) but does not extend into a new cross-service read; flagged as a real, concrete future opportunity, not built here.
- **`TEACHER` self-serve vocabulary-catalog authoring** — mirrors E8's own `ADMIN`-only precedent (§3.5 of that epic's design doc, sourced from PRD.md §5.1's "no self-serve publishing until Teacher Marketplace" rule); every catalog-authoring endpoint this epic builds is `ADMIN`-only (§3.5).

**Depends on:** E4 (Database Schema & Core Data Layer — `vocabulary.prisma`'s full model set already exists, real schema, zero drift found during this document's own research); E8 (Course Management System — establishes the `'content'` `AiRequestClass`/`ContentDraftingService` pattern §6.4 extends, and is ROADMAP.md's own stated dependency, though no direct schema coupling was found — see §3.2).

## 2. Business Objective

PRD.md module 6's acceptance bar: _"SRS scheduling follows a documented algorithm (SM-2 derivative)."_ This epic makes that literally true for the first time — `UserVocabulary`'s own schema fields (`easeFactor` defaulting to 2.5, `intervalDays`, `repetitions`, `nextReviewAt`) have sat unused since E4 T4, already shaped for exactly the classic SM-2 algorithm this epic now implements for real (§6.3). It also completes PRD.md's own Journey narrative: vocabulary "extracted for spaced repetition" is named explicitly in PRD.md's own AI-conversation journey (§4) as a session-end outcome — this epic is the load-bearing target that extraction eventually feeds, even though the extraction pipeline itself remains future scope (§1).

**Success looks like:**

- An `ADMIN` can author a `VocabularyItem` (term, translations, part of speech, example sentences) for a given language, and any authenticated learner can browse/search the published catalog for that language (§6.1).
- A learner can save a term to their personal dictionary from any named source, list their saved terms, and remove one — independent of whether a matching catalog entry exists (§6.2).
- A learner can add a catalog `VocabularyItem` to their own SRS deck, see which cards are due today, and submit a review — the resulting `easeFactor`/`intervalDays`/`repetitions`/`nextReviewAt` state transition is deterministic, documented, and directly testable against the published SM-2 algorithm, not an ad hoc approximation (§6.3, PRD's own literal bar).
- AI-assisted drafting produces a real, schema-valid `VocabularyItem` proposal (translations + example sentences) an `ADMIN` can review and edit before it is ever published to a learner — never auto-published, the same discipline E8 T4/ADR-041 already established for lesson content (§6.4).

## 3. Scoping boundary and conflicts found

### 3.1 `vocabulary.prisma` is already fully designed (E4 T4) — zero schema drift found, but a real architecture-boundary tension exists

`VocabularyItem`/`UserVocabulary`/`PersonalDictionary` exist exactly as DATABASE.md §2.4 describes, confirmed by direct inspection of `packages/database/schema/vocabulary.prisma` during this document's own research. No schema change is anticipated by this design. However, ARCHITECTURE.md §2.1's own service-boundary rule names "spaced-repetition scheduling" _by name_ as an example of what `recommendation-engine` owns ("deterministic/algorithmic decisions — SRS scheduling, next-best-activity ranking, weakness-detection scoring"). This document departs from that literal example for the synchronous review-submission path — resolved and justified in ADR-042 (§7), the same class of documented departure ADR-038 already made for the adaptive item-selection algorithm.

### 3.2 No real schema coupling to E8 was found, despite ROADMAP.md naming it a dependency

Direct inspection of `content.prisma`'s `Activity` model found no FK, join table, or JSON-shape convention linking a `VOCABULARY_DRILL`-typed `Activity` to any `VocabularyItem` row — `Activity.content` is untyped `Json`, validated only at the application layer per its own schema comment. ROADMAP.md's E9 dependency on E8 is therefore a **conceptual** one (a real content catalog and a real course-progression signal are both prerequisites for vocabulary intelligence to matter in practice, and E8 T4 supplies the AI-request-class pattern §6.4 extends), not a schema-level one. Found and flagged here rather than silently assumed deeper than it is.

### 3.3 `PersonalDictionary.vocabularyItemId` is nullable; `UserVocabulary.vocabularyItemId` is not — a real, load-bearing asymmetry

`PersonalDictionary` can record a term with no catalog match at all (camera translation or conversation can surface a term the curated catalog has never seen, per the schema's own header comment) — `term`/`translation` are always stored directly. `UserVocabulary`, by contrast, requires a real `vocabularyItemId` (`String @db.Uuid`, not nullable) — a learner **cannot** add an unmatched personal-dictionary term directly to spaced-repetition review; only a real, curated `VocabularyItem` can be SRS-tracked. This is a genuine, deliberate design decision this document makes concrete (§6.2/§6.3): no auto-creation of a `VocabularyItem` from an unmatched personal term is built here — doing so would let arbitrary user-submitted text silently populate a catalog the schema's own header comment calls "curated, shared... not per-user," the same data-quality/abuse-surface concern that already justifies `VocabularyItem`'s `ADMIN`-only authoring (§3.5). A learner whose saved term has no catalog match can keep it in their personal dictionary indefinitely but cannot review it on a schedule until a matching catalog entry appears — a real, named limitation (§10), not a silent gap.

### 3.4 No vocabulary-related domain event is pre-cataloged, and none is invented here

Unlike E8's own `learning.lesson.completed`/`learning.exercise.answered` (both pre-cataloged in `EVENT_ARCHITECTURE.md` with named future consumers before E8 ever built a producer), a full-text search of `EVENT_ARCHITECTURE.md` found **zero** vocabulary/SRS/flashcard-related catalog entries, and no epic's own design doc (including E7's, which named exactly three events it intended to consume) names a vocabulary-triggered event it expects to react to. Per this document's own discipline (matching CLAUDE.md's "don't design for hypothetical future requirements"), no new event is added — inventing one now would be speculative infrastructure with no real consumer, unlike E8's two events which had named ones. If Gamification (E14) or `recommendation-engine` later need a real-time vocabulary signal, that is their own epic's scope to name and catalog, not pre-built here.

### 3.5 This epic is backend/engine only, not the actual flashcard/dictionary UI

Matching E4–E8's own precedent (backend/engine epics, not UI epics), this epic designs the data-model operations and API contract, not `apps/web`/`apps/mobile`'s real flashcard-review or personal-dictionary screens (neither exists today, confirmed by direct inspection — `apps/web`/`apps/mobile` carry no vocabulary-related route or screen of any kind). ARCHITECTURE_REVIEW.md's own (archived, superseded) E9 deliverables list named "flashcard UI" as in-scope for "E9" generally — this document scopes that to a later, UI-focused epic instead, the same reclassification E4–E8 each already made for their own equivalent UI deliverable.

### 3.6 `TEACHER` gets no self-serve vocabulary-catalog authoring at MVP

PRD.md §5.1 states plainly the `TEACHER` role has "no monetization or self-serve course publishing until Teacher Marketplace." Every catalog-authoring endpoint this epic builds is therefore `@Roles('ADMIN')`-gated (`RolesGuard`, matching `AuditController`/`CourseModule`'s own established precedent) — not extended to `TEACHER` here.

### 3.7 `AiRequestClass` already has a fitting slot — no new class is added

`services/ai-engine`'s `RouterService.AiRequestClass` is `'teacher' | 'assessment' | 'content'` as of E8 T4 (ADR-041). Vocabulary-item drafting (§6.4) is structurally identical to lesson drafting in cost/latency/safety profile — both are `ADMIN`-only, non-conversational, structured content-authoring assistance, never auto-published — so it reuses the existing `'content'` class rather than fragmenting ADR-012's own per-class cost-circuit-breaker monitoring with a class distinguished only by content sub-type, not by a materially different call shape. Considered and rejected in §8.

## 4. Bounded context & ownership

A new `apps/api/src/modules/vocabulary/` (`VocabularyModule`) — per **ADR-001**, vocabulary catalog CRUD, personal-dictionary CRUD, and SRS review state have none of the three properties (independent scaling, runtime isolation, blast-radius isolation) that justify a separate `services/*` microservice, so they belong in `apps/api`, the same call `CourseModule`/`AssessmentModule` already made for their own domains — even though the SRS scheduling _algorithm_ itself sits at the literal boundary ARCHITECTURE.md §2.1 draws for `recommendation-engine` (§3.1, resolved by ADR-042). AI-assisted vocabulary drafting is a new method on the existing `services/ai-engine` `ContentDraftingService` (E8 T4), called from `VocabularyModule` via the existing `AiEngineClientService` — no new internal-HTTP contract, extending E8 T4's own already-established `apps/api` ↔ `ai-engine` call path.

## 6. Cross-cutting mechanics

### 6.1 Curated vocabulary catalog

`ADMIN`-only routes (`RolesGuard` + `MfaGuard`, matching `AuditController`/`CourseModule`'s own precedent) for `VocabularyItem` create/update/soft-delete. `translations` (`Json`, keyed by UI-language code) and `exampleSentences` (`Json?`, an array of `{sentence, translation?}` objects per the schema's own comment) are validated at the application layer via a new Zod schema, not the database — matching `content.prisma`'s own established `Json`-payload discipline (E8 §6.1's precedent for `Activity.content`). Read API: `GET /v1/vocabulary-items` (offset-paginated — API_GUIDELINES.md §4's own named "bounded, rarely-changing admin list" case, the same classification `Language`/`Course` catalogs already use), filterable by `languageId` and a `search` term (case-insensitive substring match on `term`); `GET /v1/vocabulary-items/:id`. Both reads are any-authenticated-user, not `ADMIN`-only (matching `CourseCatalogController`'s own published-content precedent) — soft-deleted items excluded, no draft/published distinction exists at the `VocabularyItem` level (unlike `Course`, there's no `publishedAt` field on this model; a created, non-deleted item is immediately catalog-visible, a real, deliberate simplicity call flagged in §10).

### 6.2 Personal dictionary

`POST /v1/vocabulary/personal-dictionary` (`languageId`, `term`, `translation?`, `source: VocabularySource`, `notes?`, `vocabularyItemId?` — when supplied, validated to reference a real, non-deleted `VocabularyItem`, never trusted unchecked). `GET /v1/vocabulary/personal-dictionary` (cursor-paginated per API_GUIDELINES.md §4 and the exact `{cursor, limit}` request / `{data, meta: {nextCursor}}` response shape `auditLogQuerySchema`/`auditLogListResponseSchema` already established, E2's own precedent reused rather than a new shape invented), filterable by `languageId`. `DELETE /v1/vocabulary/personal-dictionary/:id` — ownership-checked against `caller.userId`, 404 not 403 on mismatch (API_GUIDELINES.md §3's no-existence-leak rule, matching `AssessmentService.getOwnedAttempt`/`ExerciseAttemptsService`'s own established discipline). No SRS state is touched by this component at all — §3.3's own asymmetry means adding a dictionary entry to spaced-repetition review is a distinct action (§6.3), never implicit.

### 6.3 SRS review engine (ADR-042)

`POST /v1/vocabulary/deck` (body: `{vocabularyItemId}`) creates a `UserVocabulary` row at its schema defaults (`easeFactor: 2.5`, `intervalDays: 0`, `repetitions: 0`, `nextReviewAt: now()` — immediately due) or, on the `@@unique([userId, vocabularyItemId])` constraint already firing, returns the existing row unchanged rather than erroring — an idempotent "add to my deck" action safe to call twice. `GET /v1/vocabulary/deck/due` (cursor-paginated, `nextReviewAt <= now()`, ordered ascending) lists what's actually due; review is not restricted to only-due cards (a learner may review early/"cram" — a real, deliberate permissiveness call, not a gap). `POST /v1/vocabulary/deck/:id/reviews` (body: `{quality: number}`, `0`–`5`, the literal SM-2 input scale — a UI's own job to map a friendlier button set onto this range is explicitly out of this backend epic's scope, §3.5) — ownership-checked (404 not 403), applies the SM-2-derivative transition function (a new, pure, stateless `srs-scheduling.util.ts`, mirroring `AdaptiveItemSelectionService`/`exercise-scoring.util.ts`'s own "pure function, no I/O" precedent) documented in full in ADR-042, and persists the new `easeFactor`/`intervalDays`/`repetitions`/`nextReviewAt`/`lastReviewedAt`. No `Idempotency-Key` handling is added — this endpoint inherits the same pre-existing, platform-wide gap RISK_REGISTER R-85 already tracks (confirmed absent from every other retryable `POST` in this codebase, including E8 T2's own `ExerciseAttemptsController`), not a new omission specific to this epic.

**The SM-2-derivative algorithm itself, stated precisely (the PRD's own literal "documented" bar):**

Given current `(easeFactor, intervalDays, repetitions)` and a submitted `quality` (0–5):

1. New ease factor: `ef' = easeFactor + (0.1 - (5 - quality) * (0.08 + (5 - quality) * 0.02))`, floored at `1.3` (the standard SM-2 minimum — an ease factor below this makes review intervals collapse toward daily regardless of continued success, defeating the algorithm's own purpose).
2. If `quality < 3` (a failed recall): `repetitions' = 0`, `intervalDays' = 1` — the classic SM-2 "start over" branch.
3. Else (a successful recall): `repetitions' = repetitions + 1`, and `intervalDays'` is `1` if `repetitions' === 1`, `6` if `repetitions' === 2`, else `round(intervalDays * ef')` (using the _new_ ease factor, the standard SM-2 order of operations).
4. `nextReviewAt' = now() + intervalDays'` days; `lastReviewedAt' = now()`.

### 6.4 AI-assisted vocabulary-item drafting

A new `ContentDraftingService.draftVocabularyItem()` method (`services/ai-engine/src/content-authoring/`, extending E8 T4's existing module rather than a new one) composing the same already-built mechanisms that method's own sibling `draftLesson()` already established: `RouterService.generate('content', ...)` (§3.7 — the existing class, not a new one), `SafetyLayerService.sanitizeOutput()` on every returned free-text field (translations, example sentences), and a new, standalone, versioned prompt template (`vocabulary-drafting.prompt.ts`, matching `content-drafting.prompt.ts`'s own precedent). The model's JSON response is validated against a new `vocabularyItemDraftSchema` (`@linguaai/validation/vocabulary`) before ever being returned — a malformed response is a thrown error, never a silently-accepted guess, matching every other AI-output-consuming service on this platform. `apps/api`'s `AiEngineClientService` gains a `draftVocabularyItem()` method calling the new `POST /v1/content-authoring/draft-vocabulary-item` (ai-engine, no auth guard, ADR-033's internal-trust-boundary pattern); `VocabularyModule` exposes `POST /v1/admin/vocabulary-items/ai-draft` (`ADMIN`-only) returning the proposal unmodified and **persisting nothing** — the same "never auto-published, no bypass path" discipline E8 T4 established, verified the same way (a live e2e assertion of zero created rows).

## 8. Alternatives considered

- **Building the SRS scheduler inside `recommendation-engine`** (rejected, ADR-042 §7) — would require standing up that service's first-ever frontend-facing HTTP endpoint (a genuinely new architectural precedent, since its real code to date is 100% asynchronous), when `apps/api` already owns every other synchronous, per-request domain write in this platform and the algorithm itself is designed pure/relocatable regardless (the same "designed to be relocatable" precedent ADR-035/038/040 already used, so this is not a permanent foreclosure).
- **A new `'vocabulary'` `AiRequestClass`** (rejected, §3.7) — vocabulary-item drafting has no materially different cost/latency/safety profile from lesson drafting; both are `ADMIN`-only, non-conversational, structured content-authoring calls. A class per content sub-type would fragment ADR-012's own per-class cost monitoring without a real distinction to justify it.
- **Auto-creating a `VocabularyItem` from an unmatched `PersonalDictionary` entry so it becomes immediately SRS-trackable** (rejected, §3.3) — would let arbitrary user-submitted text silently populate a catalog the schema's own header comment calls "curated, shared," the same data-quality/abuse concern `VocabularyItem`'s `ADMIN`-only authoring already exists to prevent.
- **Inventing a `vocabulary.item.reviewed` domain event now, anticipating Gamification (E14)** (rejected, §3.4) — no document names a real consumer today; E8's own two events were pre-cataloged with named future consumers before their producer was ever built, a materially different situation from speculatively cataloging one here with none.
- **A `publishedAt`/draft state for `VocabularyItem`, mirroring `Course`** (rejected, §6.1) — `Course`'s own publish gate exists because a course is authored incrementally over a long-lived, multi-entity tree a learner must never see mid-edit; a single `VocabularyItem` is authored and saved atomically with no such intermediate-state risk. Added complexity with no real corresponding need — flagged in §10 as revisitable if real editorial workflow needs emerge.

## 10. Open questions

Genuinely unresolved as of this draft — not silently decided, and not yet put to the user for a resolution decision the way E4–E8's own §10 recorded theirs.

1. **Whether `VocabularyItem` eventually needs its own draft/publish gate** (§6.1, §8) — deliberately not built now (no corresponding need found), but flagged as revisitable once a real multi-step editorial review workflow for vocabulary content is named by a future epic.
2. **Whether an unmatched `PersonalDictionary` entry should ever be promotable into the curated catalog** (e.g., an `ADMIN` review queue for frequently-saved unmatched terms) — a real, plausible future feature with no current design or named requirement; left entirely undesigned rather than half-specified.
3. **Exact search/matching behavior for `GET /v1/vocabulary-items?search=`** (§6.1) — this document specifies "case-insensitive substring match on `term`" as the MVP behavior; whether that needs to extend to matching within `translations`' JSON values is left as an implementation-time call, the same class of provisional-parameter honesty E6's `CONFIDENCE_FLOOR`/E7's weakness thresholds already were.
