## 0. Why this document exists now, and what it is not

Epic E4 (Database Schema & Core Data Layer) is implementation-complete (T1–T12). Per ROADMAP.md, E5 (AI Gateway & Agent Orchestration Core) is the next epic whose dependencies (E1, E4) are both satisfied. E5 is the load-bearing epic for the platform's actual product differentiation — PRD.md's Journey B (daily loop) and Journey C (speaking practice) both route through it, and five further epics (E6, E10, E12, E13, E19) depend on it directly or transitively. This document is the **first, single-pass design** for `services/ai-engine`'s real implementation — currently a 3-file, ~40-line NestJS skeleton (§3.6) with zero AI code.

Following the same process CLAUDE.md's workflow rule and E4's own precedent establish: this is design-only unless and until the user explicitly directs otherwise. This document does **not**:

- Write any code in `services/ai-engine` or elsewhere. No provider SDK is installed, no controller exists beyond the E1 health-check skeleton.
- Modify `packages/database/schema/ai.prisma`'s already-shipped tables. Where a real schema gap is found (§3.5), it is named as a gap for a future task to close via a real migration, not silently patched here.
- Mark any gate, ADR, or the Epic itself as approved. Every checkbox in §12 is unchecked; every proposed ADR in §7 is status `Proposed`.
- Pin numeric cost-circuit-breaker thresholds. AI_GOVERNANCE.md §5 is explicit that these come from real staging/production traffic data, reviewed monthly — this document designs the _mechanism_ only (§6.4), consistent with how E4 treated `Certificate` token entropy as a real decision but left rate-limit request volumes as a smaller, later-tunable parameter.

## 1. Epic Definition

**What this Epic is:** the real implementation of `services/ai-engine` as the platform's AI gateway (ADR-006) — the eight subcomponents AI_SYSTEM.md §2 names (Router, Prompt Manager, Orchestrator, RAG Retrieval Layer, Memory Manager, Safety Layer, Cost Meter & Circuit Breaker, Provider Adapters) — plus closing the five real gaps AI_SYSTEM.md/AI_GOVERNANCE.md forward-reference but don't contain (§3.1–§3.4). It delivers the AI Coaching bounded context's core infrastructure (ARCHITECTURE.md §2.1), not any specific agent's full pedagogical behavior — a working Orchestrator + Conversation Partner + Personal Language Teacher persona pair is this epic's own proof of the mechanism; the remaining five personas' specific tool logic (Grammar/Pronunciation/Vocabulary/Writing/Exam Coach) are named in scope structurally (the tool-registry entry exists) but their real pedagogical logic is each consuming epic's own scope (E6/E9/E11/E13/E19), matching E4's own "tables into existence, correctly, once" framing applied to agent infrastructure instead of schema.

**In scope:**

- `ModelProvider` interface (`generate`/`stream`/`embed`) and real Anthropic + OpenAI adapters behind it (ADR-006).
- Router: provider/model selection per request class, tiering, and failover on provider error (ARCHITECTURE.md §7.1).
- Embedding model + dimensionality pinning — a real ADR closing E4 R-70, not a further deferral.
- Prompt Manager: versioned prompt templates, `promptVersion` tracked on every `AIMessage`/`AIUsageLog` write.
- Orchestrator: session lifecycle against `AIAgentSession`/`AIMessage`, rolling summarization for long sessions, the single-Orchestrator-owns-the-voice invariant (ADR-007).
- Specialist tool-calling mechanism: the trigger-condition catalog and tool-registry versioning scheme AI_SYSTEM.md §3 claims exists in AI_GOVERNANCE.md §2/§6 but doesn't (§3.1) — built here, with AI_GOVERNANCE.md updated to actually contain it.
- Memory Manager: `AIMemoryEntry` read/write, top-N + token-budget retrieval, confidence decay, and the versioned-supersession hygiene mechanism AI_SYSTEM.md §5 requires but has no schema support for yet (§3.5).
- RAG Retrieval Layer: `KnowledgeBaseEntry` similarity search (HNSW, cosine — already built, E4 T5) and grounding-context injection (ADR-008).
- Safety Layer: untrusted-input boundary delimiting, output sanitization, age-bracket content boundaries, human-in-the-loop sampling, bounded tool surface (AI_GOVERNANCE.md §6).
- Cost Meter & Circuit Breaker: `AIUsageLog` writes on every request, the platform-wide spend-rate-cap mechanism and 3-stage breach ladder (ADR-012) — mechanism only, not final numeric thresholds.
- The internal `apps/api` ↔ `ai-engine` request/response contract AI_SYSTEM.md §2 claims is documented but isn't (§3.2).
- `AIMessage`/`LearningEvent`/`AIUsageLog` partition-maintenance scheduling — closing E4 R-69's "not yet wired to any scheduler" gap.
- Real verification of the `AwsKmsDataKeyProvider` path (ADR-029) — closing E4 R-68's "only the local stub has ever run" gap, to whatever extent real AWS KMS access exists in this environment (flagged if it doesn't, matching T1/T5's own honest handling of the same constraint).
- CI wiring for the four AI_GOVERNANCE.md §3 evaluation suites (golden-set, factual-accuracy, red-team/safety, cost/latency regression) — at least an interim version, matching E4 T11's own "interim, not E22's final form" precedent.

**Explicitly out of scope:**

- `services/speech-service` (STT/TTS, Epic E10) and the full speaking-practice pipeline ARCHITECTURE.md §6 describes end-to-end — E5 delivers the `ai-engine` hop of that pipeline (step 3 of 5) only; E10 is what makes the other four steps real.
- Full pedagogical logic per specialist agent (grammar rule coverage, pronunciation phoneme scoring detail, exam rubric scoring precision) — each is its own consuming epic's scope (E6, E9, E11, E13, E19), per ARCHITECTURE.md §2.1's bounded-context ownership.
- `recommendation-engine`'s deterministic decision logic (SRS scheduling, next-best-activity ranking) — ARCHITECTURE.md §2.1's explicit, load-bearing boundary rule: `ai-engine` never duplicates a decision `recommendation-engine` owns.
- A `Pronunciation Lab attempt` entity — E4's own flagged gap (ai.prisma header comment), explicitly deferred to E11.
- Fine-tuning custom models — AI_SYSTEM.md §12, explicitly deferred pending evaluation data.
- AI Avatar Teacher, public AI/education API — both explicitly deferred (AI_SYSTEM.md §12, ROADMAP.md Future Research).
- Proactive coaching nudges, user-selectable teacher personality, automated re-assessment triggers — all explicitly Version 1.1 (ROADMAP.md's feature classification table).
- A managed vector DB migration (Pinecone/Weaviate) — pgvector stays canonical per ADR-004 until a defined scale trigger fires (ARCHITECTURE.md §9).

**Depends on:** E1 (per ROADMAP.md — `services/ai-engine`'s NestJS/Turborepo scaffolding, observability wiring). E4 (per ROADMAP.md — the full `ai.prisma`/`analytics.prisma` schema this epic writes to; E5 does not modify that schema except where §3.5 finds a genuine, narrow gap).

## 2. Business Objective

**Which PRD.md goal does this serve?** PRD.md §4's Journey B (daily loop, step 3: "User optionally starts a live conversation session with the AI Conversation Partner") and Journey C (speaking practice, the platform's named "signature differentiator" per ROADMAP.md's feature classification) both require a working AI gateway before either can exist as more than a mock. ROADMAP.md's own Phase-1 exit criteria name two AI-specific gates directly: "Voice conversation latency within budget" and "Positive or credibly-trending-positive unit economics (AI cost per active user vs. Premium conversion)" — both are this epic's own mechanisms (latency budget adherence via the Router/streaming design, unit economics via the Cost Meter).

**Success looks like:**

- `services/ai-engine` has a real `ModelProvider` interface with at least two working provider adapters (Anthropic, OpenAI), not a stub.
- An `AIAgentSession` can be created, exchange `AIMessage` turns with at least the Personal Language Teacher and Conversation Partner personas acting as Orchestrator, and end with a session summary — proving the Orchestrator mechanism end-to-end, not just its schema.
- At least one specialist tool call (Grammar Coach, the one AI_SYSTEM.md §3 uses as its own worked example) fires on a real trigger condition and returns a structured critique object the Orchestrator incorporates — proving ADR-007's tool-calling contract for real, not just documenting it.
- A RAG-grounded response cites `KnowledgeBaseEntry` content for at least one factual claim, proving ADR-008's "never left to the model's parametric knowledge alone" principle operates in practice.
- Every AI request writes a real `AIUsageLog` row with actual token/cost/latency figures, and the cost circuit breaker's 3-stage ladder is exercised (at minimum, in a test harness) — not merely designed.
- The five real documentation/schema gaps named in §3 are closed: the specialist trigger catalog exists, the tool registry has a versioning scheme, the `apps/api`↔`ai-engine` contract is documented, the embedding model is pinned by a real ADR, and the partition-maintenance job is scheduled.
- Every consuming epic (E6, E10, E12, E13, E19) can begin its own Technical Design phase against a real, working gateway instead of a paper one — the same "unblocks downstream epics" framing E4's own Business Objective used.

## 3. Scoping boundary and conflicts found

Per this repo's own established discipline: conflicts are documented here, not silently resolved.

### 3.1 The specialist trigger-condition catalog does not exist

AI_SYSTEM.md §3 states: "Full governance detail — including the exact trigger-condition catalog and tool-registry versioning — lives in AI_GOVERNANCE.md §2, §6." Read directly: AI_GOVERNANCE.md §2 gives exactly one worked example ("a recurring grammar-error pattern crossing a confidence threshold during a Conversation Partner session") and no catalog; §6 states only that a versioned tool registry exists as a policy ("no agent has unscoped code execution or unrestricted external calls"), not its actual schema or version scheme. **This is a real gap, not a cross-reference this document simply hadn't read carefully enough** — confirmed by reading both sections directly, the same discipline E4 applied to its own MULTITENANCY.md §6 schema-lint-script gap. **Resolved here:** §5.5/§7 (ADR-032) design the catalog format and versioning scheme; AI_GOVERNANCE.md §2/§6 get updated in the same PR that lands T5 (§9), so the forward-reference becomes true rather than staying a dangling promise.

### 3.2 The internal `apps/api` ↔ `ai-engine` contract does not exist

AI_SYSTEM.md §2 states the internal request/response contract "is documented alongside the OpenAPI spec (API_GUIDELINES.md §11) rather than left implicit." API_GUIDELINES.md §11, read directly, only states that OpenAPI is generated exclusively from `@nestjs/swagger` decorators — it names a _mechanism_ for documenting any REST contract, not this specific one. No DTO, controller, or contract for `ai-engine` exists anywhere in the repository (confirmed: `services/ai-engine/src/` has exactly one controller, the E1 health-check). **Resolved here:** §6.3/§7 (ADR-033) design the actual contract.

### 3.3 No numeric cost-circuit-breaker thresholds exist, deliberately

AI_GOVERNANCE.md §5 states thresholds "are set from real staging/production traffic data and reviewed monthly, not fixed permanently at a guessed initial value." This is not a gap this document closes — inventing a specific per-minute dollar figure with no traffic data behind it would be exactly the "guessed initial value" the governance doc rules out. **Resolved here:** §6.4 designs the breach-ladder _mechanism_ (a Redis sliding-window counter + the documented 3-stage response) with a placeholder threshold explicitly marked provisional-until-staging-data, matching the same honesty this repo already applied to the provisional embedding dimension (E4 §6.3) before ADR-031 (§7) below pins a real one.

### 3.4 This epic writes to E4's schema; it does not own changing it

DATABASE.md §2.5's own status line: "the application logic that runs sessions/RAG/scoring is separate, later epic scope (E5+)." E4's `ai.prisma` header is explicit that cross-domain FKs must be real Prisma `@relation`s (ADR-030) and that the schema is not tenant-scoped. This epic treats both as fixed constraints, not open questions — any table this epic's application code writes to already exists; the one narrow exception is §3.5.

### 3.5 Two real, narrow schema gaps found against AI_SYSTEM.md's own stated requirements

Reading AI_SYSTEM.md §5 directly against the shipped `ai.prisma` schema (not assumed from the epic's own design intent) surfaces two mismatches:

1. **Memory hygiene.** AI_SYSTEM.md §5: "memory entries are versioned/superseded rather than unboundedly appended." `AIMemoryEntry` has no `supersededByEntryId`/version column — nothing prevents unbounded append today, contradicting the stated design. This needs a real, narrow migration (a nullable self-referential `supersededByEntryId` column), not an application-layer workaround pretending the column exists.
2. **Session rolling summary.** AI_SYSTEM.md §5: "For sessions long enough to approach the model's context window... the Orchestrator applies rolling summarization rather than truncating context silently." `AIAgentSession` has no `summary`/`rollingSummary` field to persist that summary durably (only short-term in-process/Redis memory is mentioned for turn-by-turn context) — if the summary needs to survive a process restart mid-session, a column is missing.

**Resolved here:** both are named as real, scoped follow-up migration work in §9 (T6), not silently absorbed into "this is application logic, not schema" — they are schema gaps, confirmed by reading the design doc's own stated requirement against the actual `CREATE TABLE`, the same class of finding E4 T10 made for `ProficiencyLevelHistory.userId`.

### 3.6 `services/speech-service` and `recommendation-engine` are also E1 skeletons

Confirmed directly: both are structurally identical 3-file NestJS skeletons to `ai-engine`'s pre-E5 state, with no real code. ARCHITECTURE.md §6's 5-step speaking-practice data flow assumes `speech-service` is functional; it is not, and won't be until E10. This epic's own scope (§1) is written to depend on `speech-service` only where unavoidable (the Router's provider-adapter pattern is speech-service-agnostic; the Orchestrator's text-turn mechanism does not require audio) — flagged here so a reader doesn't assume E5 alone makes Journey C fully real.

## 4. Bounded context & ownership

Per ARCHITECTURE.md §2.1: this epic is the **AI Coaching** bounded context's core infrastructure, hosted in `services/ai-engine` (and, where the Router's provider-adapter pattern is reused, `services/speech-service` — out of scope per §3.6, but the adapter _pattern_ this epic establishes is designed to be reused there, not reinvented). The explicit, load-bearing boundary this epic must never violate (ARCHITECTURE.md §2.1, verbatim): `recommendation-engine` owns deterministic/algorithmic decisions; `ai-engine` owns any decision requiring a generative model call; "the two are never allowed to duplicate the same decision logic." Every task in §9 that touches a decision (e.g., which specialist to invoke, which model tier to route to) is a _generative-reasoning-adjacent_ decision (routing/tooling), not a curriculum/scheduling decision — the latter stays `recommendation-engine`'s, unchanged by this epic.

## 6. Cross-cutting mechanics

### 6.1 `ModelProvider` interface and Router

Per AI_SYSTEM.md §2's own pinned interface: `generate`, `stream`, `embed`. Anthropic and OpenAI adapters both implement it; the Router selects per request class (e.g., `AI_MODEL_TEACHER_DEFAULT`/`AI_MODEL_ASSESSMENT_DEFAULT`, already declared in `.env.example`) and fails over to a configured secondary on provider error (ARCHITECTURE.md §7.1), logged for reliability monitoring. Streaming is used at every hop per AI_SYSTEM.md §7/PERFORMANCE.md §2's own design constraint — the Router's `stream` path is not an optional add-on.

### 6.2 Embedding model — real pinning, not another placeholder

E4 T5 used `vector(1536)` explicitly labeled provisional. This epic pins a real model via ADR-031 (§7): OpenAI `text-embedding-3-small`, chosen specifically because its 1536-dimension output matches the already-shipped column type exactly — the one choice among realistic candidates that requires **no re-embedding migration** to adopt, since no production embeddings exist yet to migrate (this epic is what would first write real ones). `OPENAI_API_KEY` is already a declared env var. If AI Engineering's own review later prefers a different model (e.g., Voyage AI, often paired with Anthropic-primary stacks), that is a real, tracked re-embedding migration per AI_GOVERNANCE.md §4's own stated cost — not a cost this ADR pretends doesn't exist, just one it avoids paying today without a concrete reason to.

### 6.3 `apps/api` ↔ `ai-engine` contract

REST (ADR-003), not gRPC — matching every other `apps/api`-to-`services/*` integration already in this repo, and keeping `@nestjs/swagger` generation (API_GUIDELINES.md §11) as the actual documentation mechanism the forward-reference in §3.2 claimed. Streaming responses (session message generation) use Server-Sent Events over the same REST endpoint, matching "REST + JSON, WebSocket only for real-time flows" (ADR-003) — an SSE stream is not a WebSocket, and a full-duplex WebSocket isn't needed here since the client only consumes a stream, it doesn't need to interrupt mid-generation for MVP. `apps/api` calls through a typed client, matching `packages/types`/`packages/validation`'s established role as "the real contract enforcement mechanism" (ARCHITECTURE.md §4).

### 6.4 Cost circuit breaker mechanism

A Redis sliding-window counter (per-minute and per-hour windows, matching AI_GOVERNANCE.md §5's own cadence), incremented from every `AIUsageLog` write's `costUsdMicros`. Checked before each new AI-invoking request reaches the Router. Breach ladder, transcribed verbatim from AI_GOVERNANCE.md §5: (1) degrade new requests to a cheaper model tier where the request class allows it, (2) if breach persists, hard-stop new AI-invoking requests with the documented graceful message, (3) page on-call immediately. Initial thresholds are a conservative placeholder (documented in the real implementation task, not this design doc, since a number here would misleadingly look decided) — explicitly flagged for revision once real staging traffic data exists, per §3.3.

### 6.5 Partition maintenance scheduling

E4 R-69: `partman.run_maintenance_proc()` exists but nothing calls it on a schedule. This epic adds a BullMQ repeatable job (daily) in `ai-engine` — the heaviest writer to the three partitioned tables (`AIMessage`, and indirectly `AIUsageLog`/`LearningEvent`) — invoking it. Flagged as relocatable if a shared "platform jobs" service emerges later (module 30); not blocking on that service existing first.

### 6.6 Real AWS KMS verification

E4 R-68: only `LocalStubDataKeyProvider` has ever run. This epic's own task (§9, T9) attempts a real `AwsKmsDataKeyProvider` round-trip if AWS credentials are available in the environment this task executes in; if they are not (the same constraint T1/T5 hit), that is reported honestly as still-open, not silently marked done via the local stub alone — matching the standing discipline that a claim needs real tool output behind it.

## 8. Alternatives considered

- **gRPC instead of REST for the `apps/api`↔`ai-engine` contract** — rejected: ADR-003 already settled REST as the platform's default inter-service contract style; gRPC would be a new pattern introduced for one integration with no stated performance case that REST-with-streaming-SSE can't meet within PERFORMANCE.md §2's 900ms first-token budget.
- **WebSocket for the streaming response** — rejected in favor of SSE: the client only ever consumes a one-directional stream from `ai-engine` for a given message turn; WebSocket's full-duplex capability is unused overhead, and ADR-003 already reserves WebSocket specifically for "real-time flows" (the client↔`apps/api`↔`speech-service` audio pipeline, E10's own scope) — not this text-turn hop.
- **Voyage AI embeddings instead of OpenAI** — considered, not chosen: Voyage is a common Anthropic-ecosystem pairing and may be revisited, but choosing it now would mean the 1536-dimension placeholder was wrong regardless (Voyage models are typically 1024-dim), incurring a real re-embedding migration cost this ADR can avoid by picking the model that already matches the shipped column.
- **A dedicated "platform jobs" service for partition maintenance** — rejected for now: no such service exists, and standing one up for a single scheduled job is premature infrastructure; `ai-engine`'s own BullMQ (already a dependency this epic adds) is sufficient and the job is explicitly documented as relocatable.
- **Deferring the trigger-condition catalog/tool-registry versioning to a later epic** — rejected: ADR-007's entire tool-calling contract (structured critique objects, bounded trigger firing) is unimplementable without it; deferring would mean shipping an Orchestrator that can never actually invoke a specialist, contradicting this epic's own stated success criteria (§2).

## 10. Open questions

Genuinely unresolved as of this draft — not silently decided, and not yet put to the user for a resolution decision the way E4 §10 recorded five such resolutions.

1. **Anthropic vs. OpenAI as primary provider for the Orchestrator's own generation calls.** `.env.example` sets `AI_GATEWAY_DEFAULT_PROVIDER=anthropic`, but ADR-031 (§7) pins OpenAI for _embeddings_ specifically — is Anthropic still primary for _generation_, with OpenAI used only for the embedding call? 3. **Top-N and token-budget numbers for memory retrieval** (AI_SYSTEM.md §5) — "not numerically specified anywhere," per direct reading. Needed before T6 ships a real Memory Manager, not decidable from the docs alone.
4. **Whether the trigger-condition catalog (ADR-032, T5) is authored by AI Engineering as prose requirements this epic translates into code, or whether this epic's own author proposes the initial catalog for AI Engineering to review** — a process question about who owns the first draft of pedagogically-meaningful thresholds (e.g., "how many repeated grammar errors constitute a pattern"), not an engineering question this document can resolve unilaterally.
