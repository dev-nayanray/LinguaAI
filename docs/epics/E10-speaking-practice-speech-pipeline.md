This document does not write any application code; it designs the module, surfaces real gaps found while doing so (§3), and proposes the ADRs implementation will need (§7). **This is the largest epic designed to date** — the platform's first real-time (WebSocket) transport, `services/speech-service`'s first real code (an E1 skeleton — a health controller only, confirmed by direct inspection — through E1–E9), and the first genuinely new external-provider category (STT/TTS) this platform integrates. RISK_REGISTER.md's own R-04 ("Speech provider latency/quality fails the conversational UX budget") already names this epic specifically as needing "a provider spike before full commitment" — addressed directly in §3.7/§11, not silently deferred.

## 1. Epic Definition

`ai.prisma`'s conversation schema (`AIAgentSession`, `AIMessage`, `FluencyScore`) has existed since E4 T5 and is already exercised for real by E5's text-only Orchestrator flow — but `AIMessage.audioUrl` has sat unused since E4 T5 (confirmed by direct search: zero write sites anywhere in this repo), `FluencyScore` has never been written by any code, and `services/speech-service` itself has never had a line of real logic. This epic is what makes voice real: a WebSocket-based real-time audio pipeline (client ↔ `speech-service` ↔ STT/TTS providers), wired into E5's already-built Orchestrator/`RouterService`/memory/safety stack for the actual conversational turn, closing PRD.md Journey C end to end for the first time.

**In scope:**

- `services/speech-service`'s first real domain code: provider-agnostic STT/TTS adapters (ADR-006's own adapter pattern, extended from LLM providers to speech providers), and the real-time WebSocket gateway that terminates the client's audio connection (§6.1).
- `apps/api`'s new speaking-session lifecycle endpoints (`POST`/`DELETE /v1/speaking-sessions`) — creates/ends the underlying `AIAgentSession`, mints the short-lived internal token that authorizes the client's direct WebSocket connection to `speech-service` (§6.2, ADR-043).
- The full real-time round trip: audio chunks in → streamed STT partial/final transcript → `ai-engine`'s existing `OrchestratorService` (reused, not rebuilt) for the conversational turn → streamed TTS audio out, meeting PERFORMANCE.md §2's canonical p95 ≤ 2.5s budget (§6.3).
- Session-end handling: a new, narrow `FluencyScoringService` (`ai-engine`, one-shot, mirrors `AssessmentScoringService`/`ContentDraftingService`'s own established pattern) writing `FluencyScore`; a real integration point into E9's `PersonalDictionaryService` for "vocabulary extracted for spaced repetition" (PRD Journey C step 3); a new, cataloged (but not-yet-consumed) domain event for `analytics-service` (§6.4).
- Graceful text-only degradation on STT/TTS provider failure (AI_GOVERNANCE.md §7's own already-decided fallback, built for real here) and WebSocket reconnection/session-resumption (API_GUIDELINES.md §9's own already-specified contract, tested against simulated drops per TESTING.md §4) (§6.5).

**Explicitly out of scope** (cited against ROADMAP.md/PRD.md's own classification, not silently absorbed):

- **Phoneme-level pronunciation scoring** (`PronunciationScore`, module 8) — a separate PRD module with its own epic (E11 — Pronunciation Lab, depends on E10 per ROADMAP.md). `ai.prisma`'s own header comment already flags that `PRONUNCIATION_LAB_ATTEMPT` (one of `PronunciationScoreSource`'s two variants) has no backing entity anywhere in the schema — E10 does not close that gap; it is E11's own scope. E10's `FluencyScore` (session-level: fluency/coherence/pronunciation/grammar component scores) is a materially different, coarser signal than `PronunciationScore`'s own below-word-level phoneme data, and does not substitute for it.
- **The real conversation-session UI** (`apps/web`/`apps/mobile` pixels, mic capture, waveform, live-captioning display) — matching E4–E9's own precedent (backend/engine epics, not UI epics), this epic designs the WebSocket contract and backend pipeline a future UI consumes, not the actual screen (§3.6).
- **A live provider latency spike against real STT/TTS traffic** — RISK_REGISTER R-04 names this as a real precondition for "full commitment" to this epic; this environment has no live provider credentials (RISK_REGISTER R-88, the same standing limitation every AI-calling epic in this session has carried), so the spike itself cannot be executed here. Addressed honestly in §3.7/§11: the pipeline is built real and correct against the adapter interface, with the actual measured-latency validation named as required, real, separately-scoped follow-up the moment live credentials exist — not silently declared "done" by this epic's own local verification.
- **A second, failover STT/TTS provider** — unlike the LLM fallback chain (primary→secondary provider, AI_SYSTEM.md §2), AI_GOVERNANCE.md §7's own already-decided fallback for STT/TTS is "degrade to text-only," not "fail over to a second provider." Only one STT/TTS provider is integrated (§7, ADR-043); building a second is real, separately-scoped future work if this platform ever decides to change that fallback strategy.
- **`analytics-service`'s own consumption of the new session-completed event** — this epic is the event's producer (§6.4); `analytics-service` remains an E1 skeleton (confirmed by direct inspection, no epic has touched it through E1–E9) and building its own consumption is that service's own future epic's scope, flagged here (a new RISK_REGISTER entry, §11) rather than silently absorbed.
- **Retroactively adding signed internal tokens to `apps/api` ↔ `ai-engine`'s own existing HTTP calls** — SECURITY.md §1 states plainly that "being inside the VPC does not exempt a service-to-service call from authentication... signed internal tokens apply even between two `apps/api`-adjacent services," but direct inspection confirms `ai-engine`'s own controllers (`AssessmentScoringController`, `ContentDraftingController`, `AgentSessionsController`, etc., ADR-033's own established pattern since E5 T10) carry **no** auth guard and no token verification of any kind — a real, pre-existing gap across every prior AI-calling epic (E5–E9), not something E10 introduces. E10's own new client-facing WebSocket handoff _does_ get a real signed internal token (§6.2, ADR-043) — the literal case ARCHITECTURE.md's own data-flow example already names. Retrofitting the unrelated, already-shipped `apps/api`↔`ai-engine` HTTP surface is flagged as a new, real, found gap (§11) for whichever future task next touches that boundary, not silently fixed as a drive-by change here.

**Depends on:** E5 (AI Teacher Platform — `OrchestratorService`, `RouterService`, `AIAgentSession`/`AIMessage` persistence, memory, safety layer, and the Conversation Partner persona all already exist and are reused here, not rebuilt); E4 (Database Schema — `ai.prisma`'s conversation schema already exists, real schema, zero drift found during this document's own research).

## 2. Business Objective

PRD.md Journey C (Speaking Practice Session) is this platform's own named "signature 'personal AI teacher' moment" (ARCHITECTURE_REVIEW.md's own words) and core differentiator versus Babbel/Duolingo (neither offers live spoken AI conversation) — this epic is what makes that journey real for the first time, end to end. Its own literal acceptance criteria (PRD.md §4): "end-to-end voice round-trip p95 ≤ 2.5s at launch... session gracefully degrades to text-only on poor network/mic permission denial; feedback is specific (not generic) and tied to the transcript."

**Success looks like:**

- A learner can open a real-time voice session, speak, and receive a spoken AI response — audio captured, transcribed, reasoned over by the existing Conversation Partner Orchestrator (with full memory/safety-layer continuity, §6.3), and spoken back — with every stage's own budget from PERFORMANCE.md §2 honored by design (streaming at every hop), even though the actual measured p95 cannot be validated against a live provider in this environment (§3.7).
- A dropped connection mid-session resumes within the 60-second grace window API_GUIDELINES.md §9 already specifies, rather than losing the conversation (§6.5, TESTING.md §4's own named requirement).
- A forced STT/TTS provider failure degrades the session to text-only rather than ending it (§6.5, AI_GOVERNANCE.md §7's own already-decided fallback, built for real).
- Session end produces a real `FluencyScore` row and extracts vocabulary into the learner's own personal dictionary (E9's `PersonalDictionaryService`, `source: CONVERSATION`) — PRD Journey C step 3 ("session ends with fluency score, corrected transcript, and vocabulary extracted for spaced repetition") made real, not aspirational (§6.4).

## 3. Scoping boundary and conflicts found

### 3.1 `ai.prisma`'s conversation schema is already fully designed (E4 T5) — zero schema drift found, two real fields finally get a writer

`AIAgentSession`/`AIMessage`/`FluencyScore` exist exactly as DATABASE.md §2.5 describes, confirmed by direct inspection of `packages/database/schema/ai.prisma`. No schema change is anticipated by this design. `AIMessage.audioUrl` and `FluencyScore` (both schema-only since E4 T5, confirmed by a full-repo search finding zero write sites for either) get their first real writer in this epic (§6.3, §6.4).

### 3.2 `services/speech-service` is a pure E1 skeleton — this epic is its first real code

Confirmed by direct inspection: `services/speech-service/src/` contains only `app.module.ts`, `main.ts`, and a health controller — no domain logic, no Postgres access, no provider integration of any kind. This mirrors `recommendation-engine`'s own pre-E7 state exactly (ADR-040's own precedent for "a service's first real build-out").

### 3.3 No STT/TTS provider has ever been pinned anywhere in this platform's docs

A full-repo search for named STT/TTS providers (Deepgram, Whisper, ElevenLabs, Azure Speech, Google Speech, AssemblyAI) found zero hits outside this document's own research — `AI_SYSTEM.md` names the adapter _pattern_ ("`services/speech-service` (STT/TTS providers, behind the same adapter pattern)") but never a concrete provider, the same class of "pattern specified, value left open" gap ADR-031 already closed for the embedding model. Resolved here (§7, ADR-043).

### 3.4 No WebSocket infrastructure exists anywhere in this codebase today

Confirmed by a full-repo search (`@nestjs/websockets`, `socket.io`, `ws`, `WebSocketGateway`): zero hits in `apps/api` or any `services/*`. API.md §7/API_GUIDELINES.md §9 already specify the real-time API _policy_ (WSS, `{type, payload, sessionId, ts}` envelope, namespaced `type` values, ack/reconnection semantics) in detail — but nothing has ever implemented it. This epic is the first.

### 3.5 A real topology decision ARCHITECTURE.md's own data-flow example leaves implicit

ARCHITECTURE.md §6's own "Speaking practice session" data-flow example states: "Client opens a WebSocket to `apps/api`, which authenticates and hands off session control to `services/speech-service` via an internal token" — but doesn't specify whether `apps/api` proxies every subsequent audio frame (a WS-to-WS relay) or whether the client reconnects directly to `speech-service` after receiving the token. Resolved here (§7, ADR-043) in favor of a **direct client↔`speech-service` WebSocket** after an `apps/api`-minted, locally-verifiable token — avoiding a double-hop that would consume a meaningful fraction of PERFORMANCE.md §2's own tight 300ms transport-overhead budget for no benefit, and matching ADR-033's own "internal trust, not a synchronous re-auth round trip" reasoning, extended here from service-to-service trust to a token-mediated client-to-service handoff.

### 3.6 This epic is backend/engine only, not the actual conversation-session UI

Matching E4–E9's own precedent (backend/engine epics, not UI epics), this epic designs the WebSocket contract and backend pipeline, not `apps/web`/`apps/mobile`'s real conversation-session screen (neither exists today, confirmed by direct inspection — no microphone-capture or live-transcript UI of any kind exists in either app). PRD.md's "signature moment" acceptance bar is only fully satisfied once that later, UI-focused epic ships; this epic is its necessary, load-bearing precondition.

### 3.7 RISK_REGISTER R-04's own named precondition cannot be fully closed in this environment

R-04 ("Speech provider latency/quality fails the conversational UX budget... Provider spike before full commitment required in E10") names a real precondition this document cannot fully satisfy: this environment carries no live STT/TTS provider credentials (the same standing RISK_REGISTER R-88 limitation every AI-calling epic since E5 has carried, confirmed still true — `.env`'s own `OPENAI_API_KEY`/`ANTHROPIC_API_KEY` are present as config plumbing but no live spend/verification has ever occurred in this session). This epic builds the pipeline real and correct against the provider adapter interface (§6.1) and documents the exact, real latency budget every stage must hit (PERFORMANCE.md §2) — but the actual live-provider latency measurement R-04 calls for remains real, tracked, separately-scoped follow-up (§11), not silently declared satisfied by this epic's own necessarily-stubbed local verification.

### 3.8 `AiRequestClass` needs a fourth value — the conversational turn itself doesn't change, but session-end scoring does

`OrchestratorService.streamMessage()`/`sendMessage()` already use the `'teacher'` request class for the live conversational turn (E5) — reused here unchanged, since a spoken conversational turn is the same conversational-turn shape whether the transcript arrived by keyboard or by voice. But session-end fluency scoring (§6.4) is a one-shot, structured-output task with no session/memory concept of its own — the exact category ADR-039 already named and ADR-041 already extended once (E8 T4, `'content'`). Fluency scoring is neither conversational (`'teacher'`) nor content-authoring (`'content'`) nor essay-scoring (`'assessment'`, ADR-039's own scope was specifically writing) — resolved here (§7, ADR-044) with a fourth class, `'fluency'`, rather than overloading `'assessment'` (a materially different rubric/output shape from writing-critique scoring) or `'content'` (a materially different purpose from admin-review-gated drafting).

## 4. Bounded context & ownership

`services/speech-service` (already-justified as a separate service since E1/ARCHITECTURE.md §4: "needs low-latency streaming infra distinct from request/response REST; may run on different compute") owns the real-time WebSocket gateway and STT/TTS provider adapters. It deliberately gets **no direct Postgres access** to `ai.prisma`'s conversation tables (§7, ADR-044) — `ai-engine` remains the sole owner/writer of `AIAgentSession`/`AIMessage`/`FluencyScore`, called via internal HTTP (extending ADR-033's already-established `apps/api`↔`ai-engine` pattern to a second internal caller). A new, thin `apps/api/src/modules/speaking/` (`SpeakingModule`, per ADR-001 — session-lifecycle bookkeeping and token-minting have none of the three properties that would justify their own service) owns `POST`/`DELETE /v1/speaking-sessions`.

## 6. Cross-cutting mechanics

### 6.1 `services/speech-service`'s STT/TTS provider adapters

Mirrors `ai-engine`'s own `ModelProvider` interface pattern (ADR-006) — a provider-agnostic `SpeechProvider` interface (`streamTranscribe(audioStream) -> AsyncIterable<TranscriptChunk>`, `streamSynthesize(text) -> AsyncIterable<AudioChunk>`) with exactly one concrete implementation at launch (ADR-043) behind it, so a future provider swap is a configuration change, not a rewrite — the same "no application code calls an LLM/STT/TTS SDK directly" rule ADR-006/AI_SYSTEM.md §1 already states verbatim for this exact case.

### 6.2 Speaking-session lifecycle & the internal token handoff (ADR-043)

`POST /v1/speaking-sessions` (`apps/api`, any authenticated learner — `AuthGuard('jwt')` only, no `ADMIN` gate, matching `AssessmentModule`'s own learner-facing precedent) creates a real `AIAgentSession` (`orchestratorAgent: CONVERSATION_PARTNER`) via the existing `AiEngineClientService.startSession()` call E5 T10 already built and returns a short-lived (60s), narrowly-scoped, HS256-signed token (claims: `sessionId`, `userId`, `exp` — a new, small `@linguaai/config` schema fragment shared between `apps/api`, which signs, and `speech-service`, which verifies locally with zero network round-trip, the latency-driven reasoning §3.5 already states). The client then opens a WebSocket directly to `speech-service`'s `/realtime/speaking-sessions/:sessionId`, presenting the token at handshake (API.md §7's own "connections authenticate via the same access JWT, passed at handshake" pattern, adapted here for this narrower, session-scoped token rather than the full user access token). `DELETE /v1/speaking-sessions/:id` marks the `AIAgentSession` `ENDED` and triggers §6.4's session-end scoring.

### 6.3 The real-time round trip

1. Client streams binary audio chunks over the WebSocket; `speech-service` acknowledges each (API_GUIDELINES.md §9's own `{type: "ack", forSeq: n}` contract) and feeds them to the STT adapter's streaming transcription.
2. Partial/final transcripts stream back as `speech.partial-transcript`/`speech.final-transcript` messages (the exact `type` values API_GUIDELINES.md §9 already names) for live captioning.
3. On a final transcript, `speech-service` calls a new `ai-engine` endpoint (extending `AgentSessionsController`, E5 T10's own established shape) that both persists the user's own `AIMessage` (now with a real `audioUrl`, §3.1) and streams the Orchestrator's response — reusing `OrchestratorService.streamMessage()` end to end, unchanged (§3.8) — relayed to the client as `ai.token`/`ai.done` messages (already-named `type` values).
4. As response text arrives, `speech-service` feeds completed sentences to the TTS adapter and streams synthesized audio back as `speech.audio-chunk` messages; the assistant's own `AIMessage` row (already written by step 3) is updated with its own `audioUrl` once synthesis completes.
5. Every stage is streamed, never buffered-then-sent-whole (PERFORMANCE.md §2's own explicit design constraint on provider selection, not a post-hoc optimization).

### 6.4 Session-end: fluency scoring & vocabulary extraction

On `DELETE /v1/speaking-sessions/:id` (or a client-initiated graceful end), `apps/api` calls a new, narrow `FluencyScoringService` (`services/ai-engine/src/fluency-scoring/`, mirroring `AssessmentScoringService`/`ContentDraftingService`'s own established one-shot-capability shape exactly: `RouterService.generate('fluency', ...)`, `SafetyLayerService.sanitizeOutput()` on any returned free-text feedback, a new versioned standalone prompt template) that reads the session's own `AIMessage` history and writes a real `FluencyScore` row (`componentScores: {fluency, coherence, pronunciation, grammar}`, matching that column's own doc-comment-specified shape). The same call extracts notable vocabulary from the transcript and saves each into the learner's personal dictionary via E9's real `PersonalDictionaryService.create()` (`source: 'CONVERSATION'` — a `VocabularySource` enum value that has existed unused since E9 T2, confirmed by direct inspection, this epic's own first real consumer of it). A new `learning.speaking_session.completed` domain event is cataloged (`EVENT_ARCHITECTURE.md`) and published (existing `DomainEventPublisher`, no new transport) — no real consumer exists yet (`analytics-service` remains an E1 skeleton, §1's own scope boundary), the same "build the producer real, flag the not-yet-built consumer" precedent E7/E8 already established.

### 6.5 Graceful degradation & reconnection

**STT/TTS failure** (provider error/timeout mid-session): `speech-service` stops attempting audio synthesis/transcription for the remainder of the session and switches the client into text-only mode — the client keeps receiving `ai.token`/`ai.done` (text) but no further `speech.*` messages; a `speech.degraded` message (a new, explicitly-named `type` value) tells the client why, so the UI can show a real, honest status rather than silently going quiet. Matches AI_GOVERNANCE.md §7's own already-decided fallback ("Speaking session degrades to text-only conversation rather than failing the session entirely") — built for real here, not just documented as policy.

**Reconnection**: a dropped WebSocket is resumed by `sessionId` within the 60-second grace window API_GUIDELINES.md §9 already specifies — `speech-service` keeps the session's in-memory turn state (current STT/TTS stream position, not yet flushed to `AIMessage`) alive for that window; a reconnect within it resumes the same `AIAgentSession`, a reconnect after it must start a new session (the existing `AIAgentSession` transitions to `ABANDONED`, an already-real enum value with no prior writer, confirmed by direct inspection — this epic's own first real consumer of it too). Tested against a simulated mid-session drop (TESTING.md §4's own named requirement).

## 8. Alternatives considered

- **WebRTC instead of WebSocket for the audio transport** (rejected) — ARCHITECTURE.md §4's own service-justification table names WebRTC as a possibility ("may run on different compute (audio codecs, WebRTC)"), but API.md §1/§7 already settled on WebSocket (WSS) as this platform's own chosen real-time transport, for every real-time flow named including "live speaking sessions" explicitly — not this document's own decision to re-litigate. WebRTC's own SFU/TURN infrastructure would be real, unjustified added complexity against an already-settled policy.
- **`apps/api` proxies every audio frame to `speech-service`** (rejected, ADR-043) — a real double-hop that would consume a meaningful fraction of PERFORMANCE.md §2's own 300ms transport-overhead budget for zero benefit; the direct-connection-after-token-handoff model achieves the same authentication guarantee (§6.2) without it.
- **`speech-service` gets its own direct Postgres access to `ai.prisma`'s tables** (rejected, ADR-044) — the concrete encryption-duplication risk named above is a real, security-relevant reason to route through `ai-engine`'s own HTTP API instead, not just an abstract preference for fewer database connections.
- **A second, failover STT/TTS provider, mirroring the LLM primary→secondary chain** (rejected, ADR-043) — AI_GOVERNANCE.md §7's own already-decided fallback for STT/TTS is "degrade to text-only," a materially simpler (and already-approved) strategy than a second provider integration; building one now would be scope beyond what any document has ever required.
- **Session-end fluency scoring reuses the `'assessment'` request class** (rejected, §3.8) — `AssessmentScoringService`'s own `'assessment'` class was scoped specifically to placement-test writing critique (ADR-039); fluency scoring's own rubric/output shape and its live-conversation (not placement-test) context are materially different, the same reasoning that already justified `'content'` as its own class rather than overloading `'assessment'` for lesson drafting (ADR-041).

## 10. Open questions

Genuinely unresolved as of this draft — not silently decided, and not yet put to the user for a resolution decision the way E4–E9's own §10 recorded theirs.

1. **The exact `FluencyScore.componentScores` rubric weighting** (§6.4) — the column's own shape (`{fluency, coherence, pronunciation, grammar}`) is fixed by the schema's own doc comment, but how each component score is actually derived from a transcript (prompt design, 0-100 vs. CEFR-band output) is a real, provisional implementation-time decision, the same class of honesty E6's `CONFIDENCE_FLOOR`/E7's weakness thresholds already were.
2. **Whether "notable vocabulary" extraction (§6.4) needs its own dedicated prompt/heuristic, or piggybacks on the same `FluencyScoringService` call** — left as a real implementation-time call; a combined single model call is the more cost-efficient default, but a session with unusually rich vocabulary might warrant its own dedicated pass. Not decided here.
3. **The in-memory turn-state buffer's own durability during a `speech-service` process restart** (§6.5) — a reconnect within the grace window assumes the same `speech-service` replica (or a shared cache) still holds the session's live state; whether this needs a Redis-backed shared buffer (surviving a replica recycle) or can start as single-replica in-memory state is a real, deliberately-provisional MVP scoping call, flagged rather than silently assumed either way.
