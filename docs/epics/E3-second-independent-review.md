## 1. Executive Summary

The remediation pass is substantial, well-organised, and in large part genuinely successful. Eleven of the twenty-four original findings are independently confirmed **closed** — including three of the ten Highs (F-H3, F-H4, F-H6, plus the non-blocking F-H8) and six of the nine Mediums. The token-remapping architecture (brand-identity / accessible-text / accessible-border / solid-fill) is the right answer to F-C2 and is internally coherent. ADR-024 and ADR-025 are correctly appended to DECISIONS.md in the canonical format with `Proposed` status and index rows, not self-approved. R-54–R-61 are real register rows with owners, mitigations, and honest statuses — none marked Closed. The report is candid about what it did not fix (F-M7, F-M9) rather than papering over it. That candour is worth recording, because it is what made the rest of this review tractable.

It nonetheless cannot pass. Both Critical findings survive, for reasons the remediation could not have known but the gate must:

1. **F-C1 is not resolved, and the §6a specification is demonstrably wrong.** Applied exactly as written, it _breaks_ the very import it exists to protect. Reproduced empirically: with §6a's `ui-package` element type added and the rest of `eslint.config.js` left as the design leaves it, `apps/web/src/app/login/page.tsx` gains a new error — `No rule allows the entry point 'index.ts' in dependencies of type 'ui-package'  boundaries/entry-point`. §6a specifies changes to `boundaries/elements` and `boundaries/element-types` and says nothing about `boundaries/entry-point`, whose `default: 'disallow'` catches every element type not named as a rule `target`. The current config's own inline comment documents this exact hazard as "verified empirically — it did." The design's own "Allowed control" fixture and §21's Architecture Gate blocking criterion would both fail on day one of T2. Separately and more deeply: `pnpm lint` does not enforce these rules on real source code at all (§6, N-3), so the enforcement premise §6a rests on is itself false.

2. **F-C2 is only half-resolved, and one token recorded as PASS actually fails.** Every ratio in the Tier-2 semantic table was independently recomputed and is correct to two decimal places — that table was genuinely computed. The _derived neutral/surface/state_ table immediately below it was not: six of seven checked values are wrong, and `--color-info` `#0284c7` is recorded as **4.51:1 (PASS)** when it computes to **3.91:1** against `--color-bg`, **4.10:1** against `--color-surface`, and **3.74:1** against `--color-surface-muted` — failing WCAG 1.4.3's 4.5:1 body-text floor on every light surface the design defines. Separately, the entire matrix validates exactly one background per theme while the same section introduces `--color-surface` and `--color-surface-muted`, on which most of the component inventory actually renders: `--color-warning-border` computes to **2.91:1** on `--color-surface-muted`, below the 3:1 UI-component floor. "WCAG AA met by construction using the semantic token layer" is therefore not yet a defensible claim — the construction is validated against one of four defined light backgrounds and already fails on a second.

Beyond the Criticals, four further High findings are new to this pass: the `@/` alias fix does not cover the `transpilePackages` path that is how `packages/ui` is actually compiled by its consumers (N-4); §18's authentication mechanism cannot be built as specified, because CloudFront Functions cannot read Secrets Manager (N-5); the "complete" three-tier token hierarchy still has no type scale, which DESIGN_SYSTEM.md §3 requires and `tokens.css` lacks (N-6); and ADR-015's boundary rules are inert against real source code under the repository's actual lint invocation (N-3).

The direction remains correct and this review endorses it, as the first did. What is missing is a further pass of the same _kind_ of verification the remediation applied to the Tier-2 table — applied to the parts of the document it did not apply it to.

## 3. Verification Method

Each of the 24 findings was assessed against three independent questions, any one of which can fail on its own:

- **(a) Diagnosis** — did the remediation understand the underlying problem the first review found?
- **(b) Sufficiency** — would the proposed fix, applied _exactly_ as specified, actually solve it?
- **(c) Honesty** — does the remediation accurately represent what is and is not yet applied to the repository?

Specific techniques used:

- **Contrast ratios were recomputed from scratch** from the actual hex values in `packages/ui/src/styles/tokens.css` and the design's own proposed values, using the WCAG 2.1 relative-luminance formula (sRGB linearisation at the 0.03928 threshold, `0.2126R + 0.7152G + 0.0722B`, `(L1+0.05)/(L2+0.05)`). Fifty-eight pairings were computed, including pairings the design does not evaluate (`--color-surface`, `--color-surface-muted`, and their dark counterparts). No number was copied from either document; each was derived and then compared. The formula was sanity-checked against a known reference (`#dc2626` on `#ffffff` = 4.83, matching the published value).
- **The §6a ESLint specification was executed, not read.** A configuration replicating §6a exactly (its `boundaries/elements` insert and its `boundaries/element-types` rules, with `boundaries/entry-point` left as the repository has it, since §6a proposes no change there) was written to a scratchpad file outside the repository and run against real repository files via `eslint --config`. No repository file was modified. The plugin's element-resolution and entry-point rule sources were read at the installed version (4.2.2) to confirm the mechanism behind the observed behaviour.
- **Lint enforcement scope was tested at both invocation sites** — from the repository root (as `verify-boundary-lint.mjs` does) and from inside `apps/web` (as `turbo run lint` does) — because `eslint-plugin-boundaries` resolves element paths relative to `process.cwd()`.
- **The task graph was rebuilt independently** from the Depends-on column, and then again from the Evidence column (the method F-H10 itself prescribes), and the two were compared.
- **Every "already exists / verified present" claim was checked against the filesystem** — the `edge` Terraform module's contents, `preview-cleanup.yml`'s actual behaviour, `postcss`'s resolvability from `packages/ui` under pnpm's isolated layout, and the absence of any bundle-size or Storybook step in all eight workflows.

**Calibration.** E2's third and fourth targeted reviews each found real Critical/High defects in work two prior reviews had approved. That precedent was applied in both directions: no finding here is manufactured to appear thorough, and eleven findings are recorded as genuinely closed. The four fully-worked component contracts (§12.4) and the two ADRs were read with deliberate extra scepticism as the newest, least-precedented content.

### What this decision does and does not mean

It does **not** mean the remediation failed. Eleven findings are genuinely closed, including three blocking Highs and six Mediums. The token-remapping architecture, the layered accessibility strategy, the ADR discipline, the risk-register entries, the performance correction, and the honesty of the "specified, not applied" framing are all of a standard this project should want to keep. Where the remediation verified, it verified well — the Tier-2 contrast table is exact to two decimal places across eighteen values, which is not luck.

It means the verification was not uniform. The Tier-2 table was computed; the table beneath it was not. The `eslint.config.js` content was read; the plugin's entry-point interaction and the lint invocation's working directory were not tested. The `edge` module's existence was confirmed; its contents and the CloudFront Function runtime's actual capabilities were not. In each case the gap is exactly one step past where verification stopped.
