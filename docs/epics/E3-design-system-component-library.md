## 1. Executive Summary

E1 scaffolded `packages/ui`: design tokens, the Shadcn CLI, Storybook, one real component (`Button`) and one infrastructure component (`ErrorBoundary`). Every other component category DESIGN_SYSTEM.md §4 requires does not exist yet. E2 built minimal, duplicated form primitives directly inside `apps/web`/`apps/admin` (`auth-form.tsx`, essentially identical in both apps) rather than build a shared component library prematurely — a reasonable call at the time, and the live CODING_STANDARDS.md §3 debt this epic exists to close.

E3's job is to turn `packages/ui` into the real, 45-component (§12.2's exact count, corrected this pass from the prior approximate "~40" — closing the sixth review's P6-10), two-theme, accessible library every subsequent epic's UI is built on, without inventing new product functionality, without reopening DESIGN_SYSTEM.md's brand-color decisions, and without silently expanding into any other epic's scope.

Three design-phase Architecture Gate reviews have now examined this design. Between them they found and this pass carries forward as closed: an unenforced (and, before correction, entirely inert under real per-package lint invocation) dependency boundary; brand tokens that fail WCAG AA in functional use, both as originally accepted anchors and in a first "corrected" pass that itself asserted rather than computed several values; an unbuildable Storybook access-control mechanism (CloudFront reading Secrets Manager directly, which the runtime cannot do); a missing typography scale; several self-contradictory or vacuous component contracts; and cross-reference drift in the task graph. This pass additionally fixes: a document-completeness regression the second remediation pass caused by deleting most of its own content; an operational gap in the boundary-lint rollout that would have broken CI permanently; a Next.js/TypeScript alias design that was still missing the two files where it actually fails; a default UI border token that fails the WCAG 1.4.11 floor by a wide margin; and several smaller accuracy and ownership gaps. Every fix below states plainly whether it was verified this pass by actual computation or execution, or whether it is a plan for implementation to carry out and verify — the distinction the reviews have repeatedly found blurred in prior passes.

## 2. Scope

**In scope:** the token architecture (colors, typography, spacing, motion, breakpoints, both themes); the 45-component library across the ten DESIGN_SYSTEM.md §4 categories (foundation depth — one working, accessible implementation per component, not every visual variant a later epic might want); the primitive (Shadcn/Radix) install and theming layer; Storybook as the component-development and review environment, plus its hosted preview; the inter-package dependency boundary that keeps `packages/ui` presentational; migrating `apps/web`/`apps/admin`'s duplicated `auth-form.tsx` onto the new Form components; the Flutter design-token export mechanism (build-only, consumed by the future mobile epic, not built by it).

**Out of scope (see §3 Non-Goals for the full list and reasoning):** any new product feature or screen; DESIGN_SYSTEM.md's brand hue values; a published/versioned npm package; full cross-browser visual regression testing; the Flutter app itself; any other epic's scope.

## 3. Non-Goals

- **Not a redesign of DESIGN_SYSTEM.md's brand decisions** — **corrected this pass, closing the sixth review's P6-6 (Low): the anchor hex values DESIGN_SYSTEM.md §2 actually defines are primary/AI-purple/accent/success/warning, five anchors, not seven.** `danger` and `info` have no anchor in DESIGN_SYSTEM.md §2's color table (verified by reading it directly) and no anchor anywhere in `tokens.css` — they exist only as E3-introduced semantic-tier tokens (`--color-danger-text`/`-solid`, `--color-info-text`), derived directly with no canonical-document anchor to preserve or redesign. This document builds the semantic and component layers on top of the five real anchors; where an anchor's _functional_ (text/border/UI-component) use fails WCAG, this document proposes a derived variant for the UX Director's confirmation (§25 Q1) rather than silently changing the anchor. `danger`/`info`'s semantic-tier values are this document's own decision, not a DESIGN_SYSTEM.md value being preserved.
- **Not an LMS feature.** No lesson content, no curriculum logic, no learning-path screens. Components here are presentational primitives consumed by later epics.
- **Not E4's, E8's, or any other epic's scope pulled forward.** Every component category traces to DESIGN_SYSTEM.md §4's existing table; nothing is added because a later epic will eventually want it.
- **Not a publish-to-npm package.** `packages/ui` stays `workspace:*`-internal; §7 states this explicitly.
- **Not full cross-browser visual regression.** TESTING.md §9 (line 68) defers this explicitly: "Full cross-browser visual regression testing — introduced once the design system (DESIGN_SYSTEM.md) stabilizes past initial component development." A narrower floor is specified instead (§17).
- **Not the Flutter app.** E3 builds only the token-export mechanism (ADR-024); consuming it is a future mobile epic's work.

## 4. Business Requirements

- **BR-1.** Every subsequent epic's UI (web and admin) consumes `packages/ui` components rather than hand-rolling Tailwind markup — the mechanism CODING_STANDARDS.md §3 requires and which today has no library to point at.
- **BR-2.** No engineer building a screen after E3 has a reason to hand-roll a form field, a card, a modal, or a data table, because the library already has one that fits.
- **BR-3.** Every component in `packages/ui` meets WCAG 2.1 AA for the states and contrast pairings it actually ships in, verified by computation against the real token values (§12.1), not assumed from the canonical brand-anchor hex codes.
- **BR-4.** The design token layer (color, type, spacing, motion) is the single source of truth for both `apps/web`/`apps/admin` (via Tailwind, at build time) and, eventually, Flutter (via the ADR-024 export), so a token change never needs hand-propagation across platforms.

## 5. User Journeys

- **J1 — Engineer building a new screen.** Imports a component from `@linguaai/ui` (or a category subpath, §6d), reads its Storybook entry for props/variants/states, composes it. No Tailwind palette values, no ad hoc spacing, no component reinvention.
- **J2 — Engineer extending `packages/ui` itself.** Adds a new variant/state to an existing component or a new component in an existing category, following the contract template (§12.4), with a Storybook story per state and (per the required manual-check list, §12.5) a screen-reader pass if the component is one of the eight named high-risk ones.
- **J3 — Designer/UX Director reviewing a screen.** Uses the per-category `UI_UX_REVIEW_TEMPLATE.md` instance (§21) as the review artifact — tokens used, states covered, responsive behavior, accessibility checklist — rather than an ad hoc visual pass.
- **J4 — Future Flutter engineer (E21).** Consumes the generated `design-tokens.json` artifact (ADR-024) as a defined, versioned schema, never hand-copies a hex value out of `tokens.css`.

## 6. Architecture

`packages/ui` is a presentational-only package: React components, tokens, and Storybook stories, with no data-fetching, no `services/*` import, no direct API/network access. It sits in the same "packages" architectural tier as `packages/database`, `packages/types`, `packages/validation`, `packages/config`, `packages/utils`, `packages/events`, `packages/observability`, and `packages/auth-client`, but — uniquely among them — is intended to be imported by `apps/web` and `apps/admin` directly (ARCHITECTURE.md §2.1's existing "packages consumed by apps" pattern). No other package in that tier should import it: `packages/ui` pulls in React, Radix, and (eventually) a real component tree, none of which belongs in a Node service's or a data-layer package's own dependency graph.

**Current package enumeration (re-verified this pass against the actual `packages/` directory listing):** `database`, `types`, `validation`, `config`, `utils`, `events`, `observability`, `auth-client`, `ui`. `packages/ui`'s only internal runtime dependency is `@linguaai/observability` (for its `ErrorBoundary`'s existing Sentry-reporting path, inherited from E1). It has **no** dependency on `packages/validation`: form components accept pre-parsed error strings as props (`error?: string`), not Zod schema objects, so no import is needed — deliberately, since pulling Zod into every client bundle for a component that only needs to render a string would work against §15's bundle-size discipline. This is a considered divergence from DESIGN_SYSTEM.md §4's Forms-row text ("wired to `packages/validation` Zod errors"), which described the outcome (validation errors reach the form), not the mechanism (a direct import) — T5's deliverables include a one-line DESIGN_SYSTEM.md §4 amendment recording this, so the canonical doc and the shipped design agree, per CLAUDE.md's "a PR changing an architecture contract updates the corresponding doc" rule. `packages/ui → packages/auth-client` is explicitly disallowed in both directions — the most plausible real accidental violation, since both are client-side and consumed by the same two apps.

### 6a. Dependency direction — the rule, why it currently doesn't work, the fix, and how the fix is rolled out without breaking CI

**What the rule needs to guarantee:** `packages/ui` is never imported by any other `packages/*` member or by any `services/*` member (it should only ever be imported by `apps/*`), and `packages/ui` itself never imports from `apps/*` or `services/*`.

**Current state, re-verified this pass by reading `eslint.config.js` directly:** the file declares `apps`, `packages`, and `services` as coarse, directory-tier element types (`apps/*`, `packages/*`, `services/*`, each in `folder` mode), plus `web-feature`/`admin-feature` for intra-app feature folders. There is no `ui-package` element type and no rule distinguishing `packages/ui` from any other member of the `packages` tier — `{ from: 'packages', allow: ['packages'] }` permits any package to import any other package, `packages/ui` included. `git diff -- eslint.config.js` against the repository's current tracked state is empty; this document proposes a change, it does not apply one.

**Root cause of why simply adding a `ui-package` rule is not enough — traced this pass from the installed plugin's own source (`eslint-plugin-boundaries@4.2.2`, matching `package.json`'s `^4.2.2`), not from either prior review's prose:**

`eslint-plugin-boundaries` computes a "project path" for every linted file and every import by stripping a _root path_ prefix from the absolute filesystem path (`src/core/elementsInfo.js`'s `projectPath()`). That root path defaults to `process.cwd()` when the `boundaries/root-path` setting is unset, which it is today. Under `turbo run lint`, each workspace's `lint` script (`eslint .`) runs with **cwd set to that package's own directory**. For a file _inside_ the linted package, the cwd-prefix strip succeeds and produces a path relative to the _package itself_ (e.g. `packages/database/src/index.ts`, linted with cwd `packages/database`, becomes the string `src/index.ts`). That string matches no configured element pattern (`apps/*`, `packages/*`, `services/*` all expect a leading tier segment), so the file's own element type resolves to `null`. With the linting file itself unclassified, `boundaries/element-types` — which checks the _importing_ file's type — produces no violation for **any** import in that file, regardless of what it imports. This is true of every existing rule today, not only a hypothetical new one: it means `turbo run lint`'s per-package fan-out currently does not evaluate real per-package source against any boundary rule at all. The only place boundary rules are currently exercised against real content is `scripts/verify-boundary-lint.mjs`'s eight fixture-file checks, each invoked via an explicit path from the repository root (where `process.cwd()` correctly resolves to the repo root and the strip succeeds).

**The fix — one new setting, computed from the config file's own location so it is invocation-cwd-independent:**

```js
import path from 'node:path';
import { fileURLToPath } from 'node:url';
const REPO_ROOT = path.dirname(fileURLToPath(import.meta.url)); // eslint.config.js's own directory
```

```js
settings: {
  'boundaries/root-path': REPO_ROOT,
  // ...
}
```

**Second, independent, pre-existing defect fixed in the same change — not introduced by this pass, simply never exercised against a nested real import before now:** the current `boundaries/entry-point` rule's `allow: '*'` pattern does not match nested paths — `*` in micromatch (this plugin's glob engine) matches exactly one path segment, never a `/`. Importing `packages/ui/src/index.ts` (an ordinary, already-real import shape) computes an internal path of `src/index.ts` — two segments — against `{ target: [...], allow: '*' }`, and fails. The corrected pattern is `allow: '**'` (any depth).

**Third, corrected element-pattern granularity for the new `ui-package` type:** the pattern must be `packages/ui`, not `packages/ui/*`. In `folder` mode the plugin expands a pattern to `<pattern>/**/*`; `packages/ui/*` becomes `packages/ui/*/**/*`, which requires at least one subdirectory between `packages/ui` and the matched file — a file directly at the package root (`packages/ui/package.json`, `packages/ui/vitest.config.ts`) would not match and would fall through to the generic `packages/*` type, splitting one package across two element types. `packages/ui` (no trailing `/*`) expands to `packages/ui/**/*`, matching everything under the package including root-level files, as one element.

**Full corrected settings block — this is a T2 deliverable; it is not applied to the repository by this document:**

```js
'boundaries/elements': [
  { type: 'web-feature', pattern: 'apps/web/src/features/*', mode: 'folder' },
  { type: 'admin-feature', pattern: 'apps/admin/src/features/*', mode: 'folder' },
  { type: 'ui-package', pattern: 'packages/ui', mode: 'folder' },
  { type: 'apps', pattern: 'apps/*', mode: 'folder' },
  { type: 'packages', pattern: 'packages/*', mode: 'folder' },
  { type: 'services', pattern: 'services/*', mode: 'folder' },
],
```

```js
'boundaries/element-types': ['error', {
  default: 'disallow',
  rules: [
    { from: 'apps', allow: ['packages', 'ui-package'] },
    { from: 'services', allow: ['packages'] },
    { from: 'packages', allow: ['packages'] },
    { from: 'ui-package', allow: ['packages'] },
    { from: 'web-feature', allow: ['packages', 'ui-package', 'web-feature'] },
    { from: 'admin-feature', allow: ['packages', 'ui-package', 'admin-feature'] },
  ],
}],
'boundaries/entry-point': ['error', {
  default: 'disallow',
  rules: [
    { target: ['apps', 'packages', 'services', 'ui-package'], allow: '**' },
    { target: ['web-feature', 'admin-feature'], allow: 'index.ts' },
  ],
}],
```

**This specification (the settings block above) was executed this pass, not only written.** A temporary configuration replicating it exactly was run via `eslint --config` against real repository files — an existing, genuine import (`apps/web/src/app/login/page.tsx`, which imports `@linguaai/ui`), from both the repository root and from inside `apps/web`'s own directory (zero errors both times); a throwaway fixture in `packages/database` importing `packages/ui` (correctly caught: `No rule allowing this dependency was found. File is of type 'packages'. Dependency is of type 'ui-package'  boundaries/element-types`); and a root-level file inside `packages/ui` (`vitest.config.ts`, correctly classified as `ui-package`, not split off into the generic `packages` type). The fixture file and the temporary config overlay were removed before this pass concluded; `git status`/`git diff` against tracked files show no residual change. This confirms the _rule specification itself_ is correct — this is the one part of F-C1's history that has now been independently verified sound by two separate reviewers' own execution as well as this pass's.

**What is not yet solved by the rule alone — and what the second remediation pass got wrong by not testing this:** applying the rule above verbatim, and then running `eslint .` (exactly as `turbo run lint` does) inside `apps/web`, encounters `apps/web/src/features/__boundary_fixture_b__/deep-violator.ts` — an **existing, pre-existing (not created by E3) fixture from ADR-015/E1 Part 12**, deliberately written to violate the intra-app `web-feature` entry-point rule, and used today by `scripts/verify-boundary-lint.mjs`'s check "Intra-app frontend: cross-feature deep import (violation)" (invoked via an explicit path from the repository root, where it already correctly fails). That fixture sits inside `apps/web`'s own `src/` tree. Today, `apps/web`'s own `eslint .` does not catch it, because of the exact root-path bug this section fixes — the violation is real but invisible to per-package lint. Once `boundaries/root-path` is fixed, `apps/web`'s own `eslint .` correctly classifies that file for the first time — and correctly reports the violation it was always meant to represent. Since the fixture is permanent (it exists specifically so `verify-boundary-lint.mjs` always has something real to catch), this means `apps/web`'s own `eslint .` — and therefore `turbo run lint`, and therefore `pnpm lint`, and therefore the CI lint job — would fail on every single run, forever, the moment the root-path fix lands.

**This was verified by direct execution this pass, not inferred:** with the root-path fix applied via a temporary `ESLINT_PLUGIN_BOUNDARIES_ROOT_PATH` environment-variable override (so no tracked file was touched), running `eslint .` with cwd set to `apps/web` reports exactly the fixture's intended violation, with no other errors anywhere else in `apps/web`'s real source. Confirmed clean otherwise: a full sweep of the corrected spec across all real source in `apps`, `packages`, and `services` (256 files) produces exactly the two pre-existing, deliberately-violating fixture files (this one, and its `packages/__boundary_fixture__`/`apps/__boundary_fixture__` siblings, which are **not** workspace members and are therefore never touched by any package's own `eslint .`) and nothing else.

**The fix this requires, as a T2 deliverable (not yet applied):**

1. **`apps/web/package.json`'s `lint` script changes from `eslint .` to `eslint . --ignore-pattern 'src/features/__boundary_fixture_*/**'`.** `--ignore-pattern` is an additive, invocation-time-only exclusion — it does not touch `eslint.config.js`'s shared, repo-wide `ignores` array (which would also hide the fixture from `verify-boundary-lint.mjs`'s explicit-path invocation, since a flat-config global-ignores entry is skipped even when a file is named explicitly on the command line). `verify-boundary-lint.mjs` invokes `eslint <exact path> --no-warn-ignored` directly and does not pass `--ignore-pattern`, so its check of this same fixture is unaffected and continues to catch the violation exactly as it does today. No other workspace member has an equivalent pre-existing fixture inside its own source tree (confirmed this pass: `apps/admin/src/features/` contains no `__boundary_fixture__` directory of any kind), so `apps/admin`'s `lint` script needs no change.
2. **The new inter-package violation fixture this rule needs (to prove `packages/database → packages/ui` is actually caught, mirroring the existing `packages/__boundary_fixture__` pattern) must be placed in the existing, already-non-workspace-member location — `packages/__boundary_fixture__/` — not inside `packages/database`'s own source tree.** `packages/__boundary_fixture__` has no `package.json` of its own, so it is not a pnpm workspace member and `turbo run lint` never fans out into it; it is scanned only by `verify-boundary-lint.mjs`'s explicit-path invocation, exactly like the two fixtures already living there today. Placing the new fixture inside `packages/database` (as an earlier draft of this rule's rollout plan considered) would reproduce the identical `pnpm lint`-breaking problem this section just diagnosed, one package later. The new fixture file must use a **relative import** (`../ui/src/index.ts`-style, matching the two existing ADR-015 fixtures' own pattern) rather than the bare package specifier `@linguaai/ui` — a bare specifier is not resolvable from `packages/__boundary_fixture__`'s location under pnpm's isolated `node_modules` layout (it has no `node_modules` of its own), so the plugin would treat it as an unresolvable external import and report nothing, silently defeating the check.
3. **`scripts/verify-boundary-lint.mjs` gains one new check pair** (violation: the new fixture at `packages/__boundary_fixture__/` importing `packages/ui`, expect `boundaries/element-types`; control: the real, already-existing `apps/web/src/app/login/page.tsx` importing `@linguaai/ui`, expect pass) — extending the existing eight-check pattern, not replacing it.

**None of items 1–3 above have been applied to the repository by this document.** They are stated here as the exact, verified-necessary shape of T2's work, arrived at by actually running the corrected rule against real files and observing what breaks — the discipline the third review found missing from the second pass specifically in this section.

**Dependency graph this rule enforces, once T2 lands:** Forbidden: `packages/{database,types,validation,config,utils,events,observability,auth-client} → packages/ui`; `services/* → packages/ui`; `packages/ui → apps/*`; `packages/ui → services/*`. Allowed: `apps/{web,admin} → packages/ui`; `packages/ui → packages/observability`.

### 6b. Package resolution — the `@ui/*` alias, stated as required implementation work, not as already solved

**Why an alias is needed at all.** `packages/ui`'s Shadcn CLI configuration (`components.json`) declares every generated-component alias under the `@/` prefix (`"utils": "@/lib/cn"`, `"ui": "@/components/ui"`, `"components": "@/components"`, `"lib": "@/lib"`, `"hooks": "@/hooks"`) — the CLI's own default convention. `packages/ui/tsconfig.json` today declares **no** `baseUrl`/`paths` of any kind (confirmed this pass by reading the file directly: it extends `tsconfig.base.json`, which also declares none), so a `shadcn add`-generated file's `@/lib/cn` import cannot resolve at all inside `packages/ui`'s own type-check today. That much is a self-contained problem inside `packages/ui`, and was the shape of fix a first pass at this alias addressed.

**Why that is not sufficient, verified this pass by direct execution — the exact gap H-1 named.** Both `apps/web/next.config.ts` and `apps/admin/next.config.ts` declare `transpilePackages: ['@linguaai/ui', '@linguaai/observability', '@linguaai/auth-client']` (confirmed by reading both files this pass — an E1 decision, so `packages/ui` ships as raw TS/TSX source with hot-reload, not a pre-built `dist/`). `transpilePackages` means Next compiles `packages/ui`'s source **as part of the consuming app's own compilation unit** — both for the bundler and for TypeScript's own program. Both `apps/web/tsconfig.json` and `apps/admin/tsconfig.json` (confirmed by reading both files this pass) declare `"paths": { "@/*": ["./src/*"] }` and nothing else. TypeScript resolves `paths` against the _program's own config_, not per source file — so once `packages/ui`'s source is part of `apps/web`'s compilation, every `@/`-prefixed import inside it resolves against `apps/web`'s own `@/*` → `./src/*` map, not `packages/ui`'s.

**Demonstrated, this pass, with a real `tsc` invocation (not asserted):** a temporary probe file was added inside `packages/ui/src/` importing `@ui/lib/cn` (the eventual, corrected alias — chosen specifically because it is not `@/`, to avoid this exact collision) and then type-checked as part of `apps/web`'s own program:

```
$ tsc -p apps/web/tsconfig.json --noEmit
packages/ui/src/__probe__.ts(3,20): error TS2307: Cannot find module '@ui/lib/cn' or its corresponding type declarations.
```

The probe file was removed after the test; `git status` confirms no residual change. This fails for exactly the reason stated above: `apps/web/tsconfig.json` has no `@ui/*` entry in its own `paths`. A `packages/ui`-only fix (adding `@ui/*` solely to `packages/ui/tsconfig.json`) would make `packages/ui`'s own standalone `tsc -p packages/ui/tsconfig.json --noEmit` pass, while leaving `apps/web`'s and `apps/admin`'s own `typecheck` scripts — and `next build`'s own internal type-check, which uses the same program — broken on the same import. This is the precise mechanism by which a prior pass's `@ui/*` design, naming only `packages/ui/tsconfig.json`, `.storybook/main.ts`, and `vitest.config.ts`, would still fail: those three files govern `packages/ui`'s own standalone tooling, none of which is what actually compiles `packages/ui`'s source when `apps/web`/`apps/admin` build it.

**A second, independent resolver in each consuming app was still missing from that file list — found by the fourth review, and independently reproducible.** Both apps' own test suites (`apps/web`'s `login/page.test.tsx` and its siblings; `apps/admin`'s equivalents) exercise components that, via `transpilePackages`, pull `packages/ui`'s raw source into each app's own Vitest run — a **third** resolver, distinct from both the TypeScript program (fixed by the `tsconfig.json` entries) and the Next.js bundler (fixed by the `next.config.ts` entries), because Vitest resolves module specifiers through Vite's own resolver, configured per-app in each app's own `vitest.config.ts`. Neither `apps/web/vitest.config.ts` nor `apps/admin/vitest.config.ts` declares a `resolve.alias` for `@ui`, and neither inherits one from `packages/ui/vitest.config.ts` (each app's Vitest run is a fully separate process with its own config). Without this, `vitest run` in either app fails with `Failed to resolve import "@ui/..."` the first time a `packages/ui` component under test uses the alias — the identical failure class as the `tsc` and `next build` gaps above, one resolver later.

**Resolvers checked individually rather than assumed as a group:**

- **Jest** — not used by either app (both `apps/web/package.json` and `apps/admin/package.json` declare `"test": "vitest run --coverage"`, confirmed this pass), so there is no second test-runner resolver to account for.
- **TypeScript project references** — neither app's `tsconfig.json` declares a `"references"` array or `"composite": true`; the whole alias problem exists precisely because these apps use `paths`-based resolution rather than project references, and fixing that architecture is out of this epic's scope, not a gap in this alias fix.
- **ESLint's own import resolution — corrected this pass, closing the fifth review's N-2. A prior version of this paragraph claimed ESLint's resolver "delegates to each linted file's own nearest `tsconfig.json`," presented as verified. That claim is wrong, and the fifth review disproved it by reading the installed resolver's own source.** `eslint-import-resolver-typescript@3.10.1`'s `initMappers()` (the version this repository has installed) determines which `tsconfig.json` to use from `options.project`; when `import/resolver` is configured as the bare boolean `{ typescript: true }` (this repository's current, unmodified configuration), `options` is `true`, `options.project` is `undefined`, and the resolver falls back to searching upward from **`process.cwd()`** — not from the file being linted. **CURRENT LIMITATION, true today and unaffected by anything in this document:** under `turbo run lint` (cwd = the package directory) this happens to work, because each package's own cwd-nearest `tsconfig.json` is the one T3 gives an `@ui/*` entry. But `eslint.config.js`'s repository root has **no `tsconfig.json`** (only `tsconfig.base.json`, confirmed by listing the root directory) — so any **root-invoked** ESLint run (`scripts/verify-boundary-lint.mjs`'s `pnpm exec eslint <path>` calls, the root `pnpm lint` script, and any pre-commit hook invoking `eslint` from the repo root) resolves no tsconfig at all for a `@ui/*` specifier, and `eslint-plugin-boundaries` silently treats the unresolvable import as external, evaluating no rule against it. This is a **real, silent enforcement blind spot** for exactly the `@ui/*` alias this epic introduces, at exactly the root-invoked call sites the Architecture quality gate (§21) names as its evidence. **FUTURE STATE, required as a corrected T2 deliverable, not yet applied:** the `import/resolver` setting must be changed from the bare boolean `{ typescript: true }` to an explicit form naming the workspace's tsconfig files (e.g. `{ typescript: { project: ['tsconfig.base.json', 'apps/web/tsconfig.json', 'apps/admin/tsconfig.json', 'packages/*/tsconfig.json', 'services/*/tsconfig.json'] } }`, or an equivalent glob the installed resolver version supports) so that root-invoked lint resolves `@ui/*` the same way per-package-invoked lint does. This is a change to `eslint.config.js`'s `import/resolver` setting specifically — a narrow, corrective addition to T2's already-planned `eslint.config.js` changes (§6a), not a new architectural decision, and it is **not applied to the repository by this document**, consistent with every other T2/T3 item in this section.

T3's acceptance evidence gains a fourth item, corrected this pass: "a root-invoked `eslint <path>` run (matching `verify-boundary-lint.mjs`'s own invocation shape) against a file using the `@ui/*` alias resolves and evaluates correctly, not silently as an unresolved external import" — added specifically because the prior three assertions (`typecheck`, `next build`, `pnpm test`) do not exercise ESLint at all, and this gap is invisible to all three.

**Brand tokens vs. Action tokens — a semantic-model correction this pass, closing the sixth review's M-3 (Medium).** The tokens above were originally named `--color-secondary-text`/`--color-secondary-solid`, on the reasoning that "AI-purple is the library's second brand color after primary." That name collides with an unrelated concept: `packages/ui/src/components/button.tsx` ships **today** with a `secondary` Button _variant_ (`border-neutral-300 bg-neutral-100 text-neutral-900 dark:bg-neutral-800 dark:text-neutral-50` — a neutral, non-purple treatment), and §12.2 requires Buttons to have "Primary, secondary, ghost, destructive, icon-only" variants. A semantic tier that calls AI-purple "secondary" invites exactly the misuse DESIGN_SYSTEM.md §2 prohibits outright: **"Purple is reserved exclusively for AI-originated content/actions. It must never be reused for generic decoration."** A `secondary` Button variant is generic decoration by definition — it is not AI-originated content.

The fix separates two categories this document previously conflated under one naming scheme:

- **Brand tokens** — anchored to a specific, meaning-bearing brand color, usable only for what that color signals. AI-purple is a brand token: `--color-ai` (anchor), `--color-ai-text`, `--color-ai-solid` (both renamed this pass). Danger, warning, success, info, and accent are also brand-adjacent semantic-state tokens in this sense (each means a specific thing — an error, a caution, a success, informational content, real-time communication — and is not freely substitutable for another).
- **Action tokens** — used for a button/control's _role_ (primary emphasis, secondary emphasis, low-emphasis/ghost, destructive), independent of brand color. `--color-primary-solid` doubles as both a brand token (the Lingua Blue anchor) and the `primary` action's fill, which is fine because DESIGN_SYSTEM.md §2 assigns primary blue to exactly that role ("Primary actions, links, brand marks"). The `secondary` and `ghost` action roles have **no brand color assigned to them at all** — they are neutral, structural button treatments, and DESIGN_SYSTEM.md never says otherwise.

Confirmed this pass by reading `packages/ui/src/styles/tokens.css` directly: `--duration-micro: 150ms`, `--duration-standard: 250ms`, `--duration-celebratory: 600ms` are already present, already correctly within DESIGN_SYSTEM.md §2.2's stated ranges, and already exposed via `@utility duration-micro`/`duration-standard`/`duration-celebratory` blocks (not `@theme`, since Tailwind v4 has no `--duration-*` theme namespace — the shipped file's own comment states this reasoning accurately). **This document now specifies no change to these three values** — T1's `tokens.css` rewrite carries them forward unchanged, alongside the `@media (prefers-reduced-motion: reduce)` override (collapsing all three to nearly 0) and a `useReducedMotion` hook backed by a `matchMedia` listener, both of which are genuinely new T1 work. `packages/ui/vitest.setup.ts` today wires only RTL cleanup and jest-dom (confirmed by reading the file); a `matchMedia` stub is a T1 test-setup deliverable, since jsdom does not implement it and the hook's unit test needs both media-query states.

**Locale-aware line-height:** target-language content (rendered with a `lang` attribute other than the UI's own locale) gets a line-height override on top of the type scale (§12.1a), not a competing scale — some target scripts need more vertical breathing room than the UI chrome's own Latin-script default.

**Theme-application mechanism.** Tailwind v4's plain `@theme` block emits static custom properties resolved once at build time; overriding a property inside a `[data-theme="dark"]` selector does not retroactively change utility classes already generated from a non-`inline` `@theme` block. The pattern used for every dual-valued token in this document is `@theme inline` paired with raw values declared separately in `:root` and `[data-theme="dark"]`:

```css
:root {
  --raw-color-primary-text: #2563eb;
}
[data-theme='dark'] {
  --raw-color-primary-text: #60a5fa;
}
@theme inline {
  --color-primary-text: var(--raw-color-primary-text);
}
```

`@theme inline` tells Tailwind to reference the custom property at _runtime_ (via `var()`) rather than substitute its value at build time, so a utility like `text-primary-text` correctly re-resolves whenever `[data-theme="dark"]` is toggled on the document root — what makes Storybook's theme-switcher and any future in-app theme toggle actually work. T1's deliverable is the full `tokens.css` rewrite using this pattern for every token above, not merely the value tables.

### 12.1a Typography scale — redesigned this pass, closing the sixth review's P6-1 (HIGH)

### 12.4 Component contracts

**Contract template**, applied to every component: Props (name, type, required/optional, default) · Variants · Sizes · States (default/hover/focus/active/disabled/loading/error/empty as applicable) · Slots (children/render-prop surface) · Keyboard interaction model · ARIA pattern (referencing the relevant ARIA Authoring Practices pattern where one exists) · Responsive behavior · Theme behavior (light/dark-specific notes, if any) · Composition rules · Testing requirements.

**Five components specified in full** — four the fourth review identified as highest divergence-risk if left as bare names, plus the AI thinking/typing distinction, added this pass (§12.4, below the four) closing the sixth review's M-2:

**Dashboard grid/widget primitive.**

- Props: `children: ReactNode`, `columns?: { mobile: number; tablet: number; desktop: number }` (default `{1,2,3}`), `gap?: 'sm' | 'md' | 'lg'` (default `'md'`).
- Composition rule: children are accepted as `ReactNode`, permitting all legitimate JSX patterns (conditional rendering, fragments, `null`). A **development-mode-only runtime check** (`process.env.NODE_ENV !== 'production'`) walks direct children via `React.Children.forEach` and calls `console.warn` if a resolved child's `type` is neither `Widget` nor `React.Fragment`. **Stated limitation, deliberate:** the check does not recurse into a `Fragment`'s own children — a `<>` wrapping non-`Widget` content passes the shallow check silently. This is an accepted gap in the dev-mode lint's coverage, not a claim of exhaustiveness; it exists to catch the common case (a stray `<div>` dropped directly into the grid) without producing false positives on the equally common case (a conditionally-rendered `Widget` wrapped in a fragment for a `key` or multiple-return reason). It fires only in development/Storybook/tests and is dead-code-eliminated in production — a development-time lint, not a compile-time guarantee (TypeScript's structural typing makes a true compile-time guarantee unavailable here: `ReactElement<any>` is assignable to any narrower element-prop type, so a type annotation alone cannot exclude an arbitrary element).
- Testing: unit (renders 1/2/3-column layouts at each breakpoint token; dev-mode warning fires for a non-`Widget` direct child; does not fire for a `Widget` wrapped in a conditional or fragment).

**Voice-session state machine (presentational).**

- Props: `state: 'listening' | 'processing' | 'speaking' | 'idle' | 'error'`.
- Transitions: `idle → listening`, `listening → processing`, `processing → speaking`, `speaking → idle`, `speaking → listening` (barge-in), `* → error` (any state may fail), `error → idle` (dismissed/retried).
- Error behavior: `error` is a first-class member of the `state` union (not a separate flag), rendered with a distinct visual treatment and an `aria-live="assertive"` announcement (distinct from the other four states' `aria-live="polite"` streaming text).
- Testing: unit (all 5 states render distinct output; every transition above, including both `error` transitions, exercised).

**Admin data table.**

- Props: `columns: ColumnDef[]`, `data: T[]`, `sortable?: boolean`, `pageSize?: number`, `loading?: boolean`, `emptyMessage?: string`, `error?: { message: string; onRetry?: () => void }`, `disabled?: boolean`.
- States: default, loading (skeleton rows, matching the loaded rows' dimensions per §15's CLS rule), empty (`emptyMessage`), error (renders the error slot in place of rows, matching the empty-state visual pattern), disabled (sort headers and row-selection checkboxes become non-interactive with `aria-disabled`; existing row data remains visible — e.g. viewing a list during a bulk operation in progress).
- ARIA: `aria-sort` on sortable column headers; pagination changes announced via a polite live region.
- Testing: unit (all six states render distinctly) + interaction (sort toggles, page navigation, keyboard row focus).

**Combobox.**

- Props: `options: T[]`, `value`, `onChange`, `loading?: boolean`, `emptyMessage?: string`, `error?: string`, `disabled?: boolean`.
- ARIA pattern: full ARIA 1.2 combobox — `role="combobox"`, `aria-expanded`, `aria-controls`, `aria-activedescendant` (focus never leaves the input), typeahead filtering, Escape closes without clearing the current value.
- States: default, loading, empty (no results — distinct from `error`, since a fetch failure and a genuinely empty result set are different UX), error (a fetch failure, rendered in place of the option list), disabled.
- Testing: unit (all states) + interaction (typeahead filters the option list; arrow-key navigation moves `aria-activedescendant`, not DOM focus; Escape behavior).

**"Thinking" vs. "typing" state distinction — added this pass, closing the sixth review's M-1 (Medium). Required by DESIGN_SYSTEM.md §4's AI-chat row and listed in this document's own §12.2, but previously reduced to a bare noun with no row anywhere in this section.**

- **Purpose.** A presentational indicator distinguishing two distinct AI-response phases that read identically if unspecified: "thinking" (the model is reasoning/retrieving before any output exists) and "typing" (tokens are actively streaming, handled by the separate streaming-token renderer contract above). Without this distinction, a user has no signal during the "thinking" phase that anything is happening at all — the streaming renderer's own contract only covers the phase after the first token arrives.
- **Visual difference.** "Thinking": a static or gently-pulsing indicator (three dots, a subtle shimmer) with no token content yet rendered — deliberately _not_ a spinner, to avoid implying indeterminate-length blocking work when a partial response may arrive at any moment. "Typing": no separate indicator — the streaming-token renderer's own append-only text _is_ the typing signal, per its own contract above.
- **Props:** `phase: 'thinking' | 'typing' | 'idle'` (a sibling state to the streaming renderer's own `content` prop, not a replacement for it — `typing` is this component rendering nothing while the streaming renderer owns the visible text).
- **Accessibility behavior / ARIA live region:** `aria-live="polite"` on the thinking indicator's container, with a single, one-time text announcement ("AI is responding") on entering `thinking` — not a repeated or per-pulse announcement, which would spam a screen reader for the entire thinking duration. The live region is removed from the DOM (not merely hidden) on transition to `typing`, handing announcement responsibility to the streaming renderer's own already-specified `aria-live="polite"` region, so the two components never announce simultaneously.
- **Reduced-motion behavior:** the pulsing/shimmer animation is subject to the same `prefers-reduced-motion` override as every other motion token in §12.1 — reduces to a static (non-animated) indicator, never removed entirely, matching §12.1's stated principle that reduced motion degrades to a static equivalent rather than disappearing.
- **Loading-state behavior:** `thinking` _is_ this component's loading state — there is no further loading sub-state. Dimensioned to avoid CLS per §15's rule (a fixed-height container, not one that grows when the indicator appears).
- **Testing requirements:** unit (all three `phase` values render distinct output; the live-region announcement fires exactly once per `thinking` entry, not per render); interaction (the transition from `thinking` to `typing` removes the thinking live region and does not double-announce).
- **Boundary compliance:** presentational only, per ADR-006 and §13 — the component receives `phase` as a prop from its consumer and makes no inference about _why_ the AI is thinking or typing, no network access, no `services/*` import, consistent with every other component in this category.

**Composite Radix-primitive widgets — added this pass, closing the sixth review's M-2 (Medium). §6c installs DropdownMenu, Popover, Tabs, and Tooltip with named consumers, but none had a keyboard/ARIA/screen-reader contract; Tabs is separately named in §12.5 as a composite-widget accessibility risk (roving-tabindex correctness) and is given the most detail below for that reason.**

**Tabs — the highest-risk of the four, given special attention per §12.5's own named blind spot.**

- **Keyboard interaction:** roving `tabindex` across the tab list (only the active tab is in the natural Tab order; `0` on the active tab, `-1` on all others) — the exact pattern §12.5 names as an axe blind spot, specified here rather than left implicit. Arrow-Left/Arrow-Right move focus and selection between tabs (Home/End jump to first/last); the associated tabpanel receives focus via `Tab` from the active tab, not automatically on arrow-key selection (matching the ARIA Authoring Practices "manual activation" tabs pattern, chosen over "automatic activation" so arrow-key browsing does not trigger a panel's own side effects on every keystroke).
- **Focus management:** focus never silently leaves the tablist during arrow-key navigation; moving to a tabpanel is always an explicit user action (`Tab` or click).
- **ARIA:** `role="tablist"` on the container, `role="tab"` + `aria-selected` + `aria-controls` on each tab, `role="tabpanel"` + `aria-labelledby` on each panel.
- **Screen-reader expectations:** tab count and position are announced via native `role="tab"` semantics (no custom live region needed); this is a genuine, real interaction pattern, not merely a visual toggle, so it is added to the mandatory manual-verification list below.
- **Testing approach:** unit (roving-tabindex value correct after every selection change) + interaction (arrow-key navigation, Home/End, manual tabpanel focus) + **manual screen-reader verification (new mandatory-check addition, see the corrected count below)**.

**DropdownMenu.**

- **Keyboard interaction:** `Enter`/`Space`/`ArrowDown` on the trigger opens the menu and moves focus to the first item; `ArrowUp`/`ArrowDown` move focus between items; `Escape` closes and returns focus to the trigger; typeahead (typing a letter jumps to the next matching item) inherited from Radix's own implementation, not reimplemented.
- **Focus management:** focus moves into the menu on open, returns to the trigger on close (Escape or item selection) — a focus-restoration case, matching §12.5's own stated general requirement.
- **ARIA:** `role="menu"` + `role="menuitem"` per Radix's default primitive output; `aria-expanded` on the trigger.
- **Screen-reader expectations:** menu open/close state and item count are conveyed by native menu semantics.
- **Testing approach:** unit (open/close state) + interaction (keyboard open/navigate/select/dismiss, focus-restoration to trigger on Escape).

**Popover.**

- **Keyboard interaction:** `Escape` closes and returns focus to the trigger; content inside the popover is reachable by `Tab` in document order (a popover, unlike a menu, has no imposed roving-focus model — its content is arbitrary).
- **Focus management:** same focus-restoration requirement as DropdownMenu.
- **ARIA:** `aria-haspopup` + `aria-expanded` on the trigger; the popover content itself has no imposed role (its content determines its own semantics, per the ARIA Authoring Practices' own guidance for popovers with heterogeneous content).
- **Testing approach:** unit (open/close) + interaction (Escape-to-close and focus restoration).

**Tooltip.**

- **Keyboard interaction:** appears on keyboard focus of its trigger (not only on hover — a hover-only tooltip is unreachable by keyboard, a DESIGN_SYSTEM.md §5 violation by omission), dismisses on `Escape` or on the trigger losing focus.
- **Focus management:** does not itself receive focus (an inspectable, non-interactive annotation of its trigger).
- **ARIA:** `aria-describedby` linking the trigger to the tooltip content — not `aria-label`, which would replace rather than supplement the trigger's own accessible name.
- **Testing approach:** unit (appears on focus, not only hover) + interaction (Escape dismissal).

Neither Tabs' nor DropdownMenu's, Popover's, nor Tooltip's owning task changes — all four remain T3 installs (§6c) with their consuming component's own task (T5 Forms/T8 Navigation/T14 Admin, per §6c's named consumers) responsible for the Storybook stories and tests these contracts require. Tabs is added to the mandatory-manual-screen-reader-verification list below, since its own contract identifies a genuine, non-visual interaction risk (roving-tabindex correctness) meeting the document's own stated inclusion criterion — bringing the total from seven to **eight**.

### 12.5 Layered accessibility strategy

Automated tooling (Storybook's `@storybook/addon-a11y`, wired into CI) is **necessary and not sufficient**. Six layers apply:

1. **Automated-structural** — axe, every story, every theme.
2. **Automated-lint** — `eslint-plugin-jsx-a11y` at write time, complementing axe's render-time checks.
3. **Automated-contrast** — a Vitest test iterating the full token × surface grid in §12.1 (all four surfaces, both themes, both the 4.5:1 and 3:1 floors as applicable per token role) — not a single-background check.
4. **Keyboard-scripted** — a `@storybook/test-runner` interaction test per component exercising its documented keyboard model (§12.4).
5. **Screen-reader-manual** — a human pass with a real screen reader (NVDA or VoiceOver), required for the eight named high-risk components (§12.4), each with a `UI_UX_REVIEW_TEMPLATE.md` §7 instance as evidence.
6. **Visual** — Storybook's own rendered output, reviewed as part of ordinary PR review.

Known axe blind spots this strategy exists to cover: focus order and restoration after a modal/overlay closes; live-region announcement timing and verbosity; roving-tabindex correctness in composite widgets (tabs, comboboxes). `aria-invalid`/`aria-describedby` wiring between `FormField` and its error text is a T5 deliverable, not left implicit.

## 18. Deployment — Storybook hosting

**Mechanism: CloudFront Function + CloudFront KeyValueStore (KVS), per ADR-026 (docs/DECISIONS.md).** A prior design (a CloudFront Function reading a credential directly from AWS Secrets Manager) cannot execute: CloudFront Functions run in a deliberately restricted, sub-millisecond runtime (`cloudfront-js-2.0`) with no network access, no filesystem access, and no AWS SDK — confirmed against the runtime's documented capability set. The corrected mechanism pairs a CloudFront Function with a CloudFront KeyValueStore, a store purpose-built to be read from exactly this runtime (`cloudfront-js-2.0` includes a `kvs()` read API). Terraform — which has full AWS SDK/network access at `apply` time, unlike the edge function at request time — resolves the real credential from Secrets Manager and writes its salted hash into the KVS; the function compares the request's `Authorization: Basic` header against the KVS-stored hash, entirely within the runtime's actual capabilities.

- **Authentication flow:** request arrives → CloudFront Function fires on `viewer-request` → reads the KVS-stored hash → compares against the request's `Authorization` header → missing/mismatched header returns `401` with a `WWW-Authenticate` challenge before the origin is reached; a matching header allows the request through to the S3 origin.
- **Authorization model:** a single shared credential, not per-user — an explicit, accepted v1 limitation (RISK_REGISTER.md R-56), appropriate for a low-sensitivity internal preview tool with synthetic-only fixture data (§14).
- **Secret management, including the salt — specified this pass, closing the sixth review's P6-8 (Low): the salt's source, rotation, ownership, and failure handling were previously unstated.** The raw credential lives in AWS Secrets Manager (the durable source of truth). The salt is a second, independent value — **not derived from the credential itself** — generated once by Terraform (e.g. `random_password` or an equivalent provider-native random resource) and stored as its own field in the same Secrets Manager secret, alongside the raw credential. At `apply` time, Terraform reads both the credential and the salt, computes `hash = SHA-256(salt + credential)` (the algorithm named explicitly here, not left for T17 to choose), and writes **both** the resulting hash and the plaintext salt into the KVS as two separate entries (`credential-hash`, `credential-salt`) — the CloudFront Function needs the salt to reproduce the same computation against an incoming request's `Authorization` header, and `cloudfront-js-2.0`'s `crypto` module supports SHA-256 digest computation, so the function performs the identical hash operation at request time and compares the two hashes, never comparing raw credentials. The CloudFront Function never sees the raw secret or calls Secrets Manager directly. **Rotation:** a `terraform apply` that regenerates the credential also regenerates the salt in the same operation (both are outputs of the same Terraform resource), so a rotation always produces a fresh salt/hash pair together — there is no scenario where an old salt is compared against a new credential. **Ownership:** the Security/DevOps role that owns R-56/R-65 also owns the salt as part of the same credential-rotation responsibility — it is not a separately-tracked artifact. **Failure handling:** if the KVS's `credential-salt` entry is ever absent or unreadable when the function executes, the function fails closed (treats the request as unauthenticated, returning `401`) rather than falling back to an unsalted comparison — an explicit design choice named here so T17's implementer does not have to invent the failure behavior.
- **Terraform ownership (a T17 deliverable; none of it exists in `infrastructure/` today, confirmed by reading `infrastructure/terraform/modules/edge` this pass):** an `aws_cloudfront_key_value_store` resource, an `aws_cloudfrontkeyvaluestore_key` entry populated from the secret's hash (resource names corrected this pass — a prior draft had them swapped), an `aws_cloudfront_function` resource (`cloudfront-js-2.0` runtime) implementing the check above and associated to the Storybook cache behavior's `viewer-request` event, and a new S3 origin with Origin Access Control (the `edge` module's existing distribution has no S3 origin today — its only origin is an ALB via `custom_origin_config`).
- **WAF — corrected this pass, closing the fifth review's N-8: this bullet previously opened by calling the decision "an owned open question," then two sentences later called it "a decision, not an open option" — a leftover contradiction between pass-3 framing and the pass-4 correction placed next to it.** A CloudFront distribution requires a `CLOUDFRONT`-scoped WAF ACL in `us-east-1` if it is to have one at all — the `edge` module's existing ACL is `REGIONAL`-scoped and ALB-associated, and does not cover a CloudFront distribution regardless. **This is a decision, not an open question (§25 Q4 records it as decided-by-default, revisitable): the distribution ships v1 without a distribution-scoped WAF ACL.** This is an internal, low-traffic tool behind Basic Auth, and a new WAF ACL is a real cost/maintenance addition for a threat model (volumetric/bot abuse of an internal preview site) this tool does not meaningfully present. Tracked as its own risk-register row, **RISK_REGISTER.md R-65** (added this pass — a prior pass mis-cited R-56 here, which covers the shared-credential security model, not the WAF question; the fourth review's F-6 found that mis-citation). The Security/DevOps role owner may override this default before T17 implementation; if they do, the ACL is a T17 addition, not a redesign.
- **Revocation:** a `terraform apply` rewriting the KVS entry — KVS writes propagate to edge locations within seconds. Still whole-team rotation, matching R-56.
- **Verification (T17 acceptance criteria):** a deploy-time assertion that an unauthenticated request returns `401`, failing the deploy job otherwise; `X-Robots-Tag: noindex` + `robots.txt` disallow; an S3 public-access-block assertion; PR-close teardown.
- **Teardown precedent:** `preview.yml`'s `teardown` job (not `preview-cleanup.yml`, which is a nightly App-Runner-only safety net — confirmed by reading its own header comment) is the correct PR-close precedent to extend. Both are App-Runner-specific today, so S3/CloudFront/KVS teardown is genuinely new logic either way, not a drop-in extension.
- **Local development:** no auth, `localhost` only.

**Verification-honesty note:** the mechanism above is correct against the _documented_ capability set of CloudFront Functions and CloudFront KeyValueStore (confirmed this pass: `cloudfront-js-2.0` genuinely exposes a KVS read API and a `crypto` module capable of the comparison described; the AWS provider is pinned at `5.100.0` in this repository's `.terraform.lock.hcl` files, well past the versions that introduced the relevant KVS resources, so there is no provider-version blocker). It has **not** been built, deployed, or tested — a materially different confidence level than §6a's or §12.1's fixes, which were executed against this repository's actual, current state. RISK_REGISTER.md R-64 (new, this pass) tracks that residual explicitly.
