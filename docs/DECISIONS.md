# LinguaAI — Architecture Decision Records

Status: **v1.1 — Consolidated baseline** · Last updated: 2026-08-01

This is the durable log of significant architecture decisions and their rationale. When a decision changes, add a new ADR that supersedes the old one — never silently edit history. Each ADR references the review finding or requirement that motivated it where applicable.

Format: Context → Decision → Consequences → Status.

---

### ADR-001 — Turborepo + pnpm workspaces monorepo

**Context:** LinguaAI spans 4 apps, 6 packages, and 5 services with heavy shared-type/contract needs (PRD.md's 30 modules).
**Decision:** Single monorepo, Turborepo for task orchestration/caching, pnpm workspaces for dependency management.
**Consequences:** Fast iteration and guaranteed contract consistency across frontend/backend; requires CI caching discipline to keep build times acceptable as the repo grows.
**Status:** Accepted.

### ADR-002 — Modular monolith core + targeted microservices at the edges

**Context:** 20+ MVP modules could be built as either a single monolith or full microservices from day one.
**Decision:** Core domain (identity, courses, progress, gamification, subscriptions) lives in one NestJS API (`apps/api`); only `ai-engine`, `speech-service`, `recommendation-engine`, `notification-service`, `analytics-service` are separate, justified by independent scaling, runtime isolation, or blast-radius isolation (ARCHITECTURE.md §4).
**Consequences:** Avoids premature distributed-systems tax; requires enforced internal module boundaries (dependency-graph lint) inside `apps/api` to prevent it from becoming an unmanageable monolith as modules accumulate — this enforcement is a required deliverable of Epic E1, not optional tooling.
**Status:** Accepted.

### ADR-003 — REST over GraphQL for the primary API

**Context:** Needed one contract style across web, mobile, and admin.
**Decision:** REST + JSON, shared types (`packages/types`) and Zod schemas (`packages/validation`) as the real contract enforcement mechanism; WebSocket only for real-time flows (API_GUIDELINES.md).
**Consequences:** Simpler operational model than GraphQL federation; dashboard aggregation needs are met with a thin BFF layer (ARCHITECTURE.md §6) rather than a query language.
**Status:** Accepted.

### ADR-004 — pgvector on primary Postgres for AI memory/vector search (MVP)

**Context:** AI memory retrieval (AI_SYSTEM.md) needs vector similarity search.
**Decision:** Use `pgvector` on the same Aurora Postgres instance rather than a separate managed vector DB at MVP.
**Consequences:** Avoids operating a second stateful system before scale demands it; keeps memory retrieval transactionally close to relational data. Revisit trigger: sustained p95 vector query latency degradation or index size exceeding defined thresholds, reviewed quarterly (AI_SYSTEM.md §11).
**Status:** Accepted.

### ADR-005 — Postgres Row-Level Security as the tenant-isolation enforcement mechanism

**Context:** Architecture Review Gate (2026-07-29) identified app-layer-only tenant filtering (`organizationId` scoping in application queries) as a critical cross-tenant data-leak risk — a single missed `WHERE` clause leaks Enterprise data across tenants.
**Decision:** Postgres RLS policies enforce tenant scoping at the database layer, keyed on a session variable (`app.current_org_id`) set by Prisma middleware per request, in addition to (not instead of) application-layer scoping. Full design in MULTITENANCY.md.
**Consequences:** Defense-in-depth against the exact class of bug that caused this finding; adds RLS policy maintenance overhead per new tenant-scoped table, enforced via a schema-review checklist (DATABASE.md).
**Status:** Accepted. **Resolves Architecture Review blocker #2.**

### ADR-006 — AI Gateway pattern: all model calls route through `services/ai-engine`

**Context:** Provider swaps, cost control, and safety filtering need one enforcement point (AI_SYSTEM.md §1).
**Decision:** No application code calls an LLM/STT/TTS provider SDK directly; all traffic goes through the `ai-engine`'s `ModelProvider` interface.
**Consequences:** Provider changes and safety-policy changes are configuration, not code, changes across the whole platform.
**Status:** Accepted.

### ADR-007 — Single Orchestrator agent with tool-calling handoff for multi-agent coordination

**Context:** Architecture Review Gate identified an undecided multi-agent handoff protocol as a blocker — e.g., does the Conversation Partner silently note a grammar error, hand off entirely, or ignore it?
**Decision:** One Orchestrator agent owns session state and the user-facing voice for a given session. Specialist agents (Grammar Coach, Pronunciation Coach, etc.) are invoked as **typed tools** by the Orchestrator when a defined trigger condition is met (e.g., a recurring error pattern crosses a confidence threshold), returning a structured critique object that the Orchestrator weaves into its own response — never as independent chat participants with their own turn in the conversation.
**Consequences:** Preserves one consistent voice and full memory continuity per session; bounds cost (specialist calls happen only on trigger, not by default every turn); produces a testable, structural contract (specialist tool output is schema-validated, not freeform) per TESTING.md §3. Full detail in AI_GOVERNANCE.md.
**Status:** Accepted. **Resolves Architecture Review blocker #3.**

### ADR-008 — RAG grounding is required for factual/pedagogical agent output

**Context:** Architecture Review Gate identified that Grammar Coach and Exam Coach relying on parametric LLM knowledge for grammar rules and exam rubrics is a hallucination risk that directly threatens the product's core trust claim.
**Decision:** A curated, versioned knowledge base (CEFR descriptors, grammar reference content, official exam rubrics) is retrieved and injected as grounding context for any agent response that makes a factual or scoring claim. This is architecturally distinct from the personalization memory store (AI_SYSTEM.md §4) — same retrieval infrastructure (pgvector), different collection and governance (AI_GOVERNANCE.md).
**Consequences:** Adds a knowledge-base curation and versioning workload (owned by a named linguist/pedagogy review function, AI_GOVERNANCE.md), but is treated as a blocking dependency for Grammar Coach and Exam Coach shipping (ROADMAP.md Epic E13/E19) rather than an optional enhancement.
**Status:** Accepted. **Resolves Architecture Review blocker #1.**

### ADR-009 — ECS Fargate over Kubernetes/EKS for MVP compute

**Context:** Needed container orchestration without the operational overhead of running EKS control-plane/node lifecycle with a small platform team.
**Decision:** AWS ECS Fargate for all `apps/*` and `services/*` compute.
**Consequences:** Faster path to a working, autoscaled, rolling-deploy platform; revisited only if a specific workload (e.g., self-hosted GPU inference) requires Kubernetes-specific capability (DEPLOYMENT.md §9).
**Status:** Accepted.

### ADR-010 — Domain events over point-to-point queue calls for cross-module reactions

**Context:** Architecture Review Gate identified that Gamification, Analytics, and Notifications all reacting to the same underlying occurrences (lesson completed, session ended, subscription changed) via direct point-to-point BullMQ enqueue calls creates N:M hidden coupling as consumers multiply.
**Decision:** Introduce a documented domain-event catalog (EVENT_ARCHITECTURE.md) over the same Redis/BullMQ transport — producers publish named, versioned events; consumers subscribe without the producer knowing who's listening.
**Consequences:** Adds a light event-schema-governance process but decouples module evolution — a new consumer (e.g., a future feature reacting to `LessonCompleted`) requires zero changes to the producer.
**Status:** Accepted. **Resolves Architecture Review Part 2 finding #4.**

### ADR-011 — Mandatory MFA for `ADMIN` and `ENTERPRISE_ADMIN` roles

**Context:** Architecture Review Gate identified that MFA was "ready" but not required anywhere, leaving the highest-value account-takeover targets under-protected.
**Decision:** MFA enrollment is required (not optional) before an `ADMIN` or `ENTERPRISE_ADMIN` account can be activated.
**Consequences:** Adds friction to admin onboarding, accepted as proportionate to the privilege level; standard/`TEACHER` accounts retain optional MFA at MVP.
**Status:** Accepted. **Resolves Architecture Review blocker #5.**

### ADR-012 — Platform-level AI cost circuit breaker

**Context:** Per-user entitlement caps limit individual abuse, but nothing previously capped aggregate/runaway platform cost from a provider pricing change or systemic bug — a real financial exposure.
**Decision:** `ai-engine` enforces an aggregate, platform-wide spend-rate cap (per-minute/per-hour) independent of per-user entitlements; breach triggers automatic degrade-to-cheaper-model first, then a hard stop with a graceful user-facing message, plus paging alert (AI_GOVERNANCE.md, OBSERVABILITY.md).
**Consequences:** A rare false-positive circuit trip could degrade service during a legitimate traffic spike — accepted as the safer failure mode versus unbounded cost exposure; thresholds are tuned from real staging/production traffic data, not fixed permanently at initial values.
**Status:** Accepted. **Resolves Architecture Review blocker #4.**

### ADR-013 — Family plan (and its COPPA scope) is descoped from MVP launch

**Context:** Architecture Review Gate identified that a COPPA-compliant parental-consent flow was named as a requirement but not specified in implementable detail, and treated it as launch-blocking for the Family plan specifically.
**Decision:** Rather than under-building a compliance-critical minors' data flow under launch-date pressure, Family plan (module 22) ships in Version 2 (ROADMAP.md), after a fully specified and tested parental-consent flow exists.
**Consequences:** Removes a launch blocker by scope reduction rather than compressed delivery; Premium/Family pricing messaging in PRD.md §7 reflects Free/Premium only at MVP.
**Status:** Accepted. **Resolves Architecture Review blocker #8.**

### ADR-014 — Split test runner: Jest for NestJS surfaces, Vitest elsewhere

**Context:** Epic E1 (Foundation & Engineering Platform Bootstrap) needs one settled test-runner choice per surface before any package/app is scaffolded — deferring this to each Epic individually would produce inconsistent tooling across the monorepo.
**Decision:** `apps/api` and all `services/*` (NestJS) use **Jest** — the framework's default, with zero-friction integration for `@nestjs/testing` and decorator/metadata reflection. `apps/web`, `apps/admin`, and all `packages/*` use **Vitest** — faster, native-ESM, the standard for modern Vite/Next.js-adjacent TypeScript code, with no NestJS-specific constraints to work around.
**Consequences:** Two test runners exist in one monorepo rather than one, which is a real DX cost; accepted because forcing Vitest onto NestJS (or Jest onto the frontend) fights each framework's well-trodden defaults for no functional benefit at this stage. Turborepo's `test` pipeline task treats both uniformly (same `pnpm test` entry point per package regardless of runner). Revisit only if NestJS's own tooling recommends a runner change upstream.
**Status:** Accepted.

### ADR-015 — Dependency-boundary enforcement via ESLint, not a second monorepo tool

**Context:** ADR-002's modular-monolith boundary rules (and ARCHITECTURE.md §2.1's bounded-context map) are only real if a broken boundary fails CI — Epic E1 must deliver that enforcement mechanism, not just document the rule.
**Decision:** Use `eslint-plugin-boundaries` (or equivalent import-boundary ESLint rule) configured against the `apps/ → packages/`, `services/ → packages/`, `packages/ ↛ apps/|services/` dependency direction and the six bounded contexts, rather than adopting a second monorepo/graph tool (e.g., Nx) alongside the already-chosen Turborepo (ADR-001).
**Consequences:** One monorepo toolchain, not two competing ones; boundary violations surface as a standard lint failure in the existing `pnpm lint` / CI pipeline, with no new tool for engineers to learn. The ruleset requires maintenance as new packages/services are added — owned by whoever's Epic introduces them (CODE_REVIEW_CHECKLIST.md already checks for this).
**Status:** Accepted.

### ADR-016 — Observability stack: OpenTelemetry SDK, CloudWatch (logs), AWS X-Ray via ADOT (traces), Sentry (errors), Jaeger locally

**Context:** The Epic E1 Independent Production Readiness Review (2026-07-29, [epics/E1-production-readiness-review.md](epics/E1-production-readiness-review.md)) found E1 shipped the first deployable applications with no logging, metrics, or tracing wired in — a direct contradiction of DEPLOYMENT.md §5's existing "wired in from first deploy, not retrofitted" commitment, and a finding that E1 could not satisfy its own [DEFINITION_OF_DONE.md](DEFINITION_OF_DONE.md). A concrete technology decision was required, not just a restated policy.
**Decision:** All apps/services instrument via the **OpenTelemetry SDK** (one vendor-neutral instrumentation layer, per OBSERVABILITY.md's existing tooling direction), wrapped in a new shared package `packages/observability` so no app/service hand-rolls its own bootstrap. Export targets: structured JSON logs to **CloudWatch Logs**; traces via the **AWS Distro for OpenTelemetry (ADOT)** collector to **AWS X-Ray**; errors to **Sentry**; metrics via the OTel Metrics SDK to **CloudWatch Metrics** (through the same ADOT collector). Locally, the same OTel SDK exports to a lightweight **Jaeger all-in-one** container (traces) and console/stdout (logs, metrics) via `docker-compose.yml` — no local Prometheus/Grafana stack, to avoid overbuilding local infrastructure ahead of real usage. The correlation ID used in logs, the JSON error envelope's `requestId` field (API_GUIDELINES.md §3), and the OTel trace ID are **the same identifier** — no parallel ID scheme is maintained.
**Consequences:** One instrumentation layer (OTel) across every language/framework the platform uses, consistent with the AWS-native infrastructure choice (ADR-009); ADOT is AWS's own supported distribution for exactly this CloudWatch/X-Ray export path, minimizing custom glue code. `packages/observability` becomes a required dependency of every `apps/*`/`services/*` skeleton from Epic E1 onward, not bolted on later.
**Status:** Accepted. **Remediates Architecture Review blocker (Critical 1, E1 review).**

### ADR-017 — Container supply-chain security: Syft (SBOM) + Trivy (scan) + cosign (sign) + GitHub native attestation (provenance)

**Context:** The same E1 review found no SBOM, image signing, or build-provenance attestation planned for any container image the CI/CD pipeline produces — a direct, named gap against the SLSA supply-chain framework.
**Decision:** Every container image built in CI passes through a fixed chain before it is eligible for deployment: **Syft** generates an SPDX SBOM → **Trivy** scans the image (and SBOM) for vulnerabilities, blocking on Critical/High severity CVEs with an available fix (CVEs with no fix yet are logged and tracked per SECURITY.md §6's patch SLA, not blocking) → **cosign** signs the image **keylessly** via GitHub Actions OIDC (Sigstore Fulcio/Rekor — no long-lived signing key to manage or leak) → **GitHub's native `actions/attest-build-provenance`** generates a SLSA-aligned provenance attestation → the deploy workflow **verifies** the signature and provenance before referencing the image in an ECS task definition update, and aborts with an alert if verification fails.
**Consequences:** No new key-management burden (keyless signing); the chain is fully automatable in GitHub Actions with first-party or well-maintained actions, avoiding a custom-built signing pipeline. A CVE with no upstream fix does not perpetually block deployment, but is tracked, not silently ignored.
**Status:** Accepted. **Remediates Architecture Review blocker (Critical 2, E1 review).**

### ADR-018 — JWT access token (Bearer, 15 min) + rotating refresh token (httpOnly cookie for web, secure device storage for mobile, 30 days)

**Context:** SECURITY.md §2 already commits to "short-lived JWT access tokens + rotating, revocable refresh tokens," and to refresh tokens being "stored httpOnly/secure/SameSite=strict for web" — but specified neither the access-token transport mechanism (needed for the Flutter mobile app, E21, which has no cookie jar) nor concrete lifetimes, and API_GUIDELINES.md did not state the access-token transport either.
**Decision:** Access tokens are short-lived (15 minute) JWTs sent via `Authorization: Bearer` header — a single, platform-agnostic transport for web, mobile, and any future first-party client, rather than a web-only cookie that would force a second, different mechanism for mobile. Claims: `sub`, `role`, `organizationId`, `orgRole`, `jti`, `iat`, `exp`. Refresh tokens are long-lived (30 day), one-time-use with atomic rotation-on-use (reuse of an already-rotated token revokes the entire session chain; a race between two near-simultaneous uses resolves to exactly one winner via a conditional update, the other treated as reuse), stored per SECURITY.md §2's existing cookie requirement for web and platform-secure storage (Keychain/Keystore) for mobile. Immediate revocation for a single session is backed by a short-TTL Redis denylist keyed on JWT `jti`; immediate propagation of a **role or org-membership change** (a distinct problem — the denylist alone doesn't handle "this still-valid token now claims a stale role") is handled via `User.tokensValidAfter`: every request additionally checks `jwt.iat >= user.tokensValidAfter`, so a role change invalidates the affected user's outstanding tokens on their next request, not at natural expiry.
**Consequences:** One access-token transport across every client, no web/mobile auth code fork; Redis is a hard dependency for immediate single-session revocation guarantees (fail-open on Redis outage — a documented, accepted 15-minute worst-case exposure window, not a silent one) — an acceptable dependency since Redis is already required elsewhere (API_GUIDELINES.md §7's rate limiter, E1's `docker-compose.yml`); `tokensValidAfter` adds one indexed/cacheable column read per authenticated request, a small, deliberate cost traded for closing a real privilege-staleness window. The `jti` denylist itself was not built in E2's initial implementation pass despite being specified here — closed in E2-T28 (`JtiDenylistService`), verified via a dedicated e2e test proving a revoked session's access token stops working immediately, and a negative test proving revocation is scoped per-session, not per-user.
**Status:** Accepted.

### ADR-019 — TOTP (RFC 6238) as the mandatory MFA mechanism for `ADMIN`/`ENTERPRISE_ADMIN`

**Context:** ADR-011 mandates MFA enrollment for `ADMIN`/`ENTERPRISE_ADMIN` before activation but did not specify a mechanism.
**Decision:** Time-based One-Time Password (TOTP, RFC 6238), compatible with standard authenticator apps (Google Authenticator, Authy, 1Password, etc.) — no SMS, no email-based second factor at MVP.
**Consequences:** No SMS-provider integration or per-message cost; works offline once enrolled; slightly higher enrollment friction than SMS (a user must install an authenticator app) — accepted as proportionate for `ADMIN`/`ENTERPRISE_ADMIN` accounts specifically (ADR-011's own reasoning: these are the highest-value account-takeover targets). Standard/`TEACHER` accounts remain unaffected (MFA optional, not required, for those roles).
**Status:** Accepted.

### ADR-020 — OAuth provider set at MVP: Google and Apple only (Facebook deferred)

**Context:** PRD.md §6's module 1 feature row states MVP scope as "Email + Google + Apple auth"; SECURITY.md §2 separately listed "OAuth (Google, Apple, Facebook)" as preferred over password auth — a real discrepancy, with no ADR resolving which was authoritative.
**Decision:** Google and Apple only at MVP, matching PRD.md's explicit feature-scope statement. Apple Sign-In carries a near-mandatory requirement for iOS apps offering other social login (App Store Review Guideline 4.8), giving Google+Apple a concrete, dated reason to ship together; Facebook has no equivalent forcing function and is deferred, not rejected outright.
**Consequences:** `OAuthAccount.provider` enum is `GOOGLE | APPLE` only; adding Facebook later is an additive enum value, not a breaking schema change. SECURITY.md §2's provider list is corrected to match in the same PR that accepts this ADR (E2-T29) — this ADR is the authoritative resolution going forward.
**Status:** Accepted.

### ADR-021 — Two-person approval for `ADMIN` role grants/revocations; single-party for `TEACHER`/`ENTERPRISE_ADMIN`

**Context:** An Architecture Gate review of the E2 design found no mechanism for changing a `User.role`, including no way the first `ADMIN` account could ever be created.
**Decision:** Role changes involving `ADMIN` (promotion to, or demotion from) require two-person approval: a requesting `ADMIN` initiates via `POST /v1/users/:id/role-change-requests`, and a second, different `ADMIN` must approve via `POST .../approve` before the change takes effect (`RoleChangeRequest`, expires unapproved after 72h). `TEACHER` and `ENTERPRISE_ADMIN` changes remain single-party, matching ADR-011's existing risk-proportionate reasoning (lower blast radius than platform-wide `ADMIN`). The very first `ADMIN` in a fresh environment is created by a one-time, out-of-band bootstrap procedure (`packages/database/scripts/bootstrap-admin.ts`) outside the API surface entirely, since no existing `ADMIN` can approve a request when none yet exists; the same procedure doubles as the documented emergency-recovery path if every `ADMIN` account is ever lost, publishing a distinct `identity.role.emergency_recovery` event (not blended into routine bootstrap volume) since a recovery run is a security incident by definition. Demoting the last remaining `ADMIN` (platform-wide) or the last remaining `ENTERPRISE_ADMIN` (per org) is blocked outright.
**Consequences:** Privilege escalation to the platform's highest-trust role now requires collusion between two named individuals, not a single compromised or malicious account; adds latency to legitimate `ADMIN` grants (accepted, matching ADR-011's own "adds friction, proportionate to privilege level" reasoning) and a genuine operational risk if an organization only ever has one real `ADMIN` (tracked in RISK_REGISTER.md).
**Status:** Accepted. **Resolves E2 Architecture Gate review Critical-1.**

### ADR-022 — Narrow, `BYPASSRLS`-granted service role for the handful of operations that must legitimately cross tenant boundaries

**Context:** Completing the RLS policy matrix (ADR-005) for `User` surfaced a real problem: registration and first-touch OAuth account creation must write a `User` row before any `app.current_user_id`/`app.current_org_id` session context exists to satisfy a per-request RLS policy against, and the GDPR-erasure background job and the bootstrap procedure must legitimately act across tenant boundaries by design.
**Decision:** A separate Postgres role (`app_service_role`), granted `BYPASSRLS` (a native, superuser-only-grantable Postgres privilege), used **only** by a small, explicitly named set of code paths: registration, OAuth account creation, the bootstrap-admin CLI, and the GDPR-erasure job. The default, per-request application connection role never has this privilege. Any new use of `app_service_role` is called out in CODE_REVIEW_CHECKLIST.md as requiring elevated review, since it is the one place RLS's defense-in-depth layer is deliberately absent.
**Consequences:** A small, auditable set of code paths carries full responsibility for their own tenant-scoping correctness with no RLS backstop — a real, accepted trade-off, scoped as narrowly as the actual requirement allows, rather than broadening `BYPASSRLS` to the standard role and losing RLS's protection everywhere.
**Status:** Accepted. **Resolves E2 Architecture Gate review Critical-2.**

### ADR-023 — Privileged-column protection via `REVOKE`/`GRANT` column allowlisting + `SECURITY DEFINER` governance functions

**Context:** A second Architecture Gate review of the E2 design found that row-level RLS policies (ADR-005, extended in ADR-022) do not restrict which columns a permitted row-level write can touch — an `ENTERPRISE_ADMIN`'s legitimate `user_update` access could also be used to write `User.role` directly, bypassing ADR-021's two-person-approval workflow with no database-level objection. The same review separately found that `RoleChangeRequest` approval lacked the atomic conditional-update pattern already established elsewhere (ADR-018's refresh-token rotation), and that a role change and its `AuditLog` write weren't guaranteed to be transactionally atomic.
**Decision:** Two complementary controls: (1) `REVOKE`/`GRANT` column-level privilege allowlisting on `User`, `OrganizationMembership`, and `RoleChangeRequest`, removing standard-role write access to every field identified as privileged (`role`, `organizationId`, `mfaEnrolled`, `mfaSecret`, `tokensValidAfter`, `status`, `passwordHash`, `orgRole`, and `RoleChangeRequest`'s resolution fields); (2) a small set of `SECURITY DEFINER` PL/pgSQL functions (`approve_role_change`, `set_org_role`, `complete_mfa_enrollment`) that are the _only_ writers of those columns, each performing its entire state transition — including the `tokensValidAfter` bump and the `AuditLog` write — inside one atomic function call. `app_role` receives `EXECUTE` on these functions, never direct column access. Both functions are owned by a narrowly-privileged, purpose-specific Postgres role, never the migration/superuser role.
**Consequences:** Privilege escalation via a direct `UPDATE` is prevented by Postgres's own privilege system, not application-code discipline — closing the exact class of gap RLS itself was introduced to close for tenant isolation, now applied to role governance. Every future privileged field this or a later Epic introduces must be evaluated against the same survey criteria before deciding whether it needs the same treatment. `SECURITY DEFINER` functions are a genuine, small new security-critical surface (they run with the privileges of their owner, not the caller) — CODE_REVIEW_CHECKLIST.md's elevated-review requirement for `app_service_role` (ADR-022) is extended to cover any new `SECURITY DEFINER` function too.
**Amendment:** a subsequent, function-body-level targeted review found the function _bodies_, as first drafted, didn't fully deliver this ADR's own stated guarantee — no platform-wide "last `ADMIN`" check existed at all in `approve_role_change()`, `set_org_role()`'s equivalent check had a cross-row TOCTOU race, and neither function verified its caller-supplied identity/authorization independently of the application layer. This is not a change to the decision above — column allowlisting plus `SECURITY DEFINER` functions as the only writers remains the approved model — it is the model's concurrency and authorization guarantees being fully specified rather than partially specified. Closed via: `pg_advisory_xact_lock` keyed per-invariant (a fixed key for the platform-wide `ADMIN` floor, an org-hash-derived key for the per-org `ENTERPRISE_ADMIN` floor), so a concurrent second caller can only ever evaluate the invariant against state committed by the first, never stale data; and explicit `current_setting('app.current_user_id')` cross-checks plus a fresh in-function lookup of the approver's/actor's own role, rather than trusting either the caller-supplied ID or the application layer's own authorization check alone.
**Status:** Accepted. **Resolves E2 Architecture Gate review's second-pass mandatory findings #1/#2; amendment resolves the subsequent function-body-level targeted review's findings.**

### ADR-024 — Flutter design-token export via a build-only, never-committed generated artifact

**Context:** ARCHITECTURE.md §5 and CODING_STANDARDS.md §4 both assert Flutter's design tokens are generated from `packages/ui`'s own source values, "never hand-copied, to prevent silent drift" — but no mechanism for this existed anywhere in the codebase, confirmed absent by direct inspection during E3's design (docs/epics/E3-design-system-component-library.md). A first draft of this ADR (E3 Pass 1) specified a committed artifact with a value-match/determinism test; an independent Architecture Gate review (docs/epics/E3-architecture-gate-review.md, finding F-H9) found that design could not actually detect drift — a `tokens.css` change with no regeneration produces a stale committed file that passes both tests.
**Decision:** The generated artifact (`design-tokens.json`) is **never committed to the repository**. `apps/mobile`'s own build pipeline invokes a generation script (`packages/ui`'s `generate:tokens`, parsing `tokens.css`'s `@theme`/`@utility` blocks with a real CSS parser) fresh on every build, from the current source. This eliminates the drift class of bug by construction — there is no stale copy that can exist, because no copy is ever persisted outside a build.

**Canonical-source note (E3 remediation pass #4):** the full specification below (token-category mapping, naming convention, schema versioning, consumer compatibility rules, schema evolution, failure behavior, unsupported categories, and a worked example) is specified **only here, in this ADR** — it is not duplicated in `docs/epics/E3-design-system-component-library.md`. An earlier revision of that design document pointed here in reverse ("specified in E3's design document §23"), and a later revision of that same document deleted the content §23 was supposed to hold without anyone updating this pointer — leaving both documents pointing at the other's absence. This ADR is now the single source of truth for this mechanism; the design document's §23 states this explicitly and does not restate the content.

**Naming convention:** every generated key is the source CSS custom property's name with the leading `--` stripped and kebab-case converted to camelCase (e.g. `--color-primary-text` → `colorPrimaryText`; `--type-heading-lg` → `typeHeadingLg`), grouped under the top-level category keys shown in the table above (`colors`, `radius`, `shadows`, `spacing`, `typography`, `breakpoints`, `motion`). No category is flattened into another, and no key is renamed beyond the mechanical kebab-to-camel conversion, so a Flutter engineer reading `tokens.css` and the generated JSON side by side can find any value without a lookup table.

**Schema versioning:** the artifact carries a top-level `schemaVersion` field, a plain incrementing integer starting at `1` (not a semver string — there is exactly one producer and one consumer of this schema, so semver's independent-party compatibility signaling adds no value here). It is bumped whenever a category is added, removed, or restructured (a key renamed, a value's shape changed, e.g. `shadows` moving from a single object to an array). It is **not** bumped for an ordinary value change within an existing shape (a new color added to the `colors` map, a hex value corrected) — those are exactly the changes this mechanism exists to propagate without drift, and gating them behind a version bump would defeat the purpose.

**Consumer compatibility rules & schema evolution:** `apps/mobile`'s build reads the generated artifact's `schemaVersion` and compares it against the version its own token-consumption code was written against (a constant checked into `apps/mobile`'s own source, updated only when that code is deliberately migrated to a new schema shape). A mismatch is a **build-time failure**, not a warning or a silent best-effort mapping — per CODING_STANDARDS.md §4's "never hand-copied, to prevent silent drift," a silently-adapted-to mismatch would reintroduce a different flavor of the same drift risk this ADR exists to eliminate. Adding a new token within an existing category's shape is non-breaking and requires no version bump or `apps/mobile` change. Renaming or removing a key, or restructuring a category's shape, is breaking, requires a version bump, and requires `apps/mobile`'s consuming code to be updated in the same PR that bumps the version — mirroring CLAUDE.md's "a PR changing an architecture contract updates the corresponding doc" rule, extended here to a generated-schema contract rather than a documentation contract.

**Keyword-valued shadow rule (added, remediation pass #5, closing the fifth review's N-6):** the shipped `tokens.css` declares `--shadow-flat: none` — a bare CSS keyword, not a `box-shadow` shorthand value, and not parseable into the `{offsetX, offsetY, blur, spread, color, opacity}` shape every other shadow tier uses. The generation script maps a `none`-valued shadow token to an **empty array** (`"flat": []`) in the generated artifact, stated here as an explicit rule rather than left for T18's implementer to discover as an edge case. This is not a failure condition (see Failure behavior below) — `none` is a valid, expected CSS value for this specific token, and Flutter's own convention for "no shadow" is an empty `BoxShadow` list, so the mapping requires no further translation on the consumer side.

**Typography schema-validation rule (added, remediation pass #6, closing the sixth review's P6-1):** each `typography.<name>` entry the generator emits must contain all four of `fontSize`, `lineHeight`, `fontWeight`, and `fontFamily`, each successfully resolved to a concrete value (a numeric px/unitless value for the first three, a font-family string for the fourth). This is a build-time failure condition, not a warning: if any `@utility type-<name>` block in `tokens.css` is missing one of its four required declarations, or if a declaration's `var()` reference cannot be resolved against a `:root`-declared Tier-1 primitive, the generator fails the build and names the specific token and the specific missing/unresolvable field in its error output — an implementer adding a tenth Tier-2 token who forgets `font-family`, for example, gets a build failure naming exactly that, not a Flutter `TextStyle` silently missing a font.

**Failure behavior:** the generation script (`packages/ui`'s `generate:tokens`) fails the build (non-zero exit, no partial/best-effort output) if: `tokens.css` fails to parse under `postcss`; a token category expected by the mapping table above is entirely absent from the parsed `@theme`/`@utility` output; a typography token fails the schema-validation rule immediately above; or a mapped value does not match its expected type (e.g. a color token whose value is not a valid 3/6/8-digit hex string, a duration token that does not parse as a numeric `ms` value, or — excluding the `none`/empty-array case above — a shadow value that is neither a valid `box-shadow` shorthand nor the literal keyword `none`). There is no fallback-to-last-known-good behavior — a broken source produces a broken build, visibly, not a stale or partially-correct artifact.

**Unsupported token categories:** `--z-index-*` is deliberately excluded from the generated artifact, stated explicitly rather than silently dropped. CSS z-index has no meaningful Flutter equivalent — Flutter controls stacking order via widget-tree order (`Stack` + `Positioned`, or simply paint order), not a numeric layering property applied to an individual element. Emitting a `zIndex` field into the artifact would give Flutter code a value with nothing correct to do with it. If a future need arises for Flutter-side stacking guidance, it should be modeled as an explicit widget-composition convention documented in a future mobile epic, not force-mapped from this CSS-specific concept.

**Consequences:** No committed-artifact drift is possible by construction — a stronger guarantee than a CI-diff-check against a committed file would provide even if implemented correctly. `apps/mobile`'s build gains a build-time dependency on `packages/ui`'s source tree, which a monorepo-internal token dependency already implies. **Reversibility:** High — a future move to a committed-artifact-plus-diff-check model, or a different export format (e.g. an open Design Tokens standard), only requires rewriting the generation script, not touching any consumer.

**Context:** DESIGN_SYSTEM.md §4's component categories (form validation icons, navigation, AI message bubble's required persistent icon signaling AI-purple content per WCAG 1.4.1, admin data-table sort indicators) need a functional icon set at foundation depth, distinct from DESIGN_SYSTEM.md §7's explicitly-deferred full illustration/iconography system. ### ADR-026 — Storybook access control via CloudFront Function + CloudFront KeyValueStore, superseding the unbuildable Secrets-Manager-direct-read design

**Context:** E3's design requires a hosted, access-restricted preview of `packages/ui`'s Storybook build for team review. The first remediation pass (E3 Pass 1) proposed a CloudFront Function reading a credential from AWS Secrets Manager at request time. The second independent Architecture Gate review (docs/epics/E3-second-independent-review.md, finding N-5) found this **not buildable**: CloudFront Functions execute in a restricted `cloudfront-js-2.0` runtime with no network access, filesystem access, or AWS SDK, and cannot call Secrets Manager. The review also found the `edge` Terraform module provided less reuse than claimed (a `REGIONAL`-scoped WAF ACL tied to the ALB, no S3 origin, no Origin Access Control, no CloudFront Function precedent).
**Decision:** Keep the edge-compute tier choice (CloudFront Functions — still the cheapest, lowest-latency option genuinely suited to a stateless per-request check) but pair it with a **CloudFront KeyValueStore**, a store purpose-built for small amounts of data read by a CloudFront Function at the edge. Terraform — which has full AWS SDK/network access at `apply` time, unlike the edge function at request time — resolves the real credential from Secrets Manager, generates an independent salt (a Terraform-generated random value, not derived from the credential), and writes both the resulting `SHA-256(salt + credential)` hash and the plaintext salt into the KVS as separate entries (full mechanism, rotation, ownership, and fail-closed failure behavior specified in the E3 design document §18, corrected there in remediation pass #6). The function reproduces the same salted-hash computation against the request's `Authorization: Basic` header using `cloudfront-js-2.0`'s `crypto` module and compares the two hashes, entirely within the runtime's actual, documented capabilities. A new, minimal S3 origin with Origin Access Control is provisioned for the static Storybook build (the `edge` module's existing distribution has no S3 origin today). **The distribution ships v1 without a dedicated `CLOUDFRONT`-scoped WAF ACL** — not assumed inherited from the `edge` module's own, differently-scoped (`REGIONAL`) ACL, which does not and cannot cover a CloudFront distribution regardless of this decision. This is a stated decision, not an open option: a new WAF ACL is a real, ongoing cost/maintenance addition, and the threat model it would address (volumetric/bot abuse) does not meaningfully apply to a low-traffic internal preview tool already behind Basic Auth. The decision is revisitable — RISK_REGISTER.md R-65 tracks it explicitly, with the Security/DevOps role as owner, and a WAF ACL can be added at any later `terraform apply` without touching the KVS/function pair this ADR specifies — but it is not left open pending T17.
**Alternatives considered:** Lambda@Edge (genuine network/SDK access, rejected for v1 on latency/cost/deployment-complexity grounds relative to this simple a check — the right choice if the model later needs real statefulness); CloudFront signed cookies issued via a GitHub-OAuth-backed token endpoint (genuinely per-user and instantly revocable via GitHub org membership — the better long-term posture, evaluated in detail, rejected for v1 specifically as a materially larger build — new OAuth App, new Lambda/Function URL, new IAM surface — than a low-sensitivity internal preview tool justifies at this epic's M complexity; named as the explicit recommended upgrade path); Cognito (rejected — would introduce a second, redundant identity system alongside the one Epic E2 already built in `apps/api`, for a concern that isn't customer-facing identity); private/VPN-only hosting (rejected — no existing VPN/bastion pattern exists in this project's infrastructure to extend, and building one is a larger, unrelated investment).
**Consequences:** The credential remains shared, not per-user, and revocation (a `terraform apply` rewriting the KVS entry) is fast (seconds, via KVS's edge-propagation design) but not instant or individually scoped — an explicit, accepted limitation (RISK_REGISTER.md R-56), not improved or hidden by this ADR, only made buildable. Terraform gains a new, small, security-relevant responsibility (resolving the real secret and computing/writing its hash) that should carry the same elevated-review discipline CODE_REVIEW_CHECKLIST.md already applies to comparable narrow-privilege surfaces elsewhere in this project.
**Security implications:** The KVS stores a salted hash, never the raw credential; a KVS compromise alone does not disclose the credential.
**Reversibility:** High — moving to Lambda@Edge or the GitHub-OAuth model later replaces only the function/KVS pair, not the S3 origin, OAC, or the rest of the distribution.
**Status:** Proposed — pending Architecture Gate approval of E3's design, not self-approved.

### ADR-027 — Prisma multi-file schema composition (`prismaSchemaFolder`) for `packages/database`

**Context:** E4's design (docs/epics/E4-database-schema-core-data-layer.md §6.6) adds roughly 55 new Prisma models across nine domains on top of the ~26 E2 already shipped in a single `schema.prisma` file. DATABASE.md §2's own header text ("Each maps to one or more Prisma schema files composed into the shared `packages/database` schema") already signals multi-file intent, but no decision was ever made about the actual mechanism, and the live repository state is a single file. Left undecided, each of E4's nine domain tasks would make its own ad hoc choice about where its models live, guaranteeing inconsistency.
**Decision:** Adopt Prisma's `prismaSchemaFolder` preview feature: a `packages/database/schema/` directory containing one `.prisma` file per DATABASE.md domain (`identity.prisma` for the already-built §2.1 models, `content.prisma`, `assessment.prisma`, `vocabulary.prisma`, `ai-conversation.prisma`, `gamification.prisma`, `community.prisma`, `exams.prisma`, `billing.prisma`, `analytics.prisma`), all composed by the Prisma CLI into the single generated client and single migration history ARCHITECTURE.md §5 requires — the composition is build-time tooling behavior, not a change to the "one schema, one migration history, one client" guarantee. E2's existing models move into `identity.prisma` as a pure file-split (no field/relation changes) in the same migration that establishes the new folder structure, so the split itself never touches production data.
**Alternatives considered:** Continue single `schema.prisma` (rejected — see E4 §8: an estimated 3,000+ line single file across the full ~80-model schema is an avoidable, real code-review/navigation cost, and this epic is the last natural point to avoid paying it before the file grows further); separate Prisma projects/clients per domain (rejected outright — contradicts ARCHITECTURE.md §5's single-client guarantee and reintroduces the cross-service schema-drift risk ADR-005 exists to prevent); a folder split with no Prisma-native composition (manually concatenating files before `generate`) (rejected — `prismaSchemaFolder` is Prisma's own supported mechanism for exactly this; hand-rolling a concatenation step would be unsupported, undocumented tooling maintained by this project alone for no benefit over the vendor-supported path).
**Consequences:** Requires confirming `prismaSchemaFolder` is available (not merely announced) in this repository's pinned Prisma version before T1 (E4 §9) begins — if it is still preview-gated behind a `previewFeatures` flag, that flag becomes a new, explicit entry in `schema.prisma`'s (or the new folder's root) generator block, stated here rather than discovered mid-implementation. Every future domain (post-MVP epics adding new tables) gets an obvious, single place to add its own file, rather than a judgment call about where in one large file a new model belongs.
**Security implications:** None — a file-organization change, not a data-access or privilege change.
**Reversibility:** High — Prisma's own migration output is identical regardless of source-file layout; collapsing back to a single file later is a pure refactor with no migration/data impact.
**Status:** Accepted (2026-08-07) — by explicit user direction to proceed with E4's T1 implementation rather than through an independent Architecture Gate review (docs/epics/E4-database-schema-core-data-layer.md §12's Architecture Gate row). ### ADR-028 — `pg_partman` for time-based partition maintenance on `AIMessage`/`LearningEvent`/`AIUsageLog`

**Context:** DATABASE.md §5/§9 requires `AIMessage`, `LearningEvent`, and `AIUsageLog` to be range-partitioned by month "from the start," but specifies neither how new monthly partitions get created ahead of the active one filling, nor what happens if that creation mechanism fails. E4's design (§6.5, §8) treats this as one decision applied to all three tables, not three independent ones.
**Decision:** Use the `pg_partman` Postgres extension's native partition-maintenance function (`partman.run_maintenance()`), invoked on a monitored recurring schedule via the existing BullMQ scheduling infrastructure (EVENT_ARCHITECTURE.md §1) rather than a hand-rolled equivalent. `pg_partman` pre-creates a configurable number of future partitions (proposed default: 3 months ahead) so a single missed scheduled run does not itself cause a write failure — only a sustained, multi-run outage would, at which point the monitored job-failure alert (OBSERVABILITY.md) has already fired.
**Alternatives considered:** A hand-rolled BullMQ job directly issuing `CREATE TABLE ... PARTITION OF ...` DDL on a schedule (rejected as the primary mechanism — reimplements a well-understood problem `pg_partman` already solves, including edge cases like retention-driven old-partition detachment DATABASE.md §9's archival strategy also needs; a hand-rolled job is plausible but is the second-choice fallback if `pg_partman` proves unavailable on the target RDS/Aurora Postgres version, not preferred over it); manually pre-creating 24 months of empty partitions upfront (rejected — defers rather than solves the problem, and 24 empty partitions per table provide no benefit over automated just-in-time creation); no partitioning automation, relying on a human to run DDL monthly (rejected outright — directly contradicts DATABASE.md's own "from the start" requirement and this project's stated no-manual-production-operations posture elsewhere, e.g. ADR-024's build-only artifact reasoning).
**Consequences:** Adds `pg_partman` as a new Postgres extension dependency, requiring confirmation it's available/installable on the target RDS/Aurora Postgres version before T1 (E4 §9) begins — not assumed. Introduces a new operational surface (the scheduled maintenance job) that must be monitored, not fire-and-forget; E4's own risk register (§11) names this explicitly.
**Security implications:** None directly — partition maintenance operates on already-encrypted-where-required data (ADR-029) and does not itself touch row content.
**Reversibility:** Medium — `pg_partman`-managed partitions are still native Postgres declarative partitions; removing `pg_partman` later and managing partitions manually is possible without a data migration, but the scheduled-maintenance convenience is lost.
**Status:** Accepted (2026-08-07) — by explicit user direction to proceed with E4's T1 implementation rather than through an independent Architecture Gate review (docs/epics/E4-database-schema-core-data-layer.md §12's Architecture Gate row). Recorded here as what actually happened, not as an Architecture Gate sign-off — the same distinction ADR-025 already draws for T4's icon-library decision.

### ADR-029 — `AIMessage.content` field-level encryption via a Prisma Client Extension

**Context:** DATABASE.md §5/§8 requires field-level encryption on `AIMessage.content` (raw learner conversation transcripts, the platform's largest-volume, most PII-sensitive table), keyed via KMS envelope encryption, but does not specify the integration mechanism — Prisma has no native field-encryption feature, and E4's design (§6.4) treats this as its single highest-sensitivity mechanic.
**Decision:** Implement encryption/decryption inside a Prisma Client Extension, defined once in `packages/database`'s own generated-client wrapper (not `ai-engine` or any other consumer), intercepting `create`/`update`/`upsert`/`createMany`/`findMany`/`findUnique`/etc. operations on the `AIMessage` model specifically. The extension is built against a `DataKeyProvider` interface (envelope-encryption generate/decrypt-data-key), not a hardcoded AWS SDK call — resolved by explicit user decision at T5 implementation time (this dev environment has no AWS credentials, the same constraint T1 hit): `AwsKmsDataKeyProvider` calls real AWS KMS (`GenerateDataKey`/`Decrypt`) and is required whenever `NODE_ENV=production`; `LocalStubDataKeyProvider` is an env-gated dev/CI stand-in (reuses `@linguaai/utils`'s already-shipped AES-256-GCM primitive, the same one `User.mfaSecret` uses) that refuses to run in production. It does not choose or manage the KMS key policy itself (a Security Gate / infrastructure decision, out of this ADR's scope). Every consumer of the shared Prisma client gets transparent encryption without needing to remember to call anything — the table's own access path is where the guarantee lives, not caller discipline.
**Alternatives considered:** Encrypt explicitly at the `ai-engine` application-service layer before every write, decrypt after every read (rejected as the sole mechanism — correct for `ai-engine`'s own known call sites today, but every future consumer — a support tool, an admin export job, a future analytics pipeline — would have to independently remember and correctly implement the same discipline; a single missed call site is a silent plaintext-storage bug with no structural guard against it); Postgres `pgcrypto` column-level encryption (`pgp_sym_encrypt`/`pgp_sym_decrypt`) (rejected — requires the database itself to hold or receive the decryption key to run either function, which undermines the actual security property KMS envelope encryption is meant to provide, namely that the database alone cannot decrypt its own encrypted columns; also bypasses DATABASE.md §5's "admin/support tooling accesses a redacted view by default" requirement, since raw SQL access would see ciphertext it could trivially decrypt with the same key any other caller uses); disk/table-level encryption only, no field-level mechanism (rejected outright — DATABASE.md §8 already decided field-level encryption is required in addition to disk-level; this ADR only decides the _mechanism_, not whether to do it at all).
**Consequences:** Every `AIMessage` read/write incurs a KMS call unless a data-encryption-key caching strategy is added (envelope encryption's standard pattern: cache the decrypted data key for a short TTL, not the master key) — this ADR names the need for that caching layer but does not design it in full; that is T5's (E4 §9) own implementation-time detail, not re-litigated here. A bug in the extension's operation-interception logic (e.g., a raw `$queryRaw` call that bypasses the extension entirely) could write unencrypted content undetected — E4's own risk register (§11) and T5's evidence bar (§9: an explicit round-trip test proving on-disk ciphertext, not just a working read) exist specifically to catch this class of bug before it ships.
**Security implications:** Directly implements DATABASE.md §5's access-control requirement (raw content restricted to the owning user and the serving request path); centralizes the highest-risk data-handling code in one reviewable location (`packages/database`) rather than distributing it across every consumer.
**Reversibility:** Medium — changing the encryption mechanism later requires a re-encryption migration pass over every existing `AIMessage` row (a real, non-trivial migration, not a config change), the same cost any encryption-mechanism change would carry regardless of which alternative had been chosen instead.
**Status:** Accepted (2026-08-07) — by explicit user direction to proceed with E4's T1 implementation rather than through an independent Architecture Gate review (docs/epics/E4-database-schema-core-data-layer.md §12's Architecture Gate row). Recorded here as what actually happened, not as an Architecture Gate sign-off — the same distinction ADR-025 already draws for T4's icon-library decision.

### ADR-030 — Cross-domain FKs must be real Prisma `@relation`s, not plain scalars + manual migration SQL

**Context:** E4 T2 introduced a convention for referencing another domain file's model (e.g. `ExerciseAttempt.userId` → `identity.prisma`'s `User`) without a Prisma `@relation`: a plain scalar column, plus a hand-appended `ALTER TABLE ... ADD CONSTRAINT ... FOREIGN KEY` statement in that migration's raw SQL. The stated reason was to avoid coupling every domain file to editing another domain's file for a back-relation array. This was never formalized as its own ADR — a gap this ADR corrects retroactively, per CLAUDE.md's own rule that a significant architecture decision doesn't live only in code comments. While implementing T5, this convention was found to be broken: Prisma's migration-diff engine has no record that a hand-written constraint (invisible to `schema.prisma`) should exist, and silently emits a `DROP CONSTRAINT` for it on the very next `prisma migrate dev` run from _any_ domain, not just the one that added it. Checked directly against the live database: T3's migration had silently dropped T2's `ExerciseAttempt.userId` FK; T4's migration had silently dropped nine of T3's FKs; T5's own freshly-generated migration was about to drop T4's four. A probe schema confirmed Prisma has no supported one-sided relation declaration (FK-owning side only, no back-relation array) — the validator hard-rejects it.
**Decision:** Every cross-domain reference is a real Prisma `@relation`, with a matching back-relation array field on the referenced model (`identity.prisma`'s `User`, `content.prisma`'s `Language`), even though the referenced model's file gains one array field per new domain that references it. This is the only mechanism Prisma persists correctly across every future migration without requiring a human to remember to re-append every previously-added manual FK on every subsequent migration generation, from any domain — a discipline that had already silently failed twice (T3, T4) before being caught at T5. Applies retroactively: T2–T4's already-applied, already-pushed migrations were not rewritten (forward-only), but a new repair migration (`20260806194756_repair_cross_domain_fks_as_prisma_relations`) restored the thirteen silently-missing constraints, and every affected schema file (`identity.prisma`, `content.prisma`, `assessment.prisma`, `vocabulary.prisma`, `ai.prisma`) was updated to the real-relation form before any further domain (T6+) could repeat the mistake.
**Alternatives considered:** Keep plain scalars, formalize a checklist requiring every future migration to re-append every prior manual FK (rejected — this is the exact discipline that already failed twice without being noticed until a third, unrelated task happened to inspect the generated SQL closely; a procedural fix for a structural problem, not a real fix); hand-author every future cross-domain-touching migration's SQL from scratch, bypassing `prisma migrate dev` entirely for those cases (rejected — defeats the purpose of using Prisma Migrate, doesn't scale across T6–T12, and removes the tool's own drift-detection value for everything else in the same migration); leave the dropped constraints unfixed and treat it as an accepted gap (rejected outright — silent loss of referential integrity on user-owned data is not an acceptable trade-off for avoiding file coupling, and contradicts this repo's "no demo-level work" standard).
**Consequences:** `identity.prisma`'s `User` model and `content.prisma`'s `Language` model each accumulate one array field per future domain that references them (T6 Gamification, T7 Community, etc. will each add more) — an accepted, understood coupling cost, not an oversight. Every future E4 task (T6–T12) that references `User`/`Language` must edit those two files, not just its own domain file, and must use a real `@relation`, not a scalar — now stated explicitly in every schema file's own header comment so this isn't rediscovered the hard way a third time.
**Security implications:** None beyond what T2 already established — referential integrity itself is a data-integrity property, not new attack surface. The prior broken state (constraints silently missing) was a real, if narrow, data-integrity gap: an orphaned `userId`/`languageId` reference was possible on several tables for the period between each drop and this fix.
**Reversibility:** Low cost to reverse the specific coupling (removing an array field is a small, mechanical schema change) but the underlying lesson — manual migration-SQL FKs don't survive Prisma's own tooling — is not something a future task should re-litigate without re-deriving this same empirical finding.
**Status:** Accepted (2026-08-07) — found and fixed during E4 T5 implementation, by the same explicit user direction covering T5 (not an independent Architecture Gate review). Recorded here as what actually happened, matching ADR-025's precedent for this distinction.

### ADR-032 — Specialist trigger-condition catalog and tool-registry versioning scheme

**Context:** AI_SYSTEM.md §3 states the exact trigger-condition catalog and tool-registry versioning "live in AI_GOVERNANCE.md §2, §6." Read directly, neither section contains them — §2 gives one worked example only, §6 states only that a versioned registry exists as policy. No catalog or versioning scheme is documented anywhere in the repository. ADR-007's entire tool-calling contract (a specialist fires only on a real, defined trigger, never by default every turn) is unimplementable without this existing somewhere concrete.
**Decision:** A versioned registry file per Orchestrator-capable persona under `services/ai-engine/src/agents/registry/entries/` (`ToolRegistryEntry`: `orchestratorPersona`, `version`, `allowedTools[]`), looked up exclusively through `ToolRegistryService.getAllowedTools()` — a persona with no entry throws rather than silently permitting an undeclared tool call. Each `allowedTools` item pairs a `SpecialistPersona` with a `TriggerCondition`, a discriminated union (`error_pattern_threshold`: `confidenceThreshold` + `minRecurrenceCount`; `phoneme_score_threshold`: `confidenceThreshold`) rather than one shared shape, since different specialists' triggers are genuinely different signals. A separate, pure `evaluateTrigger(condition, signal)` function decides whether a given signal fires a condition — deliberately _not_ the same code that would _produce_ that signal (a real grammar-error-pattern classifier, or `speech-service`'s phoneme scoring, E10) — that production logic is each specialist's own pedagogical scope (E6/E9/E11/E13/E19), not this mechanism's. Version bump rule: whenever `allowedTools` changes in a way that could alter real invocation behavior (a specialist added/removed, or a trigger condition's parameters changed) — not for a cosmetic edit — mirroring T3's `PromptTemplate.version` convention exactly. Populated only where AI_SYSTEM.md §3's own agent table textually supports a real trigger relationship: **Conversation Partner** → Grammar Coach (error-pattern trigger) + Pronunciation Coach (phoneme-score trigger, not yet evaluable for real pending E10). The other four Orchestrator-capable personas get a structurally-ready, deliberately empty entry — real gaps for their own consuming epics to fill, not oversights, matching E5 §1's own "tool-registry entry exists, real pedagogical logic is each consuming epic's own scope" framing. This implementation also corrected an inaccurate over-generalization AI_GOVERNANCE.md §2 previously stated (every Orchestrator persona having "the same tool-calling relationship to the remaining specialists") — the real registry shows that isn't true; only Conversation Partner currently has one.
**Alternatives considered:** Leaving the catalog undocumented and trigger logic scattered inline per specialist's own code (rejected — reproduces exactly the "forward-reference to nothing" gap this ADR exists to close, and makes trigger conditions untestable as a structural contract per AI_GOVERNANCE.md §2's own stated requirement); one shared `TriggerCondition` shape for every specialist (rejected — Grammar Coach's recurring-pattern signal and Pronunciation Coach's single phoneme score are genuinely different data, forcing a shared shape would mean unused fields on one side or the other); populating every persona's `allowedTools` speculatively now to "complete" the catalog (rejected — would invent trigger relationships AI_SYSTEM.md §3's own table does not state, the same discipline that kept T1's provisional numeric thresholds honest instead of guessed).
**Consequences:** AI_GOVERNANCE.md §2/§6 updated in this same change, so the forward-reference is now true rather than a dangling promise. Every future epic adding a real specialist-tool relationship (E6, E9, E11, E13, E19) edits its own persona's registry entry file directly — a small, contained, individually-reviewable change, not a shared file every epic must coordinate around.
**Security implications:** The tool registry's own versioning is what AI_GOVERNANCE.md §6 calls the mechanism preventing "unscoped code execution or unrestricted external calls" — this is a real security-relevant boundary, not just documentation hygiene. `ToolRegistryService` throwing on an unregistered persona (rather than defaulting to "no tools" silently) makes a missing entry a loud, caught-at-startup-or-first-call failure, not a silent under-permission that could look like correct behavior.
**Reversibility:** High — a registry format change is additive/versioned by design.
**Status:** Accepted (2026-08-07) — implemented in E5 T5, by the same explicit user direction covering T1–T4.

### ADR-033 — Internal `apps/api` ↔ `ai-engine` contract: REST + `@nestjs/swagger` OpenAPI, SSE for streaming

**Context:** AI_SYSTEM.md §2 states the internal request/response contract between `apps/api` and `ai-engine` "is documented alongside the OpenAPI spec (API_GUIDELINES.md §11)." Read directly, API_GUIDELINES.md §11 only states OpenAPI is generated exclusively from `@nestjs/swagger` decorators — a mechanism for documenting any REST contract, not evidence this specific one exists. No DTO, controller, or contract for `ai-engine` exists anywhere in the repository as of this ADR.
**Decision:** REST (not gRPC), matching ADR-003 and every other `apps/api`-to-`services/*` integration already in this repo. Contract documented via `@nestjs/swagger` decorators on real controllers/DTOs in `services/ai-engine` (`AgentSessionsController`: `POST /v1/agent-sessions`, `POST /v1/agent-sessions/:id/messages`, `POST /v1/agent-sessions/:id/end`), the same mechanism API_GUIDELINES.md §11 already mandates platform-wide — `main.ts` now publishes it at `/v1/docs` outside production, matching `apps/api`'s own established convention. Streaming responses (session message generation) use Server-Sent Events over the same REST endpoint — not a WebSocket, and not NestJS's `@Sse()` decorator (that decorator forces `GET`, incompatible with a request body) — managed manually via `@Res()` instead, since the client only ever consumes a one-directional stream for a given message turn.
**Alternatives considered:** gRPC (rejected — no stated performance case this integration needs that REST-with-SSE can't meet within PERFORMANCE.md §2's 900ms first-token budget; would introduce a second inter-service contract style with no precedent in this repo); WebSocket for streaming (rejected — ADR-003 already reserves WebSocket specifically for "real-time flows," i.e. the client↔`apps/api`↔`speech-service` audio pipeline that is E10's own scope; full-duplex capability is unused overhead for a one-directional generation stream); a literal OpenAPI-codegen'd client for `apps/api`'s own consumption (rejected for this task — no such tool exists anywhere in this repo yet, and standing one up is a bigger infra decision than T10's own scope; "typed client" is instead achieved the same way `packages/types`/`packages/validation` already serve every other internal contract — both sides import the identical `@linguaai/validation/ai-coaching` Zod schemas, a deliberate interpretation of this ADR's own "matching packages/types/packages/validation's established role" wording, not literally what "generated from the OpenAPI spec" states).
**Consequences:** `apps/api`'s new `AiEngineClientModule`/`AiEngineClientService` calls `ai-engine` through those same shared Zod schemas (request validation before sending, response/SSE-event validation on receipt) — matching `packages/types`/`packages/validation`'s established role as the platform's real contract-enforcement mechanism (ARCHITECTURE.md §4). `OrchestratorService` itself gained a second, real streaming code path (`streamMessage()`, backed end-to-end by `RouterService.stream()`) alongside its existing non-streaming `sendMessage()` — the SSE contract is genuine token-by-token streaming, not a single buffered response wrapped in SSE framing. Live-streamed deltas are un-sanitized raw model output (`sanitizeOutput()` can only run on complete text); AI_GOVERNANCE.md §6 already documents the gateway-level sanitizer as defense-in-depth with a renderer-level sanitizer as the primary defense, so this is not a new gap, just a surface where that existing layered-defense principle now actually applies. `AiEngineClientService` is registered in `apps/api`'s DI graph but has no controller consumer yet — building a user-facing AI chat endpoint is each consuming feature epic's own scope (e.g. E6 Personal AI Language Teacher, ROADMAP.md), not this internal-contract task's, the same "build the real mechanism, flag the not-yet-wired consumer" precedent E5 T7's RAG Retrieval Layer already set.
**Security implications:** None beyond what any internal REST integration already carries (internal-network-only, matching other `services/*` integrations) — `ai-engine`'s `AgentSessionsController` has no auth guard of its own; `apps/api`'s own already-authenticated request is the trust boundary, and `userId` travels as a caller-supplied field rather than a token `ai-engine` would have to independently verify.
**Reversibility:** Medium — an internal contract, changeable without external API-consumer impact, but every consumer (`apps/api` today, potentially `apps/mobile` later) must update together.
**Status:** Accepted (2026-08-07) — implemented in E5 T10 (`services/ai-engine/src/agent-sessions/`, `apps/api/src/modules/ai-engine/`), by the same explicit user direction covering T1–T9.

### ADR-034 — AI cost circuit breaker: Redis sliding-window counter, 3-stage breach ladder, provisional thresholds

**Context:** ADR-012 already accepted the policy (a platform-wide, aggregate spend-rate cap independent of per-user entitlements). AI_GOVERNANCE.md §5 names the breach response ladder but explicitly withholds numeric thresholds, stating they "are set from real staging/production traffic data and reviewed monthly, not fixed permanently at a guessed initial value." E5 needs a real, working mechanism to ship T9, even though the numbers inside it are deliberately not yet final.
**Decision:** A Redis counter (per-minute and per-hour buckets, matching AI_GOVERNANCE.md §5's own review cadence), incremented from every `AIUsageLog.costUsdMicros` write (`CostMeterService.recordUsage()`), checked before each new AI-invoking request reaches the Router (`CircuitBreakerService.checkBreachState()`, called from `OrchestratorService` immediately before both its main-reply and its internal summarization Router calls). Breach ladder transcribed verbatim from AI_GOVERNANCE.md §5, implemented as: (1) DEGRADE — the affected Router call is made with `ModelTier: 'economy'`, resolved per request class via the new `AI_MODEL_TEACHER_ECONOMY`/`AI_MODEL_ASSESSMENT_ECONOMY` config, falling back to the default model (with a logged warning) for a class with no economy model configured; (2) HARD_STOP — `OrchestratorService` throws before the Router is ever called, surfacing a graceful user-facing error; (3) page on-call — an ERROR-level structured log on the transition into HARD_STOP, for OBSERVABILITY.md's alerting pipeline to page from (no paging provider is integrated directly by this service). **Alternatives considered:** A database-backed counter instead of Redis (rejected — Redis is already the platform's cache/rate-limit infrastructure per ARCHITECTURE.md, and a spend-rate check needs to run on every request's hot path, where a Postgres round-trip is the wrong latency profile against PERFORMANCE.md §2's 900ms LLM-stage budget); a fixed, permanently-set threshold decided now (rejected outright — directly contradicts AI_GOVERNANCE.md §5's explicit instruction not to guess a permanent value); a true sliding-window log (e.g. a sorted set of individual cost events) instead of fixed calendar-minute/-hour buckets (rejected for this task — the extra precision isn't warranted while the thresholds themselves are still provisional placeholders; flagged as a real, named simplification in RISK_REGISTER.md rather than silently presented as a true sliding window).
**Consequences:** The threshold values themselves need a real, tracked update once staging data exists — this ADR's own mechanism is stable, but the numbers inside it are expected to change, by design, not as a sign something was wrong. Cost estimation depends on a provisional, manually-maintained USD-per-million-token pricing table (`pricing-table.ts`) matched by model-id substring, not synced to any provider's live pricing API — approximate but real and continuous, the same honesty precedent as the thresholds themselves.
**Security implications:** A false-positive trip degrades service during a legitimate spike (accepted risk, per ADR-012's own consequences); a missed/too-loose threshold risks real unbounded cost exposure — the reason a P0 "circuit breaker tripped" alert already exists (OBSERVABILITY.md).
**Reversibility:** High — thresholds are a config value; the mechanism itself is stable infrastructure once built.
**Status:** Accepted (2026-08-07) — implemented in E5 T9 (`services/ai-engine/src/cost/`), by the same explicit user direction covering T1–T8.

### ADR-035 — `AIMessage`/partitioned-table maintenance runs as a BullMQ job inside `ai-engine`

### ADR-036 — `services/*` microservices connect to Postgres as `app_role`, never the migration-owning `DATABASE_URL` role

**Context:** E5 T4 (Orchestrator) is the first `services/*` microservice to touch the database at all — every prior real consumer was `apps/api`, whose `DatabaseModule` (E2-T8/T10) already deliberately avoids `packages/database`'s shared `getPrismaClient()` singleton (wired to `DATABASE_URL`, the migration-owning superuser) in favor of its own `app_role`/`app_service_role` connections (`APP_DATABASE_URL`/`APP_SERVICE_ROLE_DATABASE_URL`). `ai.prisma`'s own domain carries no RLS policy (E4 T5's own header comment: "Not tenant-scoped... no RLS policy, no organizationId column on anything here"), so the specific reason `apps/api` gives (RLS bypass) doesn't literally apply to ai-engine's own tables — but connecting as the migration-owning role is a broader least-privilege question than RLS alone, and R-72 (E4) already established that "the real application connects as `app_role`, not the migration-owning superuser" as a platform-wide statement, not an `apps/api`-specific one.
**Decision:** Every real `services/*` application (ai-engine now; `speech-service`/`recommendation-engine` when they gain real database access) connects as `app_role` via `APP_DATABASE_URL`, the same role `apps/api` uses for ordinary request-scoped queries — never `DATABASE_URL`. A compromised service credential should never carry schema-altering, every-table-including-tenant-scoped-ones access, regardless of whether that specific service's own tables happen to have RLS policies. A new, narrower `appRoleDatabaseEnvSchema` fragment (`packages/config`) exposes just `APP_DATABASE_URL` — `services/*` consumers with no `app_service_role`/`BYPASSRLS` use case (ai-engine has none of apps/api's four named exceptions, ADR-022) are never required to configure a credential they'll never use. `packages/database`'s `withAiMessageEncryption` extension is now re-exported from its public barrel (previously composed only internally by `getPrismaClient()`) so a consumer connecting under a different role can still compose the same `AIMessage.content` field-level encryption onto its own client, exactly as `apps/api` already composes its own `tenantRlsExtension` this way.
**Alternatives considered:** Reusing `getPrismaClient()` directly (rejected — hardwired to `DATABASE_URL`, the exact role this ADR says a real application must never connect as); giving ai-engine `apps/api`'s full `appDatabaseEnvSchema` including `APP_SERVICE_ROLE_DATABASE_URL` (rejected — ai-engine has no BYPASSRLS use case, and requiring an unused credential is a real, if minor, unnecessary-privilege smell worth avoiding at zero cost); a brand-new `ai_engine_role` Postgres role scoped only to `ai.*` tables (rejected as premature — `app_role` already has the correct grants on every table, including `ai.*`, per E4 T11's broad grant plus `ALTER DEFAULT PRIVILEGES`; a narrower per-service role is worth revisiting only if a real reason to differentiate `app_role`'s privileges _between_ services emerges, not speculatively now).
**Consequences:** Establishes the reusable pattern every future `services/*` epic (E10 speech-service, E14 recommendation-engine, etc.) follows rather than each independently rediscovering this question. `app_role`'s grants must keep covering every table a `services/*` consumer needs, including future `ai.*` migrations (already guaranteed by E4 T11's `ALTER DEFAULT PRIVILEGES`, R-72).
**Security implications:** Directly closes a least-privilege gap that would otherwise have shipped: ai-engine handling untrusted, LLM-adjacent user input while holding schema-altering, full-database credentials would have been a materially larger blast radius for any future ai-engine-specific vulnerability (prompt-injection-driven or otherwise) than the same vulnerability under `app_role`.
**Reversibility:** High — a connection-string/role change, no data-model impact.
**Status:** Accepted (2026-08-07) — implemented in E5 T4, by the same explicit user direction covering T1–T3.

**Context:** E6 design doc §3.3 found a real bounded-context ambiguity: ARCHITECTURE.md §2.1's own table lists "Assessment" as hosted in both `apps/api` and `recommendation-engine`, but EVENT_ARCHITECTURE.md's already-cataloged `assessment.attempt.completed` row names only `apps/api` as producer. `recommendation-engine` remains an unclaimed, empty E1 skeleton (confirmed by direct inspection) and is not a listed E6 dependency (ROADMAP.md). Per ARCHITECTURE.md §2.1's own service-boundary rule ("`recommendation-engine` owns deterministic/algorithmic decisions... not require a generative model call"), the algorithm could legitimately live in either place.
**Decision:** The adaptive difficulty-stepping algorithm (E6 design doc §6.2) is implemented as `AdaptiveItemSelectionService`, a pure, stateless class inside `apps/api/src/modules/assessment/` — it takes a skill's candidate `AssessmentItem` rows and this attempt's prior responses for that skill as plain inputs and returns a selection decision; it performs no I/O itself (`AssessmentService` does the Prisma reads/writes and calls it). **Real, load-bearing detail decided during implementation, not fully specified by the design doc's own §6.2 text:** the seed item bank (E6 T1) is intentionally sparse (13 items spanning only A1/B1/C1, not all six CEFR bands) — a strict "select from the current band only" rule would dead-end the moment the running target steps into an unseeded band (e.g. A2, B2, C2). The selector therefore falls back to the nearest CEFR band (by band-index distance, either direction) that has an unserved item for that skill when the exact target band is empty, before concluding the skill has run out of content — this is a defensive extension the design doc didn't anticipate, needed because the algorithm must work against T1's real, deliberately-small seed data, not a hypothetical fully-populated bank. Skill serving order for this task is fixed: `READING`, `LISTENING`, `VOCABULARY`, `GRAMMAR` (E6 design doc §1's own listed order) — `WRITING` is deliberately excluded from T2's item-serving sequence (see this ADR's Consequences) and `SPEAKING` is out of scope entirely (§3.2).
**Alternatives considered:** Building the algorithm as real code inside `recommendation-engine` (rejected for this epic specifically, not forever — stands up a second, entirely empty service's first-ever real code inside an epic with no other reason to touch it, when a self-contained, relocatable service class inside `apps/api` satisfies every current requirement); a full item-response-theory (IRT) calibrated model (rejected — needs real attempt-outcome data this platform doesn't have yet, a cold-start problem; the simplified difficulty-stepping approach is a real, working, honestly-flagged interim, matching this platform's other provisional-parameter precedents, e.g. ADR-034's cost thresholds).
**Consequences:** `AssessmentService`'s `submitResponse` only serves `WRITING`-skill items once E6 T4/T5 land real AI scoring — serving one now with no way to score it would leave an attempt permanently unable to reach `COMPLETED` for that skill. `AssessmentModule`'s own `completeAttempt` therefore only requires the four objective skills' stop conditions to be met, not `WRITING`; wiring `WRITING` into the same lifecycle is real, tracked follow-up work for T4/T5, not silently deferred. If a future Architecture Gate review disagrees with this ADR's placement, `AdaptiveItemSelectionService`'s pure, I/O-free design makes relocating it to `recommendation-engine` a self-contained move, the same "designed to be relocatable" precedent ADR-035 already used.
**Security implications:** None beyond ordinary per-request authorization (an attempt's own owner only, enforced in `AssessmentService`, 404 not 403 on mismatch — API_GUIDELINES.md §3's no-existence-leak rule).
**Reversibility:** High — a pure service class with no `apps/api`-specific dependency; relocating it later is low-cost.
**Status:** Accepted (2026-08-07) — implemented in E6 T2, by explicit user direction to proceed past the design phase, the same distinction E4/E5/E6-T1's own status lines draw.

### ADR-039 — Writing-skill AI scoring is a new, narrow `ai-engine` capability outside `OrchestratorService`/`AIAgentSession`, not a specialist tool or a new conversational persona

**Context:** E6 design doc §6.3 designed Writing-skill scoring as a one-shot, structured-output task: given a placement-test prompt and the learner's essay, return a CEFR level, a confidence score, and short feedback. Every existing `ai-engine` capability that talks to a model is either a full conversational persona (`OrchestratorService`/`AIAgentSession`/`AIMessage`, T3/T4 of E5 — session state, rolling summaries, multi-turn memory) or a specialist _tool_ invoked mid-conversation by the Orchestrator (`GRAMMAR_COACH`/`PRONUNCIATION_COACH`/etc., gated through `ToolRegistryService`'s per-persona trigger catalog, E5 T5). Writing-skill scoring fits neither: it has no session to belong to (a placement attempt is not a `AIAgentSession`), no learner-facing conversational turn to produce, and nothing for `ToolRegistryService`'s trigger-condition catalog to gate — it is called directly by `apps/api`'s own `AssessmentService`, once per Writing item, with no Orchestrator anywhere in the call path.
**Decision:** A new, narrow `services/ai-engine/src/assessment-scoring/` module (`AssessmentScoringService.scoreWritingResponse()`) that composes three already-built E5 mechanisms directly — `RagRetrievalService.retrieveGroundingContext()` (T7, filtered to the `CEFR_DESCRIPTOR` category and the attempt's own language), `RouterService.generate()` (T1, the `'assessment'` request class E5 T1 already reserved for exactly this kind of call), and `SafetyLayerService` (T8, both `delimitUntrustedContent()` on the learner's own essay — the same prompt-injection discipline already applied to conversational summaries/memory, and `sanitizeOutput()` on the returned feedback text) — never reimplementing any of the three. The model's JSON response is validated against a new `writingCritiqueSchema` (`@linguaai/validation/ai-coaching`, this bounded context's first real content) before ever being returned; a malformed response is a thrown error, matching this epic's own "reproducible scoring" bar (ADR-037), never a silently-accepted guess. The scoring prompt is a new, standalone, versioned template — deliberately _not_ added to `PromptManagerService`'s `AgentPersona`-keyed store (`services/ai-engine/src/prompts/`), since that store's own type (`PromptTemplate.persona: AgentPersona`) is a closed seven-value union of conversational/specialist personas with no slot for a persona-less, one-shot task; forcing a new `AgentPersona` value in just to reuse `PromptManagerService.getSystemPrompt()` would misrepresent this capability as a conversational persona it structurally isn't. The template reuses `renderTemplate()` (T3's own generic `{{placeholder}}` renderer, not persona-coupled) and follows the same versioning discipline (a `version` field, bumped on any behavior-changing edit) without depending on `PromptManagerService` itself.
**Alternatives considered:** Adding Writing scoring as a new specialist tool gated through `ToolRegistryService` (rejected — every existing specialist is triggered _within_ an ongoing Orchestrator-led conversation; a placement-test attempt has no Orchestrator session at all, so there is no trigger-condition context for the registry to evaluate); treating a placement attempt as a fabricated single-turn `AIAgentSession` so the existing Orchestrator/`AIMessage` pipeline could be reused as-is (rejected — `AIAgentSession`/`AIMessage`'s own schema and semantics model an ongoing coaching relationship with memory/summarization, none of which a one-shot scoring call has any use for; forcing the fit would be the same "category error" this ADR's own title names); adding an eighth `AgentPersona` value for this capability (rejected — `AgentPersona`'s own doc comment already frames it as "the full seven-persona superset... every persona that can incur a real model-call cost," a closed, conversational/specialist set this capability doesn't belong in).
**Consequences:** This is the first real content in the `ai-coaching` bounded context (`packages/types/src/ai-coaching/`, `packages/validation/src/ai-coaching/`) — both were empty placeholders through E1–E5. `CefrLevel` is imported from `@linguaai/types/learning` rather than redefined, since it is a shared, platform-wide concept, not context-specific data (matching that file's own header comment inviting reuse). T4 builds the service only, no REST endpoint — the `apps/api`↔`ai-engine` wire contract for calling it is E6 T5's own scope, and (per RISK_REGISTER R-86) needs E5 T10's contract pattern, which is not yet merged onto this branch line.
**Security implications:** The learner's own essay text is explicitly treated as untrusted input (`delimitUntrustedContent`) before ever reaching a system-level prompt position — the same prompt-injection discipline already applied to conversation summaries/memory (T4/T6 of E5), now extended to its first genuinely adversarial-input consumer (a test-taker has a direct, undisguised incentive to try to manipulate their own score).
**Reversibility:** High — a narrow, self-contained service with no Orchestrator/session coupling; nothing else in the codebase depends on its internal shape yet.
**Status:** Accepted (2026-08-07) — implemented in E6 T4, by explicit user direction to proceed past the design phase, the same distinction E4/E5/E6-T1–T3's own status lines draw.

### ADR-040 — `recommendation-engine`'s first real domain build: deterministic plan/goal generation, zero `ai-engine` dependency

**Context:** E7 design doc §3.1 found that `recommendation-engine` has been an empty E1 skeleton (4 files, no domain code) through E1–E6 — every prior `services/*` epic either stood up `ai-engine`'s own first real code (E5) or extended it (E6 T4/T5); nothing had ever touched `recommendation-engine`. E6's own ADR-038 (Consequences) had already reserved `recommendation-engine`'s "real build-out" as this epic's own more natural first claim, matching PRD.md module 3's "adaptive curriculum" charter — this ADR is that reservation being exercised for real, not a decision reopened from scratch. `ARCHITECTURE.md`'s own domain boundary map (currently §2.1) states the service-boundary rule directly: `recommendation-engine` owns deterministic/algorithmic decisions requiring no generative model call; `ai-engine` owns anything requiring LLM generation/reasoning.
**Decision:** `LearningPlan` generation (triggered by the already-real, already-cataloged `assessment.attempt.completed` event) and `DailyGoal` nightly generation + weakness-detection scoring are built as `recommendation-engine`'s own first real domain code — a BullMQ event consumer, a BullMQ scheduled job, and a pure, I/O-free scoring function (mirroring `AdaptiveItemSelectionService`'s own "relocatable, no service-specific dependency" design, ADR-038) — with **zero dependency on `ai-engine`** anywhere in this decision's own scope: every computation is arithmetic over already-persisted `ProficiencyLevel`/`ProficiencyLevelHistory`/`ExerciseAttempt` rows, never an LLM call, matching `ARCHITECTURE.md`'s own boundary rule exactly. `recommendation-engine`'s first real Postgres connection applies ADR-036's own already-established pattern verbatim: `createRecommendationEnginePrismaClient`, structurally identical to `ai-engine`'s own `createAiEnginePrismaClient`, connecting as `app_role` via `APP_DATABASE_URL` (reusing `@linguaai/config`'s existing `appRoleDatabaseEnvSchema` fragment, not a new one) — never the migration-owning `DATABASE_URL` role. No field-level encryption extension is composed (unlike `ai-engine`'s own `withAiMessageEncryption`) — `LearningPlan`/`DailyGoal` carry no PII-equivalent free-text column the way `AIMessage.content` does.
**Alternatives considered:** Building plan/goal generation inside `apps/api`, the same way E6's own adaptive-selection algorithm lives there (rejected — unlike that algorithm, `recommendation-engine` already has an explicit PRD/ARCHITECTURE charter for exactly this domain, and ADR-038's own Consequences text already reserved this epic as its "more natural first claim"; building it a second time inside `apps/api` would leave `recommendation-engine` permanently unclaimed, directly contradicting that reservation); routing weakness-detection or plan-generation decisions through `ai-engine`'s `RouterService` (rejected — `ARCHITECTURE.md`'s own boundary rule is explicit that deterministic/algorithmic decisions never require a generative call).
**Consequences:** `recommendation-engine` now has real Prisma access, verified against the live local Postgres as `app_role` — `SELECT`/`INSERT`/`UPDATE`/`DELETE` grants on `LearningPlan`/`DailyGoal` confirmed via a direct `information_schema.role_table_grants` query (E4 T11's `ALTER DEFAULT PRIVILEGES` fix covering these tables automatically, the same positive verification E6 T1 already did for `AssessmentItem`, not assumed). Establishes the concrete precedent every future task that touches `recommendation-engine` (E9's own SRS scheduling, a future explanation-generation feature that _would_ need `ai-engine`) follows, rather than each independently rediscovering this question.
**Security implications:** None beyond ADR-036's own already-stated reasoning, now applied to a second `services/*` consumer — a compromised `recommendation-engine` credential should never carry schema-altering, every-table access, regardless of whether `LearningPlan`/`DailyGoal` carry an RLS policy of their own (they don't).
**Reversibility:** High — `createRecommendationEnginePrismaClient`/`DatabaseModule` are a self-contained connection layer with no feature-specific coupling; the scoring/generation logic this ADR also covers is designed pure and relocatable, the same "designed to be relocatable" precedent ADR-035/ADR-038 already used.
**Status:** Accepted (2026-08-07) — the Postgres-access half of this decision is implemented in E7 T1 (this task, by explicit user direction "start T1"); the deterministic plan/goal-generation logic this ADR also covers is T2/T3's own remaining scope, not yet built.

### ADR-041 — `apps/api` gets a new `CourseModule`, `ADMIN`-only authoring + `ContentVersion` snapshotting, and a third `AiRequestClass` (`'content'`) for admin-review-gated AI drafting

**Context:** E8 design doc §7 found three real gaps a single ADR needed to close before content-management work could begin: (1) no `apps/api` module owned `content.prisma`'s hierarchy (`Course`/`Level`/`Unit`/`Lesson`/`Activity`/`Exercise`/`Quiz`) despite ADR-001's own "core domain lives in `apps/api`" pattern already governing every other first-party domain; (2) `ContentVersion` (scoped to `LESSON`/`ACTIVITY`/`EXERCISE`/`QUIZ` only, per `ExerciseAttempt.contentVersionId`'s own stated purpose of pinning what a learner's attempt was actually scored against) had no writer; (3) AI-assisted content generation (§6.4) fit neither the `'teacher'` nor `'assessment'` `AiRequestClass` `RouterService` already supported (E5 T1/E6 T4) — forcing it into either would make ADR-012's own per-request-class cost-circuit-breaker monitoring misleading, the same class of category error ADR-039 already found and rejected for Writing-skill scoring.
**Decision:** A new `apps/api` `CourseModule` (`RolesGuard`-gated `ADMIN`-only authoring routes, matching `AuditController`'s own precedent) owns the full hierarchy CRUD, publish/versioning workflow, and learner-facing published-only read API (T1/T2), publishes `learning.exercise.answered`/`learning.lesson.completed` domain events on scored attempts (T3, via the existing `DomainEventPublisher`, no new transport), and gets a `ContentAuthoringController` (T4) that calls a new, narrow `services/ai-engine/src/content-authoring/` capability (`ContentDraftingService.draftLesson()`) through a new `'content'` `AiRequestClass` — composing the same already-built E5 mechanisms `AssessmentScoringService` established the pattern for (`RouterService.generate()`, `SafetyLayerService.sanitizeOutput()`, a standalone versioned prompt template deliberately not forced into `PromptManagerService`'s persona-keyed store, ADR-039's own precedent). The AI draft is **never auto-published**: `POST /v1/admin/lessons/ai-draft` returns a proposed `Lesson`/`Activity`/`Exercise` shape only — nothing is persisted on that call path — and an `ADMIN` must explicitly review/edit and submit it through T1's own real create/update endpoints, directly extending `AI_SYSTEM.md` §3's "never model-generated content feeding back... uncurated" principle from the RAG knowledge base to authored curriculum content.
**Alternatives considered:** A separate `content-service` microservice (rejected per ADR-001 — content CRUD needs no independent scaling/runtime isolation/blast-radius separation from `apps/api`'s core domain); reusing `AssessmentModule`'s objective-scoring util for `Exercise` attempts (rejected — `ExerciseType`/`AssessmentItemType` are independently-defined enums with only superficial overlap; a shared scorer would silently drop `MATCHING`/`TRANSLATION`/`LISTENING_COMPREHENSION` support or corrupt `AssessmentModule`'s own type); forcing AI-assisted drafting into the existing `'assessment'` request class (rejected — materially different cost/latency/safety profile, would corrupt ADR-012's per-class monitoring); auto-publishing AI-generated drafts directly (rejected — contradicts `AI_SYSTEM.md` §3 and RISK_REGISTER R-03's own "content pipeline" quality-risk framing).
**Consequences:** Establishes the concrete, load-bearing precedent every future content-adjacent epic (E9 Vocabulary, E12 Listening/Reading, E13 Writing/Story Generator — all depend on E8 per ROADMAP.md) builds on top of, for both the authoring-module shape and the AI-request-class extension pattern. `RouterService.modelFor()`'s original binary ternary (`'teacher' | 'assessment'`) was refactored into switch-based `defaultModelFor()`/`economyModelFor()` lookups (T4) since a ternary cannot scale to a third class — the concrete implementation detail this ADR's own request-class extension required. The draft schema's `contentDraftExerciseSchema.type` excludes `SPEAKING_PROMPT` at the Zod level (not just prompt instruction), since that exercise type can never actually be attempted under this epic's own §6.2 scope boundary (422-rejected pending `services/speech-service`, E10) — generating a draft of it would be a genuine design smell, not a real proposal.
**Security implications:** No `delimitUntrustedContent` call wraps the admin-supplied drafting `topic` input, a deliberate departure from `AssessmentScoringService`'s treatment of a learner's own essay — the caller of `ContentDraftingService.draftLesson()` is always an authenticated `ADMIN` (a trusted actor class under this platform's threat model), not an anonymous, potentially-adversarial learner. `ContentAuthoringController` carries the same `AuthGuard('jwt') + RolesGuard + MfaGuard` stack as every other `ADMIN`-only route (ADR-011).
**Reversibility:** High — `CourseModule` and `ContentAuthoringModule` are self-contained; the `'content'` request class is an additive union member with no coupling to `'teacher'`/`'assessment'` call sites.
**Status:** Accepted (2026-08-08) — implemented across E8 T1–T4 (T1: hierarchy CRUD + `ContentVersion`, T2: learner-facing read API + attempt scoring, T3: domain event emission, T4: AI-assisted drafting, this task), by explicit user direction to proceed past the design phase task-by-task, the same distinction E6/E7's own status lines draw. E8's own §9 task sequence is now fully delivered — no further task remains.

### ADR-042 — The SM-2-derivative SRS scheduling algorithm lives in `apps/api`'s own `VocabularyModule`, not `recommendation-engine`

**Context:** E9 design doc §3.1 found a real tension: ARCHITECTURE.md §2.1's own service-boundary rule names "SRS scheduling" _by name_ as an example of what `recommendation-engine` owns ("deterministic/algorithmic decisions... not require a generative model call"). But `recommendation-engine`'s own real code, established across E7 T1–T3, is exclusively asynchronous — a BullMQ event consumer (`LearningPlan` generation on `assessment.attempt.completed`) and a nightly scheduled job (`DailyGoal` generation) — with zero public HTTP surface to any frontend (confirmed by direct inspection: only `health.controller.ts` exists there today). Flashcard review is a synchronous, per-request learner action: a learner reviews a card and needs an immediate response (the updated schedule, so the UI can show the next card) — the same shape of requirement ADR-038 already found for the adaptive item-selection algorithm, resolved the same way.
**Decision:** The SM-2-derivative scheduling algorithm (`applySm2Review`, `apps/api/src/modules/vocabulary/srs-scheduling.util.ts`) and its review-submission endpoint (`SrsDeckController`/`SrsDeckService`) live in `apps/api`'s own `VocabularyModule`, not `recommendation-engine` — a deliberate, documented departure from ARCHITECTURE.md §2.1's literal example. `applySm2Review` is a pure, stateless function (`{easeFactor, intervalDays, repetitions}` in, the same shape out) — it performs no I/O and knows nothing of `Date`/wall-clock time; `SrsDeckService` is the only caller that converts `intervalDays` into a real `nextReviewAt` timestamp. `POST /v1/vocabulary/deck` (idempotent add-to-deck, via Prisma `upsert`), `GET /v1/vocabulary/deck/due` (cursor-paginated, `nextReviewAt <= now()`), and `POST /v1/vocabulary/deck/:id/reviews` (`quality: 0-5`, the literal standard SM-2 input scale) are all `apps/api`-hosted, any-authenticated-user routes, ownership-checked by hand (404, not 403, on a cross-user access attempt — `vocabulary.prisma` carries no RLS policy on `UserVocabulary`).
**Alternatives considered:** Building the scheduler inside `recommendation-engine` (rejected — would require standing up that service's first-ever frontend-facing HTTP endpoint, a genuinely new architectural precedent for a service whose real code to date is 100% asynchronous; `apps/api` already owns every other synchronous per-request domain write in this platform, e.g. `ExerciseAttemptsService`/`exercise-scoring.util.ts`, E8 T2); building it as a synchronous call from `apps/api` into a new `recommendation-engine` HTTP endpoint (rejected — real added latency and a new inter-service failure mode for a computation with no actual need for `recommendation-engine`'s own infrastructure, since it touches no data that service owns); treating cramming (reviewing a not-yet-due card) as disallowed and gating `submitReview` on `nextReviewAt <= now()` (rejected — a real, deliberate permissiveness call, design doc §6.3: a learner may legitimately want to review early, and gating it would fight the learner rather than help them).
**Consequences:** The PRD's own literal module-6 acceptance bar ("SRS scheduling follows a documented algorithm (SM-2 derivative)") is now met for real — `applySm2Review`'s own doc comment states the formula precisely (the 0.1/0.08/0.02 ease-factor coefficients, the 1.3 floor, the 1-day/6-day first-two-repetition stages), and it is exhaustively unit-tested (9 tests covering every branch: failure resets, the ease-factor floor under repeated failure, each of the three interval-growth stages, and a failure-then-recovery sequence). If a future, independent Architecture Gate review disagrees with this ADR's placement, `applySm2Review`'s pure, I/O-free design makes relocating it to `recommendation-engine` a self-contained move — the same "designed to be relocatable" precedent ADR-035/038/040 already relied on.
**Security implications:** None beyond ordinary per-request ownership enforcement (404 not 403 on a cross-user deck-entry access, API_GUIDELINES.md §3's no-existence-leak rule, matching `PersonalDictionaryService`'s own established discipline). No `Idempotency-Key` handling was added to `POST /v1/vocabulary/deck/:id/reviews` — it inherits the same pre-existing, platform-wide gap RISK_REGISTER R-85 already tracks, confirmed absent from every other retryable `POST` in this codebase including E8 T2's own `ExerciseAttemptsController`, not a new omission specific to this task.
**Reversibility:** High — `applySm2Review` has zero dependency on `apps/api`-specific infrastructure; `SrsDeckService`'s own Prisma access is the only part that would need to move.
**Status:** Accepted (2026-08-08) — implemented in E9 T3, by explicit user direction ("E9: T3") to proceed past the design phase, the same distinction E4–E8's own status lines draw.

### ADR-043 — STT/TTS pinned to OpenAI; the client connects directly to `speech-service` over WebSocket after an `apps/api`-minted, locally-verifiable internal token

**Context:** E10 design doc §3.3/§3.5 found two real, load-bearing gaps a single ADR needed to close before the speaking-practice pipeline could be built: (1) no STT/TTS provider had ever been pinned anywhere in this platform's docs — `AI_SYSTEM.md` names the adapter _pattern_ but never a concrete provider, the same class of "pattern specified, value left open" gap ADR-031 already closed for the embedding model; (2) `ARCHITECTURE.md` §6's own "Speaking practice session" data-flow example states plainly that "Client opens a WebSocket to `apps/api`, which authenticates and hands off session control to `services/speech-service` via an internal token" but never specifies whether `apps/api` proxies every subsequent audio frame (a WS-to-WS relay) or the client reconnects directly to `speech-service` after the handoff — a real topology decision left implicit, and genuinely load-bearing for PERFORMANCE.md §2's own tight 300ms transport-overhead budget.
**Decision:** Both STT and TTS are pinned to OpenAI (`whisper-1` transcription, `tts-1`/`alloy` synthesis) — reusing this platform's already-integrated `OPENAI_API_KEY`/subprocessor relationship, behind a provider-agnostic `SttProvider`/`TtsProvider` adapter pair (`services/speech-service`, T1) mirroring `ai-engine`'s own `ModelProvider` interface-segregation pattern (ADR-006), so a future provider swap stays a configuration change. No second, failover STT/TTS provider is built — AI_GOVERNANCE.md §7's own already-decided fallback for a provider failure is "degrade to text-only," not a failover chain (§6.5). The client connects **directly** to `speech-service` over WebSocket after `apps/api`'s new `SpeakingModule` (T2) creates the underlying `AIAgentSession` (`orchestratorAgent: CONVERSATION_PARTNER`, via the existing `AiEngineClientService.startSession()`, its first real caller) and mints a short-lived (60s), narrowly-scoped, HMAC-signed token (claims: `sessionId`, `userId`, `exp` — `packages/utils`' hand-rolled `signSpeechSessionToken`/`verifySpeechSessionToken`, T1, deliberately not `jsonwebtoken` to keep that package dependency-free) — never an `apps/api`-proxied relay of every audio frame. `speech-service` verifies the token locally (T1's `SessionTokenService`) with zero network round-trip back to `apps/api`. `DELETE /v1/speaking-sessions/:id` ends the session via a real ownership check this task also added to ai-engine's own `OrchestratorService.endSession()` — previously a blind, unauthenticated update by id alone; now 404s (not silently succeeds, API_GUIDELINES.md §3's no-existence-leak rule) when the caller-supplied `userId` (never a client-controllable value — always `req.user.userId` from the verified JWT) doesn't match the session's own owner, closing a real hole a bare `sessionId`-only end call would have left open.
**Alternatives considered:** `apps/api` proxying every audio frame to `speech-service` (rejected — a real double-hop consuming a meaningful fraction of the 300ms transport budget for zero benefit; the direct-connection-after-token-handoff model achieves the same authentication guarantee without it); a second, failover STT/TTS provider mirroring the LLM primary→secondary chain (rejected — AI_GOVERNANCE.md §7's own already-decided, materially simpler "degrade to text-only" fallback already covers this); `speech-service` verifying the token against apps/api over the network on every connection (rejected — defeats the latency purpose of minting a locally-verifiable token at all; the whole point of an HMAC-signed token is that the holder of the shared secret can verify it without a round trip); leaving `endSession` as a blind, ownership-unchecked update (rejected once found — a real, concrete availability/correctness hole: any authenticated learner could otherwise end any other learner's active session by guessing or observing its UUID).
**Consequences:** `services/speech-service` gets its first real domain code (T1) rather than remaining a pure E1 skeleton. `startSession()`/`endSession()` (registered app-wide since E5 T10 but unconsumed until now) get their first real caller. `OrchestratorService.endSession()`'s signature changed (`EndSessionInput` gains a required `userId`) — a real, deliberate breaking change to an internal-only contract with exactly one caller (`AiEngineClientService`), not a public API, so no versioning/deprecation concern applies. The actual live-provider latency measurement RISK_REGISTER R-04 calls for ("a provider spike before full commitment") remains unexecuted in this credential-less environment (RISK_REGISTER R-88) — flagged as real, tracked follow-up, not silently declared satisfied.
**Security implications:** The internal token is deliberately narrow (only `sessionId`/`userId`/`exp`, no broader access) and short-lived (60s — long enough to complete a WebSocket handshake, short enough that a leaked token has almost no exploitation window); signature verification runs before JSON parsing (`verifySpeechSessionToken`, T1) — a deliberate ordering, never parse unverified data. The `endSession` ownership fix is itself a genuine, if narrow, security hardening found and closed during this task, not a pre-existing, separately-tracked gap.
**Reversibility:** Medium — the provider pinning is low-cost to reverse (adapter interface already abstracts it, ADR-006's own precedent); the direct-connection topology is more load-bearing, since T3's own WebSocket gateway (not yet built) will be designed against it — reversing to an `apps/api`-proxied relay after T3 ships would mean rebuilding that gateway's own connection-handling assumptions, not a pure configuration change.
**Status:** Accepted (2026-08-08) — the provider-pinning half (STT/TTS adapters) implemented in E10 T1; the session-lifecycle/token-topology half (this task's own primary scope) implemented in E10 T2, by explicit user direction ("next T2") to proceed past the design phase, the same distinction E4–E9's own status lines draw. The real-time WebSocket gateway itself (T3) — the component that actually consumes this token — remains unbuilt.

### ADR-044 — `services/speech-service` gets no direct Postgres access to `ai.prisma`'s conversation tables; all `AIAgentSession`/`AIMessage`/`FluencyScore` persistence routes through `ai-engine`'s internal HTTP API

**Context:** E10's design (§4) assigns `services/speech-service` the real-time WebSocket gateway and STT/TTS provider adapters, while `ai-engine` remains the sole owner/writer of `ai.prisma`'s conversation tables (`AIAgentSession`/`AIMessage`/`FluencyScore`). A real, concrete security-driven boundary decision was needed: two services independently writing to the same encrypted column (`AIMessage.content`, field-level encrypted per ADR-029) is a genuine future-drift risk — a second Prisma client could silently bypass the encryption extension if independently configured.
**Decision:** `services/speech-service` connects to Postgres as `app_role` (ADR-036's established pattern) but receives **no `ai.prisma` domain access at all** — it has no Prisma client for `ai.prisma`, no migration file in `packages/database/schema/`, and no direct database credential scoped to conversation tables. All `AIAgentSession`/`AIMessage`/`FluencyScore` persistence goes through `ai-engine`'s own internal HTTP API (extending ADR-033's established `apps/api`↔`ai-engine` REST contract pattern to a second internal caller). `ai-engine` remains the single service responsible for applying `withAiMessageEncryption` (ADR-029) on every `AIMessage` write.
**Alternatives considered:** Giving `speech-service` its own `ai.prisma`-scoped Prisma client with the encryption extension composed onto it (rejected — duplicates the encryption discipline across two independently-configured clients; a future developer adding a write path in `speech-service` could easily forget to apply the extension, silently producing plaintext `AIMessage.content`); letting `speech-service` write directly to `AIAgentSession`/`AIMessage` without encryption because "the gateway never sees raw learner text, only audio" (rejected — the STT transcript is the learner's text, written to `AIMessage.content` by `ai-engine`'s extended `AgentSessionsController`; `speech-service` never holds the plaintext, but `ai-engine` does, and centralizing the write path is the actual security boundary).
**Consequences:** `speech-service` gains a hard dependency on `ai-engine`'s internal HTTP API shape — a real, accepted coupling (the same class ADR-033 already established for `apps/api`). Any change to `AIAgentSession`/`AIMessage`'s write contract in `ai-engine` must be coordinated with `speech-service`'s consumer side. `app_role`'s grants must cover `ai.*` tables for `speech-service`'s future read needs (E10 T4's round-trip extension) — already guaranteed by E4 T11's `ALTER DEFAULT PRIVILEGES` (ADR-036).
**Security implications:** Directly closes the encryption-duplication risk — there is now exactly one service that can write `AIMessage.content`, and exactly one place the encryption extension is applied. A second service independently writing to the same encrypted column is no longer possible because the second service has no database access to that column at all.
**Reversibility:** Medium — reintroducing direct database access to `speech-service` would require a new Prisma client, the encryption extension, and a new `app_role` grant scope, but no data-model change.
**Status:** Accepted (2026-08-11) — implemented in E10 T1–T3, by explicit user direction to proceed with T3's WebSocket gateway, the same distinction prior E10 ADRs draw.

### ADR-045 — Raw `ws` + manual HTTP upgrade for `speech-service`'s WebSocket gateway, not `@nestjs/websockets` or Socket.IO

**Context:** E10 T3 needs a real-time WebSocket endpoint (`/realtime/speaking-sessions/:sessionId`) that terminates directly on `services/speech-service`'s own HTTP server. Three options existed: NestJS's `@nestjs/websockets` Gateway abstraction (decorator-driven, platform-level `ws`/`socket.io` adapter), Socket.IO (full framework with rooms/acks/reconnection built in), or raw `ws` with a manual `upgrade` listener on the underlying Node.js HTTP server. The platform's own API_GUIDELINES.md §7 specifies WSS with a `{type, payload, sessionId, ts}` envelope and per-chunk ack semantics — neither abstraction models the binary-audio/JSON-control split or the per-connection auth flow this endpoint requires.
**Decision:** Raw `ws` (v8) with `WebSocketServer({ noServer: true })` and a manual `'upgrade'` listener attached to NestJS's underlying HTTP server via `HttpAdapterHost`. The token minted by `apps/api` (T1/T2) is verified in the upgrade handler — before the WebSocket handshake completes — using `SessionTokenService.verify()`. Only after verification does `wss.handleUpgrade()` run. Per-connection message routing lives in a framework-agnostic `SpeechSessionConnection` class, keeping the gateway thin (auth + socket lifecycle) and the business logic directly unit-testable against a plain fake client.
**Alternatives considered:** `@nestjs/websockets` Gateway (rejected — the Gateway abstraction assumes the server manages the entire WebSocket lifecycle; per-connection auth that runs _before_ the handshake completes (the T1/T2 short-lived token, never after) is awkward to express, and the decorator model doesn't cleanly separate binary-audio ingestion from JSON-control-message routing); Socket.IO (rejected — a full transport framework with its own protocol overhead, room/namespace model, and reconnection semantics that don't match API_GUIDELINES.md §9's already-specified contract; adds ~30kB of client-side JS the web/mobile apps don't need and forces a Socket.IO client on every platform); `apps/api` proxying every audio frame to `speech-service` (rejected — a real double-hop that consumes a meaningful fraction of PERFORMANCE.md §2's own 300ms transport-overhead budget for zero benefit; the direct-connection-after-token-handoff model achieves the same authentication guarantee without it).
**Consequences:** The gateway owns the HTTP upgrade path directly — a deliberate trade-off against NestJS's abstraction model, accepted because the manual upgrade handler is ~40 lines of well-contained code and the latency/security properties it buys (pre-handshake auth, binary/JSON split) are load-bearing for this endpoint. A dropped connection's graceful resumption (E10 T7) and the 60s grace window (API_GUIDELINES.md §9) are implemented in application logic (`SpeechSessionConnection` + in-memory turn state), not in the transport layer — Socket.IO's built-in reconnection was the only alternative that would have provided this for free, but its protocol mismatch with the platform's own envelope format ruled it out.
**Security implications:** Token verification before the handshake completes means a client with an invalid or expired token never gets a WebSocket — the server returns a proper HTTP 401 response and destroys the socket, matching API_GUIDELINES.md §9's "no existence leak" rule (a 101 Switching Protocols response would implicitly confirm the endpoint exists even to an unauthenticated caller).
**Reversibility:** High — `ws` is already a dependency (added in E10 T1); the `noServer` + manual upgrade pattern is a standard `ws` usage mode, not a custom protocol; moving to `@nestjs/websockets` later would require rewriting the gateway class but not the underlying `SpeechSessionConnection` business logic.
**Status:** Accepted (2026-08-11) — implemented in E10 T3, by explicit user direction to proceed with T3's WebSocket gateway, matching the prior E10 T1–T2 ADR precedent.

### ADR-046 — The `services/speech-service` e2e test wrapper uses a dedicated `.env.e2e` file instead of the root `.env`

**Context:** E10 T3's e2e test suite (`test:e2e:api`) needs `SPEECH_SESSION_TOKEN_SECRET` to sign/verify test tokens, but loading the root `.env` via `dotenv-cli` also brings in `OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318` (set for production observability, ADR-016). When `app.close()` runs during test teardown, OpenTelemetry's `BatchSpanProcessor` tries to flush remaining spans to that endpoint — which isn't running in this test environment — producing an `ECONNREFUSED` `AggregateError` that causes Jest to report a suite failure even though every individual test passes.
**Decision:** `test:e2e:api` loads `services/speech-service/.env.e2e` (a committed file containing only `SPEECH_SESSION_TOKEN_SECRET=local-dev-speech-session-token-secret-not-for-prod`) instead of the root `.env`. The full `.env`'s database, Redis, OAuth, and OTLP settings are not needed by the e2e suite because `SpeechProviderModule`'s config is overridden with a dummy value in the test module, and the health/gateway endpoints exercise no external service.
**Alternatives considered:** Overriding `OTEL_EXPORTER_OTLP_ENDPOINT` in the `dotenv-cli` command (rejected — `dotenv-cli`'s `-v` flag doesn't accept empty-string overrides, so we can't unset a value already loaded from `.env`); catching the `AggregateError` in `afterAll` and swallowing it (rejected — works, but leaves an open-handle warning and masks a real configuration problem that would affect any future e2e test that _does_ need OTLP); setting `OTEL_TRACES_EXPORTER=none` (rejected — the `@linguaai/observability` package doesn't read that env var; it only checks `OTEL_EXPORTER_OTLP_ENDPOINT`).
**Consequences:** `.env.e2e` is a new, service-specific test-scoped env file. Any future e2e test in `speech-service` that needs additional vars adds them here. The file is committed (the secret value is a local-dev placeholder, not a real credential), matching the existing `.env` pattern.
**Security implications:** None — the value in `.env.e2e` is the same local-dev placeholder already present in the root `.env`, never a production credential.
**Reversibility:** High — reverting to `dotenv -e ../../.env` is a one-line change; `.env.e2e` can be deleted.
**Status:** Accepted (2026-08-11) — implemented alongside E10 T3's e2e test suite, by explicit user direction to fix the `test:e2e:api` dotenv wrapper.

### ADR-047 — `services/speech-service`'s first real object-storage consumer: `@aws-sdk/client-s3` against the already-configured S3/MinIO target, storing a stable (not presigned) URL

**Context:** E10 T4 (design doc §6.3 steps 3-4) needs both `AIMessage` rows a speaking turn produces to get a real `audioUrl` — the learner's own recorded audio, and the assistant's own synthesized reply. `.env`/`.env.example` have declared `S3_ENDPOINT`/`S3_REGION`/`S3_BUCKET`/`S3_ACCESS_KEY_ID`/`S3_SECRET_ACCESS_KEY`/`S3_FORCE_PATH_STYLE` since E1 (DATABASE.md's own named object-storage target), and `docker-compose.yml`'s `minio-init` step already auto-creates the `linguaai-media` bucket — but a full-repo search confirms zero code anywhere has ever consumed these vars or called any S3 SDK; `AIMessage.audioUrl`/`AssessmentItem.audioUrl`/`VocabularyItem.audioUrl` have all sat null since their own respective schemas landed. The same "pattern specified, value left open" gap ADR-031 (embedding model) and ADR-043 (speech providers) already closed for their own domains.
**Decision:** A new `AudioStorageProvider` adapter (`services/speech-service/src/audio-storage/`, mirroring `SttProvider`/`TtsProvider`'s own ADR-006 interface-segregation precedent) with one real implementation, `S3AudioStorageProvider`, built on `@aws-sdk/client-s3`'s `PutObjectCommand` — works against both MinIO (local dev, `S3_FORCE_PATH_STYLE=true`, path-style URLs) and real AWS S3 (production, virtual-hosted-style URLs) via the SDK's own `forcePathStyle` flag. `SpeechSessionConnection` (T4) uploads the turn's raw audio once `speech.end-of-turn` arrives (key: `speaking-sessions/<sessionId>/<turnNumber>-user.webm`) before calling `ai-engine`, and the accumulated synthesized-speech bytes once the assistant's own reply and TTS both finish (key: `...-assistant.mp3`), attaching that second URL via the new `PATCH .../audio-url` endpoint (this same task, extending ADR-033/044's established `apps/api`-and-now-`speech-service`↔`ai-engine` internal-HTTP pattern). `AudioUploadResult.url` is a **stable, non-expiring** reference (the object's own direct S3/MinIO URL) — not a time-limited presigned URL — a deliberate choice matching `AIMessage.audioUrl`'s own schema shape: a plain, permanently-stored `String?` column with no companion expiry/key field this task's own scope doesn't add, so a URL that later stops working would silently corrupt an already-persisted row.
**Alternatives considered:** A presigned, time-limited GET URL (rejected for now — the objectively "more correct" production access-control pattern for private learner voice data, but incompatible with `audioUrl`'s own durable-storage schema shape without also adding a schema migration and a signed-URL-on-read serving layer, both genuinely out of this task's scope); making the bucket public-read (rejected — a real, serious privacy exposure for personal spoken-conversation recordings, which SECURITY.md's own file-upload-handling guidance implicitly rules out by treating voice recordings as sensitive); building a CloudFront-fronted signed-URL gateway now (rejected — ARCHITECTURE.md §7 names CloudFront-in-front-of-S3 as the production target for course media, but no CDN infrastructure of any kind exists yet anywhere in this repo; premature to build for one task when the underlying schema doesn't yet support it either).
**Consequences:** `services/speech-service` gains its first AWS SDK dependency (`@aws-sdk/client-s3`, versioned to match `packages/database`'s own already-present `@aws-sdk/client-kms`). **A real, deliberately-not-closed gap, flagged rather than silently left implicit:** because the bucket `minio-init` creates is private by default and this task stores a stable (not presigned) URL, the `audioUrl` values persisted today are **not actually fetchable** by an end-user client without a future signed-URL-on-read serving layer (or a bucket policy change) — tracked as RISK_REGISTER R-93, real follow-up work for whichever future task builds the actual playback UI (out of this backend-only epic's own scope, §3.6). **A second, separately-flagged gap:** SECURITY.md §"File upload handling" requires uploaded voice recordings to go through "virus/malware scanning on ingest" — no such scanning infrastructure exists anywhere in this platform (E1-E9 never built one), and this task does not add it either; also tracked in R-93, not silently declared satisfied.
**Security implications:** Content-Type/size are set server-side from what `speech-service` itself already knows (never trusting a client-supplied MIME type) — the "validates content type/size server-side" half of SECURITY.md's own requirement is met; the "virus/malware scanning on ingest" half is not (see Consequences). Credentials are read via the same `loadConfig`/env-schema discipline every other secret in this platform uses — no credential is ever logged or embedded in a returned URL.
**Reversibility:** Medium — `AudioStorageProvider`'s own interface is adapter-shaped and swappable (a presigned-URL implementation could replace `S3AudioStorageProvider` without touching `SpeechSessionConnection`'s own call sites), but every already-persisted `audioUrl` value would need a backfill/migration if the URL _shape_ itself later changes (e.g. switching to a `audioKey`-plus-signed-URL-on-read model).
**Status:** Accepted (2026-08-11) — implemented in E10 T4, by explicit user direction ("T4") to proceed past the design phase, the same distinction prior E10 ADRs draw.

### ADR-048 — A fourth `AiRequestClass` (`'fluency'`) for session-end speaking-practice scoring, and `FluencyScoringService` reads `ai-engine`'s own already-persisted transcript rather than a caller-supplied one

**Context:** E10 T5 (design doc §6.4) needs to score a just-ended speaking session's overall fluency and extract notable vocabulary — a one-shot, structured-output task, the same shape `AssessmentScoringService` (ADR-039, `'assessment'`) and `ContentDraftingService` (ADR-041, `'content'`) already established their own request classes for. Neither existing class fits: `'assessment'` was scoped specifically to single-essay placement-test writing critique (ADR-039's own Context), a materially different rubric/input shape from scoring an entire multi-turn conversation transcript; `'content'` was scoped to admin-review-gated creative drafting (ADR-041), not scoring at all. Forcing this call into either would corrupt ADR-012's own per-request-class cost-circuit-breaker monitoring, the same category error ADR-039/041 already avoided for their own domains.
**Decision:** `AiRequestClass` gains a fourth value, `'fluency'` (`services/ai-engine/src/gateway/router.service.ts`), with matching `AI_MODEL_FLUENCY_DEFAULT`/`AI_MODEL_FLUENCY_ECONOMY` config (`aiGatewayEnvSchema`) and `RouterService.defaultModelFor()`/`economyModelFor()` switch cases — TypeScript's own exhaustiveness checking on the switch (no `default` case) forces every future `AiRequestClass` addition through this same two-switch update, real compile-time insurance against a silently-unhandled class. A new `FluencyScoringService`/`FluencyScoringController` (`services/ai-engine/src/fluency-scoring/`, `POST /v1/fluency-scoring`, ADR-033's internal-trust pattern) is a genuine departure from `AssessmentScoringService`/`ContentDraftingService`'s own "no session concept, caller supplies all content" shape: it takes only a `sessionId` and reads that session's own already-persisted `AIMessage` history directly via `ai.prisma` (`ai-engine` already owns this table, ADR-044) — there is no fresh content for a caller to hand over, only existing history to score. Writes a real `FluencyScore` row and returns extracted vocabulary for the caller (`apps/api`'s `SpeakingService`) to persist into the learner's own personal dictionary — `ai-engine` itself never touches `PersonalDictionary` (a `vocabulary.prisma`/`apps/api`-owned table it has no access to).
**Alternatives considered:** Overloading `'assessment'` (rejected — a materially different rubric/output shape and a live-conversation, not placement-test, context, the same reasoning §3.8 of the E10 design doc already used to justify a new class rather than reusing `'content'` for this exact call); routing fluency scoring through `OrchestratorService`/a new `AIAgentSession`-bound specialist persona (rejected — scoring an _already-ended_ session has no conversational turn of its own, no memory/multi-turn concept ADR-007's single-Orchestrator model exists to serve); having the caller (`apps/api`) pass the full transcript as request content, mirroring `scoreWritingRequestSchema`'s own caller-supplies-everything shape (rejected — `apps/api` has no direct read access to `AIMessage.content`'s field-level-encrypted rows and no business reading them decrypted outside `ai-engine`'s own boundary; `ai-engine` already has the real data in hand, so a `sessionId`-only request avoids a redundant, `apps/api`-side re-fetch-and-forward round trip).
**Consequences:** `FluencyScoringService` is idempotent by a cheap application-level check (an existing `FluencyScore` row for a `sessionId` short-circuits re-scoring and returns an empty `extractedVocabulary`, avoiding duplicate `PersonalDictionary` writes on a retried `DELETE /v1/speaking-sessions/:id`) — a real, narrow mitigation, not a claim that this closes RISK_REGISTER R-85's own broader "no generic Idempotency-Key infrastructure" gap platform-wide. `.env.example`'s own pre-existing drift (missing `AI_MODEL_CONTENT_DEFAULT` since ADR-041, never previously caught) was found and fixed alongside adding the new `AI_MODEL_FLUENCY_*` vars.
**Security implications:** None beyond the already-accepted `'content'`/`'assessment'` precedent — `FluencyScoringController` carries no auth guard (ADR-033's internal-network-only trust boundary, `apps/api`'s own already-authenticated request). Model-generated `feedback`/vocabulary `translation`/`notes` fields are all sanitized (`SafetyLayerService.sanitizeOutput()`) before ever leaving `ai-engine`, the same AI_GOVERNANCE.md §7 discipline every other model-generated free-text field in this platform already carries; the transcript itself is delimited as untrusted content before it reaches the model's own prompt, mirroring `AssessmentScoringService`'s own treatment of a learner's essay.
**Reversibility:** High — `'fluency'` is an additive union member with no coupling to `'teacher'`/`'assessment'`/`'content'` call sites; `FluencyScoringService` is a self-contained module.
**Status:** Accepted (2026-08-12) — implemented in E10 T5, by explicit user direction ("T5") to proceed past the design phase, the same distinction prior E10 ADRs draw.
